# Part I — Projection, Applied

## 3. Projection Rules

ZRM-003B §10 (PJ-D01) defines a Projection abstractly: `π : G → G'`, preserving a named subset of properties. Semantic Projection is the specific case where `G'` is a space of **semantic labels** — Touchpoint, Intent, Contract, etc. — rather than another Reality Graph.

### **Rule PR-001 — No New Facts.** 
A Semantic Projection may relabel, aggregate, or interpret existing structure in `G`. It SHALL NOT introduce a vertex, edge, State, or Event that doesn't already exist in `G` as established by ZRM-003B/004. If a semantic construct requires something to exist that isn't already provable from prior documents, that is a gap in this document, not license to assert it.

### **Rule PR-002 — Reversibility of Reference.** 
Every semantically labeled construct SHALL be traceable back to the specific vertices, edges, or States in `G` it was projected from. A semantic label with no traceable origin in `G` is not a valid projection.

## 4. Projection Correctness

A Semantic Projection `π` is correct with respect to a named construct iff every property that construct's derivation claims to preserve is actually preserved by `π`, per PJ-D01's correctness condition. Each derivation in §6 states explicitly what it preserves; that statement is the correctness claim for that construct, open to falsification by S6 like any other.

# Part II — Semantic Projection

## 5. Identity Resolution, in Practice

ZRM-003B ID-T01 establishes that Identity is unique and immutable. In practice, resolving "which Identity does this access path point to" is itself a Projection: given a vertex `v ∈ V` reachable through some access mechanism, resolution is the function `resolve : AccessPath → V` returning the unique `v` such that `i(v)` holds (ID-T01). This is the formal basis for Touchpoint below — Touchpoint *is* the access mechanism this function takes as input.

## 6. Derived Semantic Constructs

### 6.1 Touchpoint
*Legacy origin: WS-01 §5.3, WS-02 Primitive 03 — "a mechanism through which an actor accesses an identity."*

**Derivation.** A Touchpoint is an Object (ZRM-002 §4.2) whose defining Relationship (ZRM-003B §5) is that it serves as the domain of the `resolve` function in §5: `∀ tp ∈ Touchpoint : ∃ v ∈ V : resolve(tp) = v`. A Touchpoint has no independent constitutional status beyond this — it is not a new primitive, it is an Object playing a specific structural role.

**What this preserves:** the WS-01 distinction "Touchpoint ≠ Identity ≠ Referent" falls out automatically — `tp`, `resolve(tp)`, and the Object `resolve(tp)` identifies are three distinct elements of `G` by construction.

### 6.2 Intent
*Legacy origin: WS-03A.4 — "a desired future state expressed by an Actor," closed vocabulary of 12 types.*

**Derivation.** Using ZRM-003B's State Mathematics (§9): an Intent is a Relationship between a Subject `s` and a candidate future State `State(x, t')` where `t' ` is not yet realized — `intent(s, x, t') `, read as "`s` desires `x` to reach the state described by `t'`." This is consistent with WS-03A.4 CP-INT-04/CP-INT-05: Intent does not itself cause a State Transition (ZRM-003A §4.5) — it names one as desired. Only a Transaction (§6.5) can actually cause it.

**Preserved closed vocabulary** (WS-03A.4 §3, unchanged in substance, re-derived as labels over the `intent` relation rather than free-floating types): Discover, Access, Verify, Authenticate, Register, Claim, Purchase, Transfer, Return, Support, Subscribe, Trigger. Each names a category of desired State transition, not a new mathematical object.

**Preserved principle** (CP-INT-02, Intent is Atomic): `intent(s, x, t')` names exactly one desired State, never a composite of several.

### 6.3 Intent Contract
*Legacy origin: WS-03A.5 — "how an Intent may be fulfilled."*

**Derivation.** Using ZRM-003B's Mathematical Transformations (§11, TR-D01): a Contract is a Transformation `f : (intent(s, x, t'), State(x, t)) → Transaction-candidate`, i.e. a function that, given a desired State and the current State, produces a candidate Transaction capable of closing the gap between them — subject to whatever Constraints (ZRM-003B §12) apply.

**Preserved principle** (CP-CTR-03, execution-oriented not business-specific): the Transformation `f` is defined over the *shape* of the State gap, not over which specific Object or Referent is involved — this is exactly why WS-03A.5 prohibits referent-specific contracts (no `CoffeePurchaseContract`), and it now follows from the Transformation being defined generically over State pairs rather than specific vertices.

### 6.4 System
*Legacy origin: WS-01 §5.8, WS-02 Primitive 09 — "a mechanism capable of executing Transactions."*

**Derivation.** A System is an Object that is the acting party of a Mathematical Transition (ZRM-003A §4.5) — i.e., the entity that carries out the function derived in §6.3 and produces the resulting Transaction (§6.5). A System is never a Subject in the constitutional sense (ZRM-002 §4.1); it executes on behalf of one, per SEC-001's existing Authority-before-Execution chain.

### 6.5 Transaction
*Legacy origin: WS-03A.6 — immutable Subject-Predicate-Object Reality Claim.*

**Derivation.** This is the cleanest derivation in the set. A Transaction is precisely an **Event** (ZRM-004 EV-T01–EV-T09) whose effect is a single, atomic change to the edge set `E` of the Reality Graph (ZRM-003B GR-D01): establishing, terminating, reversing, or superseding one edge `(subject, predicate, object) ∈ E`.

- EV-T01 (Immutability) → the Transaction record itself never changes; corrections are new Transactions (matches WS-03A.6 CP-TXN-01).
- EV-T02 (Atomicity) → one Transaction mutates exactly one edge (matches CP-TXN-02, "one claim per transaction").
- EV-T09 (Finality) → once committed, a Transaction's standing doesn't change (matches WS-03A.6's immutability model).

No new mathematics is needed here — the WS-03A.6 Transaction model already *was* Event Mathematics, just not recognized as such until ZRM-004 existed to name it.

### 6.6 Outcome
*Legacy origin: WS-03A.7 — tracked, lifecycle-aware consequence of a Transaction.*

**Derivation.** An Outcome is a derived State (ZRM-003B ST-T01) that stands in the causal relationship established by EV-T05 to a Transaction (§6.5): `causes(transaction, State(x, t))`, restricted to the subset of cases satisfying WS-03A.7's Material Consequence Threshold (CD-OUT-02) — not every Transaction produces a tracked Outcome, consistent with the existing 0..N cardinality (CD-OUT-05).

**What's genuinely new here, not just recovered:** WS-03A.7 asserted Outcome ≠ Transaction ≠ Event as separate constitutional facts. This derivation shows *why* — a Transaction is an Event (§6.5), an Outcome is a State (ST-T01) causally downstream of that Event (EV-T05) — three different mathematical objects, not three arbitrary labels.

### 6.7 Campaign
*Legacy origin: WS-01 §5.6/§7 (locked as Tier 1 Core Domain Entity), later reclassified WS-02A §7 as Intelligence → Context → Campaign.*

**Derivation.** A Campaign is a bounded subgraph of `G`: a set of Events and Relationships sharing a common Attribute (ZRM-003B §4, "campaign membership") over a defined time window (ZRM-003B §8, Temporal Mathematics). Formally, `Campaign(c) = {e ∈ Event : attr(e, "campaign") = c, t(e) ∈ [t_start(c), t_end(c)]}`.

**Preserved distinction** (WS-03A.2 TR-008, Context/Identity Symmetry): Campaign-the-context (the subgraph above) and Campaign Identity (an Object with its own `i()` per ID-T01, used to reference the campaign as a thing) are different mathematical objects — the symmetry rule from WS-03A.2 is preserved exactly, now with a formal reason: one is a subgraph, the other is a vertex with an Identity relationship.

### 6.8 Intelligence
*Legacy origin: WS-03A.9 — evidence-based interpretation; not reality, not truth, not action.*

**Derivation.** Intelligence is a Semantic Projection in the strict sense of §3–4: `π : (Event, Evidence) → InterpretiveSpace`, where the target space is explicitly **not** `G` itself. This directly formalizes WS-03A.9 CP-INT-02/CP-INT-03 (Intelligence is not Intent, cannot trigger Intent): by PR-001 (No New Facts), a Projection cannot introduce a new vertex or edge into `G` — so Intelligence, being a Projection, is constitutionally incapable of modifying Reality, which is exactly the guarantee WS-03A.9 asserted operationally. Here it follows from the mathematics rather than being separately declared.

**Preserved content** (WS-03A.9 §11): the closed method taxonomy (Prediction, Classification, Inference, Anomaly Detection) and the epistemic_status field (definite/probable/possible/uncertain/speculative) are retained as the vocabulary of the projection's output space — not re-derived, since they describe the target space's structure rather than a mathematical claim about `G`.

# Part III — Materialization

## 7. Materialized Reality Graph
*Legacy origin: ZRM v1.1 Chapter 22 (Semantic Projection Engine), Chapter 25 (Graph Materialization).*

The Materialized Reality Graph is the specific projection `π : G_full → G_view` where `G_view` is a queryable, time-bounded slice of the full Reality Graph — consistent with ZRM v1.1's original "Facts → Meaning" pipeline, now stated in terms of ZRM-003B's formal Projection (PJ-D01) rather than the informal "Semantic Projection Engine" language.

## 8. Query Semantics

A query against `G_view` is a further Projection composed with §7's: `query = π_q ∘ π_view`, subject to the same PR-001/PR-002 rules — no query may introduce a fact not already in `G`, and every query result must be traceable back to its origin in `G`.
