## Preamble

RI-003 defines the Constitutional Verification Framework: the mathematical proof engine that independently reconstructs constitutional truth from the frozen constitutional corpus and proves — rather than merely checks — that the RI-001 Constitutional Compiler has produced the unique, constitutionally correct derivation.

RI-003 is not a validator. It is a theorem prover. The distinction is constitutionally significant. A validator asks whether compiler output looks correct. A theorem prover demonstrates that the published constitutional artifacts are the unique deterministic consequence of the frozen Constitution. RI-003 achieves this by independently reconstructing every constitutional artifact from first principles, without consuming any compiler-produced intermediate output, and comparing the two derivations using a formally specified algorithm whose correctness is machine-checkable.

## Part I — Foundations

### 1. Purpose

RI-003 exists to answer one constitutional question:

> Can an entirely independent implementation, using only the frozen constitutional corpus and RI specifications, reconstruct identical constitutional truth — without consuming any compiler-produced intermediate artifacts?

If yes, the compiler output is constitutionally certified. If no, the compiler contains a defect.

RI-003 provides this guarantee by:

1. Executing an independent reconstruction of the Active Constitutional View, Population Units, and Dependency Plan from sealed Phase A artifacts
2. Comparing its reconstruction against compiler output using a formally verified comparison algorithm
3. Producing immutable Proof Objects that permanently record every derivation step and its constitutional justification
4. Issuing a certification decision that is deterministic, reproducible, and auditable indefinitely

- The Proof Object format and lifecycle
- The Differential Verification Matrix (DVMatrix) for multi-implementation certification
- The Mutation and Soundness Framework

- The verification certification workflow

**RI-003 does not govern:**

- Compiler execution (RI-001)
- Population execution (RI-004B)

## Part II — Mathematical Foundations

### 5. Constitutional Uniqueness Theorem (CUT-001)

**CUT-001** is the foundational theorem of RI-003. It establishes that constitutional agreement between compiler and verifier is not a coincidence — it is a mathematical necessity when both are correct.

**Statement:**

```
Given:
  C  = frozen constitutional corpus (sealed under CFR-002)
  SR = Supersession Register (sealed, current version)
  S  = RI-002 CSM Schema (ratified, v1.0)
  R  = RI-000 Stable Ordering Contract + RFC 8785 Serialization Rules

Then:
  ∃! ACV such that ACV = f(C, SR, S, R)

  (there exists exactly one Active Constitutional View that is
   the correct derivation from these four sealed inputs)
```

**Proof Sketch:**

*(1) Supersession ordering is total.* SR-001 entry sequence indices are monotonically increasing integers starting at 1. This defines a total order on supersession application. Therefore, supersession produces a unique resolved corpus.

*(2) Deprecation filtering is deterministic.* The predicate `status = "DEPRECATED"` is a boolean on each CSM object, defined at translation time. No ambiguity exists. Therefore, the filtered corpus is unique.

*(3) The ontology graph is explicitly declared.* CW-001 (Closed World Principle) prohibits inference: absent concepts do not exist. Every node and every edge in the constitutional graph must be explicitly present in the CSM. No nodes or edges are generated by rule or implication. Therefore, the node set and edge set are uniquely determined.

*(4) Canonical serialization is a total function.* RFC 8785 defines a unique canonical form for every valid JSON object. The Stable Ordering Contract (RI-000 CP-007) defines a total order on all array elements. The NFC normalization requirement eliminates Unicode aliasing. Therefore, the canonical byte sequence is unique.

*(5) Composition of unique functions is unique.* Steps 1–4 are a composed sequence of deterministic functions. The composition is therefore deterministic. □

**Corollary (COL-001):** If RI-001 and RI-003 disagree on any artifact, exactly one contains a constitutional defect. The disagreement is sufficient evidence that a defect exists. No human judgment is required to know a defect is present — only to locate which implementation contains it.

### 6. Proof Obligations (PO-001 through PO-004)

Every module contract, every comparison algorithm, and every certification criterion in RI-003 must be traceable to one of these four proof obligations. They are the success criteria of the verification framework.

**PO-001 — Soundness:**

```
If RI-003 produces PASS, then the compiler output is constitutionally correct.

Formally:
  Verifier(C, SR, CompilerOutput) = PASS
  ⟹
  CompilerOutput = f(C, SR, S, R)
```

**PO-002 — Completeness:**

```
If the compiler output is constitutionally incorrect, RI-003 produces FAIL.

Formally:
  CompilerOutput ≠ f(C, SR, S, R)
  ⟹
  Verifier(C, SR, CompilerOutput) = FAIL
```

**PO-003 — Determinism:**

```
For identical constitutional inputs, RI-003 always produces identical output.

Formally:
  ∀ C, SR, X, i, j:
  Verifier_i(C, SR, X) = Verifier_j(C, SR, X)

  (pure function — no hidden state, no entropy sources, execution index irrelevant)
```

**PO-004 — Independence:**

```
The correctness of RI-003 does not depend on the correctness of RI-001.

Formally:
  Correct(RI-003) ⊬ Correct(RI-001)

  RI-003 must execute its full reconstruction pipeline (Stages V1–V4)
  and produce complete Proof Objects even if the /compiler/ directory
  does not exist and RI-001 has never been run.
  Only Stage V5 (comparison) consumes compiler artifacts.
```

### 7. Verification Independence Theorem (VT-001)

**VT-001 — Verification Independence:**

```
Verification SHALL be capable of executing successfully even if the
RI-001 compiler implementation does not exist.

Constitutional Implication:
  Deleting the compiler source tree from the repository SHALL NOT
  prevent RI-003 from completing Stages V1 through V4 and producing:
    - acv_v.json
    - population_units_v.json
    - dependency_plan_v.json
    - Proof Objects for all reconstruction stages

  Only Stage V5 requires compiler output for comparison.
  Stages V1–V4 are fully self-contained.
```

This is the strongest architectural constraint in RI-003. It eliminates hidden coupling between the verifier and the compiler at the implementation level.

### 8. RFC 8785 Semantic Fidelity (FV-001 and FV-002)

The byte comparison in Stage V5 is valid as a semantic check only if the following assumption holds.

**FV-001 — RFC 8785 Semantic Fidelity Assumption:**

```
Two constitutional graphs G1 and G2 are semantically equivalent
if and only if:

  SHA256(NFC(RFC8785_CANONICALIZE(G1)))
  ==
  SHA256(NFC(RFC8785_CANONICALIZE(G2)))

This is an explicit constitutional assumption, not a theorem.
```

**Known vulnerability conditions that would violate FV-001:**

| Condition | Risk | Mitigation |
|---|---|---|
| Array semantic ordering difference | Two valid orderings of same elements produce different canonical forms | Stable Ordering Contract (RI-000 CP-007) eliminates this |
| Unicode non-unique normalization | Two byte sequences represent the same character | NFC normalization required before canonicalization |
| Structural aliasing | Field absent vs. field present with default value represent same meaning | Null Prohibition (CSM-SER-001) eliminates this |

**FV-002 — Implementation Rule:**

```
Every implementation (both RI-001 and RI-003) SHALL apply transformations
in exactly this order before computing any hash:

  Step 1: NFC Unicode normalization of all string values
  Step 2: RFC 8785 JSON Canonicalization
  Step 3: SHA-256 digest computation

No intermediate transformations are permitted between these steps.
Deviation from this order is a Determinism Budget violation (0x00F6 in
RI-001 error namespace; VER-0x0060 in RI-003 error namespace).
```

### 9. Completeness Theorem (CT-001)

**CT-001** establishes that PO-002 (Completeness) holds at the architectural level, not merely the testing level.

**Statement:**

```
If RI-003 independently reconstructs artifact A_V from constitutional
sources, and compiler produces artifact A_C, and SE-003(A_V, A_C) = PASS,
then A_C is constitutionally correct.

Proof:
  (1) By CUT-001, ∃! constitutionally correct artifact A*.
  (2) By PO-004, RI-003 derives A_V without consuming A_C.
  (3) By INV-010 (Clean-Room Diversity), RI-003 shares no code with RI-001.
      If RI-003 is correct: A_V = A*.
  (4) If SE-003(A_V, A_C) = PASS, then A_V ≡ A_C (by SE-002).
  (5) Therefore A_C = A_V = A*.  □

Critical Dependency — Step (3):
  "If RI-003 is correct" is guaranteed by the DVMatrix:
  k=3 independent verifier implementations (language-diverse, per INV-010)
  all produce the same A_V. Under INV-010 (no shared code), the probability
  that all k have the same bug at the same location is negligibly small.
  For k=3 this constitutes a mathematical near-certainty.

Constitutional Implication:
  Mutation testing (MUT-001 through MUT-020 and VST-001 through VST-008)
  serves regression testing and attack surface documentation — not the
  completeness proof. CT-001 and the DVMatrix constitute the completeness proof.
```

## Part III — Constitutional Invariants and Governance Rules

### 10. Constitutional Invariants

**INV-010 — Clean-Room Diversity Mandate:**

```
The RI-001 Constitutional Compiler and the RI-003 Constitutional Verifier
SHALL NOT share:
  - any source code files
  - any utility libraries or modules
  - any data parsing frameworks
  - any JSON processing libraries
  - any serialization or hashing utilities
  - any runtime dependency (including transitive dependencies)

To eliminate systemic vulnerability in a shared runtime, the verifier
SHOULD be implemented in a different programming language than the compiler.

If RI-001 primary implementation is Go:
  RI-003 primary implementation SHALL be Rust or Python.

Language diversity requirements for the DVMatrix:
  At minimum 2 different languages across the 3 certified implementations.

Rationale:
  A bug in a shared code component produces a correlated failure:
  both compiler and verifier encounter the same error, agree on the
  wrong result, and produce a false PASS. INV-010 eliminates this class
  of correlated failure.
```

**INV-011 — Proof Independence:**

```
A constitutional proof SHALL NOT consume any artifact whose existence
depends upon the implementation being proven.

Formally:
  Correct(Proof) ⊬ Correct(RI-001)

Operational Implication:
  RI-003 Stages V1 through V4 SHALL complete and produce Proof Objects
  using only:
    - constitution_manifest.json (Phase A artifact)
    - SR-001 (Phase A artifact)
    - CSM corpus files (Phase B.2 artifacts)
    - RI-000, RI-001, RI-002 specifications

  Compiler-produced artifacts SHALL NOT be consumed until Stage V5.
```

**INV-012 — Comparison Algorithm Formal Verification Requirement:**

```
The constitutional comparison algorithms SE-003 and any future successors
SHALL be formally verified using a machine-checkable proof assistant.

Acceptable proof assistants: TLA+, Coq, Lean, Isabelle, or equivalent
with machine-checkable formal semantics.

The formal proof SHALL establish:
  (a) Termination: the algorithm terminates for all valid finite inputs
  (b) Soundness: PASS is returned iff inputs are semantically equivalent
  (c) Determinism: the algorithm is a pure function of its inputs

Proof artifacts are constitutional documents subject to CFR-002.
They SHALL be stored in:
  /outputs/proofs/comparison-engine/

and referenced in the Artifact Manifest.

Constitutional Implication:
  SE-003 is the one component of RI-003 that is formally proven correct,
  rather than trusted through implementation diversity. This removes the
  comparison engine from the "trust through DVMatrix" regime.
```

**INV-013 — Constitutional Monotonicity:**

```
For a sealed constitutional corpus, executing RI-003 multiple times
SHALL produce identical outputs.

Formally:
  ∀ execution_i, execution_j on identical sealed inputs:
  RI-003(C, SR, CSM)_i = RI-003(C, SR, CSM)_j

No mechanism may cause RI-003 to produce different results
across executions with identical inputs. Prohibited mechanisms include:

  - cache warming effects
  - execution history
  - optimization pass state
  - runtime heuristics
  - results from previous Proof Objects
  - wall-clock timestamp variation
  - any non-deterministic entropy source

Constitutional Effect:
  RI-003 is a mathematical function, not a process.
  INV-013 completes the determinism model for the verification layer.
  It complements VT-001, INV-010, INV-011, INV-012, and VR-003.
```

### 11. Verification Governance Rules

**VR-001 — Reconstruction Priority:**

```
RI-003 SHALL complete its independent reconstruction of all constitutional
artifacts (Stages V1 through V4) before consuming any compiler output.
Stage V5 (comparison) is the only stage that reads compiler artifacts.
```

**VR-002 — Proof Object Permanence:**

```
Proof Objects are immutable constitutional artifacts.
They SHALL be:
  - stored in /outputs/proofs/
  - referenced in the Artifact Manifest
  - never modified after production
  - never deleted
  - queryable by future auditors without re-executing the verifier

Proof Objects enable verification of certification decisions across
decades without requiring any re-execution.
```

**VR-003 — Zero Entropy:**

```
The verifier SHALL consume zero entropy beyond its declared constitutional
inputs. The same Determinism Budget as RI-001 applies to RI-003:

  Prohibited:  system clock, wall-clock timestamps, randomness,
               locale, timezone, filesystem iteration order,
               hash-map iteration order, thread scheduling,
               floating-point formatting, process ID, network state,
               environment variables, external API calls

The verifier is a pure function of its constitutional inputs.
```

**VR-004 — Ordered Comparison:**

```
The SE-003 comparison engine SHALL evaluate in fixed order:
  (1) Node sets (by FQCN)
  (2) Edge sets (by source FQCN, then predicate FQCN, then target FQCN)
  (3) Node attributes (by field name ascending, per FQCN order)
  (4) Edge labels (by edge identity)

Failure reports SHALL preserve this evaluation order.

Constitutional Implication:
  All DVMatrix implementations produce the same failure report structure
  for the same divergent input.
```

**VR-005 — External Integrity Commitment:**

```
Before any compilation run begins, the csm_corpus_hash from
csm-corpus.json SHALL be committed to an append-only external ledger
with an independently verifiable timestamp.

This commitment is a constitutional artifact and SHALL be referenced
in the Artifact Manifest.

Rationale:
  Without an external commitment, a privileged attacker could modify
  all CSM files, recompute all file-level hashes, recompute the
  Lexicographical Merkle Root, and update csm-corpus.json — all before
  either the compiler or verifier loads the corpus. Both would then
  reconstruct the same incorrect constitutional view and agree.
  The external commitment, timestamped before any run, makes this
  coordinated tampering detectable.

Minimum acceptable ledger:
  A publicly verifiable cryptographic timestamp (e.g., RFC 3161
  compliant timestamping authority, or equivalent immutable public log).
```

1. **Independent Reconstruction** (Stages V1–V4): RI-003 derives constitutional truth from sealed Phase A and Phase B artifacts, producing Proof Objects
2. **Comparison** (Stage V5): RI-003 compares its reconstruction against compiler output
3. **Certification** (Stage V5): A certification decision is issued based exclusively on the comparison result

This separation embodies PO-004 (Independence). The first component can run without the compiler. The second component produces a deterministic binary result. The third component cannot issue a PASS without the second having produced one.

## Part V — Five-Stage Verification Pipeline

### 14. Pipeline Overview

RI-003 executes exactly five constitutional stages. Each stage is a pure function with declared inputs, outputs, invariants, and failure modes. Stages communicate exclusively through immutable artifacts (per VR-001). No in-memory state passes between stages.

| Stage | Name | Input | Output |
|---|---|---|---|
| V1 | Independent Manifest Verification | Constitutional sources | verified_v.json + Proof P1 |
| V2 | Independent ACV Construction | verified_v.json | acv_v.json + Proof P2 |
| V3 | Independent Discovery | acv_v.json | population_units_v.json + Proof P3 |
| V4 | Independent Dependency Reconstruction | population_units_v.json | dependency_plan_v.json + Proof P4 |
| V5 | Comparison and Certification | Compiler artifacts + Verifier artifacts | validation_report.json + certificate |

### 15. Verification Ordering Convention

**Critical architectural note — FQCN-First Ordering (Resolution of Issue 2):**

During Stages V1–V4, the verifier operates exclusively with FQCNs. ZE-IDs do not exist at this stage — they are allocated by RI-001 Stage 5 (M-504), which has already run but whose output is not consumed until Stage V5.

Therefore:

```
RI-001 Stages 1-5: Sort using ZE-ID ascending → UUID ascending → Name ascending
RI-003 Stages V1-V4: Sort using FQCN ascending → Canonical Name ascending → Clause ID ascending
```

In Stage V5, module V-114 (FQCN-to-ZE-ID Mapping Verifier) explicitly verifies that the compiler's ZE-ID allocation is constitutionally correct: every entity sorted by ZE-ID ascending in the compiler output must correspond to the same entity sorted by FQCN ascending in the verifier output, per the deterministic allocation algorithm (RI-001 M-504).

### 16. Stage V1 — Independent Manifest Verification

**Purpose:** Independently verify that the constitutional sources are sealed, unmodified, and internally consistent before any reconstruction begins.

**Inputs:**
- `constitution_manifest.json` (Phase A artifact)
- Constitutional corpus documents (WS-01 through WS-05E, SR-001, etc.)
- `csm-corpus.json` (Phase B.2 artifact)
- External integrity commitment (VR-005)

**Output:** `verified_v.json` + Proof Object P1

**Constitutional Invariants:**
- Manifest integrity must match SHA-256 recomputation
- Every corpus document must pass per-document hash verification
- SR-001 sequence must be monotonically increasing
- SR-001 dependency graph must be acyclic
- External integrity commitment timestamp must precede this execution
- CSM Lexicographical Merkle Root must verify

**Failure Behavior:** Any failure halts the entire pipeline. No reconstruction proceeds on an unverified corpus.

### 17. Stage V2 — Independent ACV Construction

**Purpose:** Construct an Active Constitutional View from first principles, applying SR-001 supersessions in strict sequence order, removing deprecated concepts, building the ontology graph, and verifying it is acyclic.

**Inputs:** `verified_v.json`

**Output:** `acv_v.json` + Proof Object P2

**Constitutional Invariants:**
- Supersessions applied in SR-001 sequence order (monotonically increasing)
- No supersession applied before its `depends_on` entries are applied
- All concepts with `status: DEPRECATED` excluded from active graph
- Ontology graph is acyclic (Kahn's algorithm with FQCN-ascending priority queue)
- INV-001 through INV-009 verified against the constructed graph
- Canonical serialization via NFC → RFC 8785 → SHA-256

**Ordering Rule:** All collections sorted FQCN ascending → Canonical Name ascending (not ZE-ID ascending; see §15).

**Failure Behavior:** Ontology cycles halt pipeline with VER-0x0015. This is a constitutional defect requiring council amendment — the verifier MUST NOT attempt resolution.

### 18. Stage V3 — Independent Discovery

**Purpose:** Discover every Population Unit from the independently constructed ACV. Each CSM object in the active ontology produces exactly one Population Unit.

**Inputs:** `acv_v.json`

**Output:** `population_units_v.json` + Proof Object P3

**Constitutional Invariants:**
- Every admissible ACV node produces exactly one Population Unit
- No Population Unit is produced for deprecated, superseded, or excluded nodes
- No Population Units are invented beyond what the ACV contains (CW-001)
- Collection sorted: FQCN ascending → Canonical Name ascending
- No duplicate FQCNs in output

**Failure Behavior:** Zero Population Units discovered is a constitutional error (VER-0x0022). Discovery must be complete.

### 19. Stage V4 — Independent Dependency Reconstruction

**Purpose:** Build the constitutional dependency graph and produce a deterministic topological ordering of Population Units.

**Inputs:** `population_units_v.json`

**Output:** `dependency_plan_v.json` + Proof Object P4

**Constitutional Invariants:**
- Dependency edges derived exclusively from Population Unit `source_clause` references
- Topological sort uses Kahn's algorithm with FQCN-ascending priority queue
- Graph is acyclic (without INV-001 atomic batch justification)
- Atomic batches require justification artifact with constitutional clause citations
- SHA-256 tiebreak for units at the same dependency depth with identical FQCN prefix

**Failure Behavior:** Dependency cycles without INV-001 justification halt pipeline (VER-0x0030).

### 20. Stage V5 — Comparison and Certification

**Purpose:** Compare verifier reconstruction against compiler output using the formally specified comparison algorithm. Issue a certification decision. The only stage that consumes compiler-produced artifacts.

**Inputs:**
- `dependency_plan_v.json` (verifier output from V4)
- `acv_v.json` (verifier output from V2)
- `population_units_v.json` (verifier output from V3)
- `acv.json` (compiler output from RI-001 Stage 2)
- `population-units.json` (compiler output from RI-001 Stage 3)
- `dependency-plan.json` (compiler output from RI-001 Stage 4)
- `population-plan.json` (compiler output from RI-001 Stage 5)
- Proof Objects P1–P4

**Output:**
- `validation_report.json`
- `registry_certificate.json` (AUTHORIZED or UNAUTHORIZED)
- Updated Artifact Manifest

**Comparison sequence:**
1. V-111: Hash comparison (byte-level, per FV-002 ordering)
2. V-112: Semantic comparison (SE-003 algorithm)
3. V-113: Difference classification and reporting
4. V-114: FQCN-to-ZE-ID mapping verification
5. V-115: Certification generation

**Certification rule:** AUTHORIZED if and only if all comparisons return PASS and all CLASS A, B, C, E, F findings have count zero. CLASS D and CLASS G findings produce warnings but do not block certification if they represent deterministic serialization differences that the DVMatrix confirms are consistent.

## Part VII — Semantic Model

### 26. Constitutional Graph Definition (SE-001)

```
Definition SE-001 — Constitutional Graph:

A Constitutional Graph G is a labeled directed multigraph:
  G = (N, E, λ_N, λ_E)

Where:
  N  = finite set of nodes
       (one per active CSM object, identified by FQCN)

  E  ⊆ N × N
       = finite set of directed edges
       (one per Relationship CSM object)

  λ_N : N → Attributes
       = node labeling function
       (maps each node to its complete attribute set, as flat key-value pairs)

  λ_E : E → PredicateFQCN
       = edge labeling function
       (maps each directed edge to the FQCN of its Predicate)

Note on computational complexity:
  FQCNs provide canonical node identity by construction (RI-002 §7).
  Constitutional graph equivalence is therefore NOT general graph isomorphism
  (GI-complete). It is O(|N| + |E|) key-based equality — we compare nodes
  directly by their FQCN primary key, not by searching for a permutation.
```

### 27. Semantic Equivalence Definition (SE-002)

```
Definition SE-002 — Constitutional Semantic Equivalence:

Two constitutional graphs G1 = (N1, E1, λ_N1, λ_E1) and
                          G2 = (N2, E2, λ_N2, λ_E2)
are semantically equivalent (G1 ≡ G2) iff:

  (1) N1 = N2
      (Same node set, identified by FQCN.
       Missing nodes in G2: constitutional omission.
       Extra nodes in G2: constitutional invention — Ghost-Clause Exploit.)

  (2) E1 = E2
      (Same edge set, identified by (source_fqcn, predicate_fqcn, target_fqcn).
       Missing edges: omitted relationships.
       Extra edges: invented relationships.)

  (3) ∀n ∈ N1: λ_N1(n) = λ_N2(n)
      (Same attribute values for every node.
       Attribute comparison is string equality after NFC normalization.
       Integer comparison is numeric equality.)

  (4) ∀e ∈ E1: λ_E1(e) = λ_E2(e)
      (Same predicate FQCN for every edge.)

Constitutional graph equivalence is a stronger condition than graph
isomorphism because it additionally requires identical node identities
(FQCNs must match, not merely exist in correspondence).
```

### 28. Semantic Comparison Algorithm (SE-003)

This is the reference algorithm for module V-114. Its formal correctness is proven per INV-012.

```
FUNCTION SE-003(G_V: ConstitutionalGraph, G_C: ConstitutionalGraph)
    → ComparisonResult:

  findings ← EMPTY_LIST

  # ── Step 1: Node Set Comparison ─────────────────────────────────────
  nodes_V ← SET(G_V.N)   # keyed by FQCN
  nodes_C ← SET(G_C.N)   # keyed by FQCN

  missing_in_C ← nodes_V - nodes_C
  extra_in_C   ← nodes_C - nodes_V

  FOR fqcn IN SORT(missing_in_C, BY_FQCN_ASCENDING):
    findings.APPEND(Finding(
      class         = CLASS_B,
      severity      = CRITICAL,
      type          = NODE_MISSING_FROM_COMPILER,
      entity_fqcn   = fqcn,
      verifier_value = "present",
      compiler_value = "absent",
      citation      = "RI-002 §4.3 CW-001 + SE-002 condition (1)"
    ))

  FOR fqcn IN SORT(extra_in_C, BY_FQCN_ASCENDING):
    findings.APPEND(Finding(
      class          = CLASS_B,
      severity       = CRITICAL,
      type           = NODE_INVENTED_BY_COMPILER,
      entity_fqcn    = fqcn,
      verifier_value = "absent",
      compiler_value = "present",
      citation       = "RI-002 §4.3 CW-001 + SE-002 condition (1)"
    ))

  # ── Step 2: Edge Set Comparison ──────────────────────────────────────
  edges_V ← SET(G_V.E)   # keyed by (source_fqcn, predicate_fqcn, target_fqcn)
  edges_C ← SET(G_C.E)

  missing_edges ← edges_V - edges_C
  extra_edges   ← edges_C - edges_V

  FOR edge IN SORT(missing_edges, BY_SOURCE_FQCN_THEN_PREDICATE):
    findings.APPEND(Finding(
      class   = CLASS_B,
      severity = CRITICAL,
      type    = EDGE_MISSING_FROM_COMPILER,
      edge    = edge,
      citation = "SE-002 condition (2)"
    ))

  FOR edge IN SORT(extra_edges, BY_SOURCE_FQCN_THEN_PREDICATE):
    findings.APPEND(Finding(
      class   = CLASS_B,
      severity = CRITICAL,
      type    = EDGE_INVENTED_BY_COMPILER,
      edge    = edge,
      citation = "SE-002 condition (2)"
    ))

  # ── Step 3: Node Attribute Comparison ────────────────────────────────
  common_nodes ← nodes_V ∩ nodes_C

  FOR fqcn IN SORT(common_nodes, BY_FQCN_ASCENDING):
    attrs_V ← G_V.λ_N(fqcn)
    attrs_C ← G_C.λ_N(fqcn)

    all_keys ← SET(attrs_V.KEYS()) ∪ SET(attrs_C.KEYS())

    FOR key IN SORT(all_keys, ALPHABETICALLY):
      v_val ← attrs_V.GET(key, ABSENT)
      c_val ← attrs_C.GET(key, ABSENT)

      IF NFC_NORMALIZE(STRINGIFY(v_val)) ≠ NFC_NORMALIZE(STRINGIFY(c_val)):
        findings.APPEND(Finding(
          class          = CLASS_B,
          severity       = CRITICAL,
          type           = ATTRIBUTE_MISMATCH,
          entity_fqcn    = fqcn,
          attribute_name = key,
          verifier_value = v_val,
          compiler_value = c_val,
          citation       = "SE-002 condition (3)"
        ))

  # ── Step 4: Edge Label Comparison ────────────────────────────────────
  common_edges ← edges_V ∩ edges_C

  FOR edge IN SORT(common_edges, BY_SOURCE_FQCN_THEN_PREDICATE):
    label_V ← G_V.λ_E(edge)
    label_C ← G_C.λ_E(edge)

    IF label_V ≠ label_C:
      findings.APPEND(Finding(
        class          = CLASS_B,
        severity       = CRITICAL,
        type           = EDGE_LABEL_MISMATCH,
        edge           = edge,
        verifier_value = label_V,
        compiler_value = label_C,
        citation       = "SE-002 condition (4)"
      ))

  # ── Result ────────────────────────────────────────────────────────────
  IF findings IS EMPTY:
    RETURN ComparisonResult(status = PASS, findings = [])
  ELSE:
    RETURN ComparisonResult(status = FAIL, findings = findings)

# ── Complexity Analysis ───────────────────────────────────────────────
#
# Step 1: O(|N|)  — set difference on FQCN-keyed sets
# Step 2: O(|E|)  — set difference on edge-keyed sets
# Step 3: O(|N| × avg_attributes) = O(|N|) for bounded attribute count
# Step 4: O(|E|)
#
# Total: O(|N| + |E|) — linear in constitutional graph size
#
# Note: This is NOT general graph isomorphism (NP).
# FQCN primary keys reduce it to key-based equality, which is linear.

END FUNCTION
```

## Part X — Mutation and Soundness Framework

### 36. Purpose

The mutation framework serves two purposes:

1. **Compiler Mutation Tests (MUT series):** Verify that RI-003 detects known classes of compiler defects
2. **Verifier Soundness Tests (VST series):** Verify that RI-003 cannot be tricked into producing a false PASS

Both suites require 100% detection rate. Any mutation that passes undetected is a CRITICAL defect in the verification framework.

All mutation cases are seeded and deterministic. Seeds are committed to the repository and never regenerated randomly.

### 41. Hash Mismatch Resolution Protocol

When DVMatrix divergence or Stage V5 hash mismatch is detected:

```
Step 1  FREEZE     Halt all certification runs immediately
Step 2  PRESERVE   Archive all intermediate artifacts from all implementations
Step 3  DUMP       Each implementation outputs all Proof Objects in full
Step 4  ISOLATE    Diff Proof Objects stage-by-stage to identify first divergence
Step 5  CLASSIFY   Determine: Verifier Bug | Compiler Bug | Specification Ambiguity
Step 6  COUNCIL    Architecture Council reviews root cause
Step 7  LOG        Resolution documented in resolution_log appended to Artifact Manifest
Step 8  REPAIR     Fix defect in identified implementation
Step 9  RERUN      All implementations re-run; DVMatrix re-validates
Step 10 FREEZE     New baseline hashes frozen only after unanimous DVMatrix CONVERGE
```

No implementation is considered certified until all DVMatrix implementations produce identical hashes against the same constitutional input.

## Appendix C — Proof Object Reference

**Proof Object file naming convention:**

```
proof-v{stage}-{run_id}.json
```

Where `run_id` is derived deterministically from the sealed Manifest's `sealed_at_unix_ms` and the verifier's language identifier. No wall-clock timestamps in file names.

**Proof chain integrity:**

Each Proof Object references the prior one via `prior_proof_id`:

```
P1 (manifest verification)
  → prior_proof_id: null
P2 (ACV construction)
  → prior_proof_id: PROOF-V1-{run_id}
P3 (discovery)
  → prior_proof_id: PROOF-V2-{run_id}
P4 (dependency plan)
  → prior_proof_id: PROOF-V3-{run_id}
```

This forms an immutable chain. Tampering with any Proof Object breaks the chain integrity of every subsequent object.
