## Preamble

RI-004 defines the Registry Population Engine: the constitutional materializer that transforms a proven Population Plan into an immutable, Merkleized, cryptographically certified Master Registry.

RI-004 is not a registry builder. It is a constitutional materializer. The distinction is architecturally fundamental. A registry builder makes execution decisions. A constitutional materializer makes none — every value written to the registry already exists within the proven Population Plan. RI-004 reads, verifies, writes, reads back, Merkleizes, invokes independent certification, and commits. At no point does it derive, infer, optimize, reorder, reinterpret, repair, or synthesize constitutional information.

The Population Plan is already a proven theorem (RI-003). RI-004 therefore executes a deterministic state machine against a pre-decided outcome. The registry that emerges is not the source of constitutional truth — it is a deterministic projection of the Population Plan, which itself is a deterministic consequence of the frozen Constitution. The registry may always be destroyed and rebuilt from the Population Plan without loss of constitutional information.

RI-004 terminates when the registry reaches the CERTIFIED state. Registry publication, packaging, signing, distribution, and activation are the responsibility of RI-005.

## Part I — Foundations

### 1. Purpose

RI-004 receives a verified, signed Population Plan from RI-001 and:

1. Pre-verifies the plan against the sealed constitutional manifest (RI-004A)
2. Materializes every Population Unit into the registry in dependency order, with no constitutional decisions (RI-004B)
3. Constructs a Merkleized registry structure with per-entity and per-cluster integrity hashes
4. Invokes RI-003 independent verification against the materialized registry
5. Receives the registry certificate from RI-003 and reaches CERTIFIED state

RI-004 produces exactly one constitutional output: a CERTIFIED registry. Everything required to produce that output is already contained in the Population Plan. RI-004 adds nothing.

### 2. Scope

**RI-004 governs:**

- Pre-execution plan verification (RI-004A)
- Population execution: batch sequencing, entity writing, relationship writing (RI-004B)
- Block-level read-back verification after each batch
- Merkle tree construction for registry entities and clusters
- Rollback on any failure to a clean pre-batch state
- RI-003 invocation and certificate receipt
- Registry lifecycle states from GENERATING through CERTIFIED
- Provenance segregation for all materialized objects
- Registry chain integrity (each registry references its predecessor)

**RI-004 does not govern:**

- Population Plan derivation (RI-001)
- Independent verification or certification logic (RI-003)
- Registry publication, packaging, or distribution (RI-005)
- Runtime SDK behavior (RI-006)
- Registry interface adapters (RI-006)

## Part II — Constitutional Invariants

### 7. Locked Invariants

**INV-015 — Provenance Segregation:**

```
Provenance metadata (source Population Plan, compiler version, batch ID,
verification certificate, materialization timestamp logical, executor version)
SHALL be stored in a separate provenance record for each registry entity.

Provenance records SHALL NOT be merged into entity payload objects.
Entity payloads contain constitutional data only.

Structure:
  registry/
    entities/
      {ZE-ID}.json         ← constitutional payload + integrity hash
    provenance/
      {ZE-ID}.prov.json    ← provenance record (separate, immutable)

Rationale:
  Constitutional data and execution metadata are different constitutional
  concerns. Merging them prevents independent verification of entity
  content without contaminating the constitutional hash.
```

**INV-017 — Block-Level Read-Back Verification:**

```
After writing every committed batch to the registry, RI-004B SHALL:

  (1) Read back every entity and relationship written in that batch
  (2) Compute SHA256(RFC8785(payload)) of each read-back object
  (3) Compare against the hash declared in the Population Plan

  If any read-back hash mismatches the plan:
    HALT with MAT-0x0050 (READ_BACK_MISMATCH)
    Rollback entire batch
    Preserve failed-batch forensic artifacts

Rationale:
  Storage layer bugs (bit-flip, compression artifact, encoding error)
  can produce silent write corruption. Read-back verification catches
  these before the entity is committed to the registry state.
  This extends the constitutional guarantee from the plan to the
  materialized registry.
```

**INV-018 — Registry Projection Rule:**

```
The Master Registry SHALL be treated as a deterministic projection
of the Population Plan.

The Population Plan remains the canonical constitutional source.

The Registry may be destroyed and rebuilt from the Population Plan
without constitutional information loss.

The Registry is an immutable value object. It is never modified.
Constitutional evolution produces new registry versions; it does
not mutate existing ones.
```

**INV-019 — Dumb Executor Rule:**

```
RI-004B SHALL perform no constitutional reasoning.

Every value written to the registry SHALL already exist within the
signed, verified Population Plan:
  - ZE-IDs: already allocated in Population Plan (M-504)
  - UUIDs: already generated deterministically (M-503)
  - Predicates: already validated against Predicate Registry
  - Patterns: already validated against Pattern Registry
  - Lifecycle tracks: already verified against INV-005
  - Authority references: already validated against Trust Registry
  - Dependencies: already resolved in Population Plan batch sequence

If any value is absent from the Population Plan, RI-004B halts.
It never defaults, infers, or substitutes.

Enforcement:
  Every write operation MUST cite the Population Plan field path
  from which the written value was read. This citation is recorded
  in the provenance record (INV-015).
```

**INV-020 — Atomic Reality:**

```
No runtime SHALL ever observe a partially populated registry.

Registry reality SHALL transition atomically from Registry(n)
to Registry(n+1) using a single atomic pointer swap.

Implementation:
  registry/
    active/   →  symlink or pointer to current certified version
    v1/       →  immutable, sealed
    v2/       →  immutable, sealed (if current)

  Activation: rename(active → v2) is one atomic OS operation.

Intermediate states are constitutionally forbidden.
A registry that is GENERATING or VERIFYING SHALL NEVER be
reachable by runtime consumers.
```

**INV-021 — Activation Integrity:**

```
No registry SHALL enter the CERTIFIED state unless the following
form a cryptographically consistent chain:

  (1) Registry Merkle Root
  (2) Population Plan hash (the plan from which it was materialized)
  (3) Registry Certificate (from RI-003, binding all three hashes)
  (4) Artifact Manifest (binding all pipeline artifacts)

Activation Verification (performed by RI-005 before publication):
  SHA256(merkle_root + plan_hash + certificate_hash + manifest_hash)
  = activation_chain_hash

  This hash is recorded in the Activation Manifest.
  Runtime SDKs verify the Activation Manifest on load.

Violation: any hash in the chain failing verification SHALL
halt activation with MAT-0x0070 (ACTIVATION_CHAIN_VIOLATION).
```

**INV-022 — Registry Chain:**

```
Every certified registry SHALL reference its immediately
preceding certified registry.

Structure in registry manifest:
  "previous_registry": {
    "registry_version":  "1.0",
    "merkle_root":       {"algorithm": "sha256", "value": "..."},
    "certificate_id":    "UUIDv7",
    "certificate_hash":  {"algorithm": "sha256", "value": "..."}
  }

Genesis Case:
  The first registry (v1.0) has no predecessor.
  It SHALL declare:
  "previous_registry": null

  This is the only valid use of null in the registry manifest.
  It is the constitutional genesis anchor.

Chain Validation:
  Any consumer or auditor MAY traverse the chain backward
  to the genesis anchor to verify constitutional lineage.
  A broken chain SHALL be treated as a constitutional integrity failure.
```

**INV-023 — Registry Representation Independence:**

```
Runtime SDKs SHALL consume a constitutional Registry Interface.
They SHALL NOT depend upon any specific registry storage representation.

The Registry Interface is a constitutional contract.
The registry storage representation (JSON files, OCI image, database,
remote API) is an implementation detail governed by RI-005 adapters.

Consequence:
  Changing storage representation (e.g., from JSON files to OCI
  content-addressed storage) SHALL require no SDK changes.

  Only the storage adapter is replaced. The Registry Interface
  and all SDK behavior remain identical.

Formal statement:
  SDK behavior = f(RegistryInterface)
  NOT
  SDK behavior = f(registry.json)
```

### 8. Population Executor Governance Rules

**MR-E001 — Plan-First Principle:**

```
The Population Plan is the sole authority for all materialization decisions.
No value may be written to the registry unless it appears in the plan.
No ordering may be applied beyond the proven batch sequence.
```

**MR-E002 — Batch Atomicity:**

```
Batches are the unit of atomic commitment.
Either all entities and relationships in a batch are committed,
or none are. Partial batch states do not exist.
```

**MR-E003 — Rollback Completeness:**

```
On any batch failure, rollback SHALL restore the registry to its
exact pre-batch state. Rollback is defined as:

  registry_state_after_rollback = registry_state_before_batch_started

No partial entity, no partial relationship, no partial index update
may remain after rollback.
```

**MR-E004 — Forensic Preservation:**

```
Failed batches SHALL be preserved in /outputs/failed-batches/
before rollback executes. These artifacts are constitutional
evidence and SHALL NOT be deleted.

Forensic artifact set:
  failed-batch-{batch_id}.json   ← batch contents
  failure-report-{batch_id}.json ← error details + stack + MAT code
  registry-state-{timestamp_logical}.hash ← pre-failure state hash
```

## Part IV — RI-004B Population Executor

### 12. Purpose

RI-004B consumes the verified Population Plan and materializes every Population Unit into the registry using the following five execution phases. It makes zero constitutional decisions. Every value written was already present in the signed plan.

### 13. Execution Phases

```
Phase 0 — Final Plan Verification
  Verify Pre-Execution Confirmation Report present and hash-valid
  Verify Population Plan hash unchanged since RI-004A
  Verify previous registry hash (INV-022)
  Initialize empty registry working directory
  Record materialization start in Artifact Manifest

Phase 1 — Batch-by-Batch Entity Materialization
  For each batch in proven sequence order:
    Write all entities in batch
    Write all relationships in batch
    Execute block-level read-back verification (INV-017)
    If read-back PASS: commit batch
    If read-back FAIL: rollback + preserve forensics + HALT

Phase 2 — Merkle Tree Construction
  For each entity: compute entity_hash = SHA256(RFC8785(entity_payload))
  For each cluster: compute cluster_hash = SHA256(sorted entity_hashes)
  Compute registry_merkle_root = SHA256(sorted cluster_hashes)
  Build merkle_index.json mapping every ZE-ID to its hash chain

Phase 3 — RI-003 Invocation
  Pass materialized registry to RI-003 independent verification pipeline
  RI-003 executes Stages V1–V5 against materialized registry
  RI-004B waits for validation_report.json and registry_certificate.json

Phase 4 — Certificate Receipt and Registry Sealing
  Receive registry_certificate.json from RI-003
  If certificate status = AUTHORIZED:
    Seal registry (mark CERTIFIED)
    Record certificate in Artifact Manifest
    Build registry_manifest.json
    Transition to CERTIFIED state
  If certificate status = UNAUTHORIZED:
    Quarantine registry
    Preserve all forensic artifacts
    HALT with MAT-0x0060 (CERTIFICATION_FAILED)
```
