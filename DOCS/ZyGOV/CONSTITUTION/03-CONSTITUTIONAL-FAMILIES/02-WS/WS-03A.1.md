## 1. Purpose
This document defines the constitutional taxonomy for CL-11 Event.

The Event Cluster establishes the canonical classification system for all observable occurrences within the Zyppi Reality Model (ZRM).

Events represent facts about reality.

**Events are distinct from:**
- Outcomes (results of events)
- Intelligence (interpretations of events)
- Transactions (execution mechanisms)
- Identities
- Referents
- Actors

An Event records that something happened.

An Event does not explain what that occurrence means.

## 2. Constitutional Principle
### CP-E01 — Event Before Intelligence
Reality exists before interpretation.

An Event SHALL be treated as a first-order reality primitive.

Intelligence SHALL be treated as a derived layer constructed from Events.

**Therefore:**
```
Reality
 └── Event
       └── Interaction
```
**NOT:**
```
Reality
 └── Intelligence
       └── Event
```

## 3. Event Root Taxonomy
```
CL-11 Event
│
├── CL-11.1 Interaction
├── CL-11.2 Observation
├── CL-11.3 Assertion
├── CL-11.4 Mutation
├── CL-11.5 Verification Event
└── CL-11.6 System Event
```
Each Event SHALL belong to exactly one primary branch.

Multiple classifications SHALL NOT be assigned.

## 4. Event Branch Definitions
### CL-11.1 Interaction
**Definition:**
> An Event representing engagement between an Actor and another element of Reality.

**Examples:**
- QR Scan
- NFC Tap
- URL Click
- Form Submission
- Authentication Request
- Registration Request
- API Trigger

Interaction records engagement.

Interaction does not imply success.

### CL-11.2 Observation
**Definition:**
> An Event representing the detection or recording of a state without modifying that state.

**Examples:**
- Sensor Reading
- Presence Detection
- Location Capture
- Inventory Count
- Temperature Reading
- Camera Detection

Observation records what was detected.

Observation does not create change.

### CL-11.3 Assertion
**Definition:**
> An Event representing a claim, declaration, or statement introduced into Reality.

**Examples:**
- Ownership Claim
- Identity Claim
- Certification Submission
- Sustainability Declaration
- Product Origin Declaration

Assertion introduces information.

Assertion does not prove information.

#### Assertion Subtypes
```
Assertion
│
├── Claim
├── Declaration
├── Certification Submission
└── Consent Event
```
##### Claim
> Actor asserts ownership, entitlement, status, or relationship.

**Examples:**
- Ownership Claim
- Warranty Claim
- Membership Claim

##### Declaration
> Formal statement introduced into Reality.

**Examples:**
- Carbon Footprint Declaration
- Material Composition Declaration
- Product Origin Declaration

##### Certification Submission
> Submission of evidence for future evaluation.

**Examples:**
- ISO Certificate Submission
- ESPR Documentation Submission
- GS1 Compliance Submission

##### Consent Event
> Granting, modifying, or revoking consent.

**Examples:**
- Marketing Consent
- Privacy Consent
- Data Sharing Consent
- Consent Withdrawal

### CL-11.4 Mutation
**Definition:**
> An Event that changes state.

**Examples:**
- Identity Commissioned
- Ownership Transferred
- Asset Updated
- Record Modified
- Product Recalled
- Identity Archived

Mutation creates change.

Mutation records transition.

### CL-11.5 Verification Event
**Definition:**
> An Event evaluating or confirming an Assertion, Identity, Referent, or State.

**Examples:**
- Authenticity Check
- Certification Verification
- Identity Verification
- DPP Validation
- Compliance Validation

Verification Event evaluates.

Verification Event does not create the original claim.

### CL-11.6 System Event
**Definition:**
> An Event generated by infrastructure, automation, or machine processes.

**Examples:**
- Webhook Received
- API Request
- Synchronization Event
- Projection Rebuild
- AI Invocation

System Events describe system activity.

They do not represent direct human interactions.

#### System Event Subtypes
```
System Event
│
├── Routing Event
├── Resolution Event
├── Webhook Event
├── Ingestion Event
├── Replay Event
├── Projection Event
└── Integration Event
```
##### Routing Event
Execution of routing logic.

**Examples:**
- Intent Routing
- Destination Selection
- Context Routing

##### Resolution Event
Resolution of a Touchpoint into an Identity, Referent, or Intent.

**Examples:**
- QR Resolution
- Digital Link Resolution
- NFC Resolution

##### Webhook Event
Outbound or inbound webhook processing.

##### Ingestion Event
Acceptance of data into the event store.

##### Replay Event
Reconstruction of state from historical facts.

##### Projection Event
Rebuilding of materialized views.

##### Integration Event
Synchronization with external systems.

**Examples:**
- ERP Sync
- CRM Sync
- GS1 Sync
- DPP Registry Sync

## 5. Interaction Taxonomy
### CL-11.1 Interaction Subtypes
```
Interaction
│
├── Discovery
├── Access
├── Submission
├── Authentication
├── Registration
├── Verification Request
└── Trigger
```

#### Discovery
**Purpose:**

Discover a resource.

**Examples:**
- QR Scan
- NFC Tap
- Link Click

#### Access
**Purpose:**

Open or retrieve content.

**Examples:**
- View Product Passport
- Open Landing Page
- Access Documentation

#### Submission
**Purpose:**

Provide information.

**Examples:**
- Form Submission
- Feedback Submission
- Warranty Submission

#### Authentication
**Purpose:**

Prove identity.

**Examples:**
- Login
- SSO Authentication
- Identity Validation Request

#### Registration
**Purpose:**

Create or establish a relationship.

**Examples:**
- Product Registration
- Warranty Registration
- Loyalty Registration

#### Verification Request
**Purpose:**

Request evaluation of authenticity or validity.

**Examples:**
- Authenticity Check
- Certification Check
- Ownership Verification

#### Trigger
**Purpose:**

Initiate downstream processing.

**Examples:**
- API Trigger
- Workflow Trigger
- Automation Trigger

## 6. Event vs Transaction
Transaction is a constitutional primitive.

Transaction belongs to CL-09.

Transaction SHALL NOT be classified as an Interaction subtype.

### Correct flow:
```
Interaction Event
      ↓
Intent
      ↓
Intent Contract
      ↓
System
      ↓
Transaction
      ↓
Outcome
```
**Example:**
```
QR Scan
     ↓
Purchase Intent
     ↓
Checkout Contract
     ↓
Commerce System
     ↓
Purchase Transaction
     ↓
Purchase Completed
```
A Transaction may be initiated by an Event.

A Transaction is not an Event subtype.

## 7. Event vs Outcome
Events and Outcomes are separate constitutional concepts.

**Examples:**

Event  | Outcome
---|---
QR Scan | Content Viewed
Registration Submission | Registration Completed
Authenticity Verification Request | Product Verified
Purchase Transaction | Purchase Completed
Recall Initiated | Recall Active

> `Event = occurrence.`
>
> `Outcome = result.`

## 8. Cardinality Rules
### CR-E01
Every Event SHALL belong to exactly one Event branch.

### CR-E02
Every Event SHALL possess temporal metadata.

### CR-E03
Events MAY reference:
- Actors
- Identities
- Referents
- Systems
- Transactions
- Outcomes

### CR-E04
Events MAY generate Outcomes.

### CR-E05
Outcomes SHALL NOT generate Reality Events.

**Outcomes MAY trigger System Events exclusively for:**
- Recording
- Projection
- Synchronization
- Integration

Such System Events SHALL NOT re-enter the constitutional reality flow.

### CR-E06
An Event SHALL remain immutable after recording.
Corrections SHALL be represented by new Events.

## 10. Event and Intelligence Separation
### Event records:
> "What happened?"

**Examples:**
- Scan occurred
- Verification occurred
- Submission occurred
### Intelligence answers:
- Why it happened
- What it means
- What patterns exist
- What predictions emerge

**Therefore:**
```
CL-11 Event
        ↓
CL-16 Intelligence
```
Intelligence SHALL consume Events.

Events SHALL NOT depend upon Intelligence.

Event is a constitutional reality primitive.

## 12. Ratification
### Upon ratification:
CL-11 SHALL be officially renamed from Intelligence to Event.

Event SHALL become a constitutional taxonomy cluster.

Intelligence SHALL be relocated to CL-16.

All future Event entities SHALL use the prefix:

`ZE-EVT-XXX`

Intelligence entities SHALL retain the Intelligence namespace under CL-16.
