## Purpose
`WS-03` validates the complete taxonomic structure of the Zyppi Reality Graph before registry population begins.

### This workstream defines:
- parent-child inheritance rules
- cluster ownership rules
- dual-role entity governance
- cross-cluster relationship governance
- constitutional flow validation
- compliance hierarchy requirements
- registry readiness criteria

WS-03 does not create entities.

WS-03 defines the structural rules that every future entity must obey.

## SECTION 01
## Taxonomy Principles
The Zyppi Reality Graph uses a strict inheritance model.

**Taxonomy answers:**
> What is this thing?

**Relationships answer:**
> How does this thing connect to other things?

Taxonomy and relationships must never be confused.

**Example:**

**Correct:**
```
Dynamic QR Code
    IS-A
Touchpoint
```
**Correct:**
```
Touchpoint
    HOSTED_ON
Surface
```
**Incorrect:**
```
Dynamic QR Code
    IS-A
Product Package
```
A package hosts a QR code.

A QR code is not a package.

## SECTION 02
## Taxonomy Rules

### TR-001

`One Entity = One Parent`

Every entity must have exactly one primary parent.
No entity may inherit from multiple parents.

### TR-002

`One Entity = One Primary Cluster`

Every entity belongs to exactly one primary cluster.

Cross-cluster references are permitted.

Cross-cluster ownership is prohibited.

### TR-003

`Inheritance Flows Downward`

Children inherit attributes from parents.

Parents never inherit from children.

### TR-004

`No Circular Taxonomy`

Circular inheritance is prohibited.

**Example:**

`A → B → C → A`

**Invalid**.

### TR-005

`Dual-Role Single Home Rule`

An entity may perform multiple functions.

It must still have one canonical home.

**Examples:**
- Digital Product Passport
- Digital Twin
- Product Identity
- GS1 Digital Link
- Intent Contract

**Each receives:**
- one primary cluster
- one primary parent

Additional appearances are references only.

### TR-006

`Strategic Categories Are Leaf Nodes`

Strategic Categories never own entities.

Strategic Categories never drive inheritance.

CL-12 entities exist only as strategic framing concepts.

All CL-12 entities are leaf nodes.

Every CL-12 entity must reference its primary conceptual home elsewhere in the ontology.

**Example:**
```
Product Memory
   ↳ references Identity

Physical Internet
   ↳ references Identity + Referent
```

### TR-007

`Strategic Programs Never Drive Taxonomy`

- Core
- Helios
- Atlas
- Mercury
remain metadata only.

**Programs never determine:**
- parent
- cluster
- inheritance

### TR-008

`Context / Identity Symmetry Rule`

Some concepts exist both as:
- contextual state
- resolvable identity
These must be modeled separately.

**Examples:**
```
Campaign
    Context Entity

Campaign Identity
    Identity Entity
```
**Examples include:**
- Campaign
- Device
- Location
- Audience
Context entities belong to Intelligence.

Identity entities belong to Identity.

### TR-009

`Interaction Is First-Class`

Interaction is a constitutional entity.

Interaction is not a Tier-0 primitive.

**Interaction belongs to:**

CL-11 Intelligence
Tier 1
Parent = Event

**Purpose:**

Interaction represents the discrete moment of contact between a Touchpoint and an Identity.

Examples:
- QR scan
- NFC tap
- Digital Link resolution
- AI agent invocation
- API access event

### TR-010

`Reality Remains Constitutional`

Reality remains a constitutional concept.
Reality is not an entity.
Reality is not a cluster.

**Reality represents:**
the complete state of all entities and relationships within the Zyppi Reality Graph at a specific moment in time.

Reality is therefore a derived graph state.
Not a registry node.

### TR-011

`Parent Selection Tie-Break Rule`

When multiple valid parents exist:
- The primary parent must be the parent that most specifically describes the entity's function.
- Secondary associations belong in relationship mappings.

**Examples:**
```
Trust Score
    Parent = Trust

Attribution Window
    Parent = Attribution

Audience Segment
    Parent = Segment
```

### TR-012

`Dual-Role Reference Mechanism`

**Dual-role entities contain:**
```
secondary_clusters[]
```
metadata.

**Example:**
#### Digital Product Passport

**Primary Cluster:**
- CL-04 Identity

**Secondary Clusters:**
- CL-12 Strategic Categories
- CL-14 Compliance

**Cross-cluster references are also represented using:**
- REFERENCED_BY

relationships.

### TR-013

`Surface Is Contextual`

Surface is not a sequential step.
Surface provides context for Touchpoints.

**Constitutional flow therefore becomes:**
```
Actor
    →
Touchpoint
    [on Surface]
    →
Interaction
    →
Identity
    →
Referent
    →
Intent
    →
Intent Contract
    →
System
    →
Transaction
    →
Outcome
    →
Reality
```

### TR-014

`External Standards Version Governance`

**Every external standard entity must include:**
-  standard_version

**Examples:**
- GS1 General Specifications
- EPCIS
- Digital Link
- ESPR
- DPP Regulations

Existing entities retain their original version references.

No retroactive standard upgrades are permitted.

## SECTION 05
## Validation Layers

### VL-001
**Parent Validation**

Every entity must have exactly one parent.

### VL-002
**Cluster Validation**

Every entity must belong to exactly one primary cluster.

### VL-003
**Circular Validation**

Circular inheritance prohibited.

### VL-004
**Dual-Role Validation**

All dual-role entities must define:

`secondary_clusters[]`


### VL-005
**Temporal Validation**
- Tier-0
- Tier-1
- Tier-2

entities must include:
- valid_from
- valid_to

Tier-3 entities may optionally include temporal fields.

### VL-006
**Cross-Cluster Reference Validation**

Every cross-cluster relationship must reference valid entities.
No dangling references permitted.

### VL-007
**Cardinality Validation**

All WS-02A cardinality rules must be preserved.
