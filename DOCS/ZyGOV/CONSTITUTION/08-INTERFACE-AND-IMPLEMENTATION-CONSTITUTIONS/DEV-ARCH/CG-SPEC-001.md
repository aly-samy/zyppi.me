# CG-SPEC-001 — Capability Graph Constitution
 
## Chapter 1 — Constitutional Position & Purpose
 
**Status:** Ratified (Locked) **Version:** 1.0
  
# 1. Purpose
 
CG-SPEC-001 defines the constitutional model governing the **Zyppi Capability Graph**.
 
The Capability Graph is the Runtime's canonical projection of constitutional business capabilities.
 
It exists to answer one question—and one question only:
 
 
**"Given this identity, this standing, this jurisdiction, this policy context, and this moment in time, what business capabilities constitutionally exist?"**
 
 
Every interface within the Zyppi Interface Ecosystem SHALL derive capability discovery from this specification.
 
No interface owns capability discovery.
 
No interface defines capabilities.
 
No interface may construct an independent capability model.
  
# 2. Constitutional Position
 
The Capability Graph is **not** documentation.
 
It is **not** an API catalogue.
 
It is **not** endpoint discovery.
 
It is **not** service registration.
 
It is **not** transport metadata.
 
It is **not** an implementation registry.
 
It is the Runtime's constitutional projection of executable business capability.
 
Every capability exposed by the Runtime SHALL originate from constitutional governance.
 
The Capability Graph projects those constitutional facts into a machine-discoverable form.
  
# 3. Constitutional Authority
 
CG-SPEC-001 is a constitutional specification.
 
It establishes immutable principles governing capability discovery across the entire Zyppi platform.
 
It does **not** define:
 
 
- HTTP endpoints
 
- SDK methods
 
- RPC procedures
 
- CLI commands
 
- Plugin APIs
 
- Payload formats
 
- Serialization
 
- Transport protocols
 

 
Those belong to downstream interface specifications.
 
CG-SPEC-001 governs **what constitutionally exists**.
 
Interface specifications govern **how consumers interact with it**.
  
# 4. Scope
 
CG-SPEC-001 governs every capability exposed by the Zyppi Runtime, including those consumed through:
 
 
- API-SPEC-001
 
- AI-RPC-SPEC-001
 
- CLI-SPEC-001
 
- SDK-SPEC-001
 
- DEVTOOLS-SPEC-001
 
- Marketplace Integrations
 
- Extension Interfaces
 
- Plugin Interfaces
 
- Future constitutional interfaces
 

 
Every present and future interface SHALL consume the Capability Graph as its exclusive capability discovery mechanism.
  
# 5. Constitutional Definition of an Interface
 
A **Zyppi Interface** is any external surface through which a human or machine expresses business intent to the Runtime and receives constitutional outcomes.
 
Interfaces project constitutional behavior.
 
Interfaces never originate constitutional behavior.
 
Examples include:
 
 
- Network APIs
 
- SDKs
 
- Command-line tools
 
- AI-native interfaces
 
- Marketplace integrations
 
- Plugin ecosystems
 
- Future interface technologies
 

 
The constitutional definition of an interface is independent of transport technology.
  
# 6. Constitutional Definition of a Capability
 
A **Capability** is the smallest discoverable constitutional unit of business behavior.
 
A capability is **not** an endpoint.
 
It is **not** a function.
 
It is **not** a method.
 
It is **not** an implementation.
 
A capability is a constitutional projection describing that a specific business behavior may exist under a specific constitutional context.
 
Every Capability Entry SHALL include:
 
 
- Stable Capability Identifier
 
- Governing Constitutional Artifact
 
- Operation Category
 
- Lifecycle State
 
- Certification State
 
- Identity Requirements
 
- Standing Requirements
 
- **Jurisdiction Requirements**
 
- Policy Requirements
 
- Constitutional Metadata
 

 
For delegated capabilities, the Capability Entry SHALL identify the governing delegation source responsible for granting that capability.
 
Capabilities are immutable constitutional identities.
 
Their implementations may evolve.
 
Their identifiers SHALL NOT.
  
# 7. Constitutional Origin
 
Every capability SHALL originate from an appropriate constitutional artifact.
 
Constitutional Operations and Authorization Pre-flight Operations originate from:
 
 
- CL-07 Intent Contracts
 

 
Reasoning Operations originate from:
 
 
- RSN-002 Blueprint Registry
 

 
No capability SHALL exist independently of constitutional governance.
  
# 8. Core Philosophy
 
The Capability Graph exists to provide one universal mental model across every interface.
 
Discovery SHALL remain:
 
 
- Identity-aware
 
- Standing-aware
 
- Policy-aware
 
- Jurisdiction-aware
 
- Delegation-aware
 
- Deterministic
 
- Machine-readable
 
- Transport-independent
 

 
The Capability Graph SHALL be a **materialized projection of constitutional state**.
 
Constitutional state changes trigger graph materialization.
 
Consumers discover capabilities through graph snapshots.
 
Consumers SHALL NEVER rely upon live constitutional computation for capability discovery.
 
Every Capability Graph Snapshot SHALL possess:
 
 
- Stable Graph Identifier
 
- Snapshot Timestamp
 
- Content Identity
 

 
These identities enable deterministic discovery, offline validation, auditing, and reproducible AI planning.
 
Consumers discover capabilities once.
 
They never rediscover them differently across interfaces.

# 10. Mission
 
The Capability Graph answers:
 
 
**What business capabilities constitutionally exist for this consumer?**
 
 
The Capability Graph describes **discoverability**.
 
It does **not** determine **executability**.
 
Discovery establishes that a capability constitutionally exists.
 
Execution determines whether that capability may be performed under the consumer's current identity, standing, jurisdiction, policy context, and runtime conditions.
 
The Capability Graph deliberately does **not** answer:
 
 
- What URLs exist?
 
- What endpoints exist?
 
- Which HTTP methods are supported?
 
- Which SDK methods are available?
 
- Which protocol transports the request?

# Chapter 2 — Capability Model (Final Constitutional Draft)
 
## 2.4 Constitutional Identity
 
Every Capability Entry SHALL possess a globally unique, immutable Capability Identifier.
 
A Capability Identifier:
 
 
- SHALL NEVER change.
 
- SHALL NEVER be reused.
 
- SHALL survive implementation changes.
 
- SHALL survive Runtime upgrades.
 
- SHALL survive SDK evolution.
 
- SHALL survive transport evolution.
 
- SHALL survive interface evolution.
 

 
Capability Identifiers SHALL be globally unique across all Zyppi ecosystems, including federated deployments.
 
A breaking constitutional change SHALL create a new Capability Entry with a new Capability Identifier.
 
The previous Capability Entry SHALL remain permanently discoverable for constitutional lineage, audit, and historical verification.
  
## 2.6 Governing Constitutional Artifact
 
Every Capability Entry SHALL reference exactly one governing constitutional artifact.
 
The governing artifact SHALL be one of:
 
 
- CL-07 Intent Contract
 
- RSN-002 Blueprint Registry
 

 
Never both.
 
Never neither.
 
Composite capabilities SHALL themselves be governed by a dedicated CL-07 Intent Contract.
 
Composite Capability Entries SHALL additionally declare the Capability Identifiers of all constituent atomic Capability Entries.
 
Execution sequencing and orchestration remain defined by the governing CL-07 Intent Contract.
 
The Capability Graph records dependency relationships only.
  
## 2.7 Intrinsic Metadata
 
Every Capability Entry SHALL contain immutable constitutional metadata.
 
Intrinsic metadata exists independently of discovery context and SHALL NEVER change after creation.
 
Intrinsic metadata SHALL include:
 
 
- Capability Identifier
 
- Capability Name
 
- Capability Description
 
- Operation Category
 
- Constitutional Domain
 
- Governing Constitutional Artifact Reference
 
- Certified Governing Artifact Hash
 
- Certified Contract Schema Hash
 
- Stability Tier
 
- Capability Version
 
- Creation Timestamp
 
- Lineage Ancestor Identifier (Optional)
 
- Constituent Capability Identifiers (Composite Capabilities Only)
 

 
Intrinsic metadata SHALL remain identical regardless of:
 
 
- Identity
 
- Workspace
 
- Standing
 
- Jurisdiction
 
- Delegation
 
- Policy
 
- Interface
 
- Discovery Context
 

 
The following are NOT intrinsic metadata:
 
 
- Visibility
 
- Standing Requirements
 
- Identity Requirements
 
- Jurisdiction Requirements
 
- Delegation State
 
- Policy Evaluation
 
- Consumer Eligibility
 

 
These contextual attributes are projected during discovery and governed by Chapter 4.
  
## 2.7.1 Governed State
 
Lifecycle State and Certification State are constitutional governance properties.
 
They are NOT part of immutable Capability identity.
 
They SHALL be maintained through constitutional governance processes defined in:
 
 
- Chapter 6 — Lifecycle & Governance
 
- Chapter 7 — Certification & Conformance
 

 
Lifecycle State and Certification State are globally consistent for every Capability Entry but MAY evolve through governed constitutional processes.
 
Evolution of these states SHALL NOT alter:
 
 
- Capability Identifier
 
- Capability Version
 
- Certified Governing Artifact Hash
 
- Certified Contract Schema Hash
 

  
## 2.8 Constitutional Invariants
 
The following invariants SHALL always hold:
 
 
- One Capability Identifier refers to exactly one Capability Entry.
 
- Every Capability Entry has exactly one governing constitutional artifact.
 
- Every Capability Entry belongs to exactly one Operation Category.
 
- Capability identity SHALL NEVER mutate.
 
- Capability origin SHALL NEVER mutate.
 
- Capability category SHALL NEVER mutate.
 
- Silent semantic mutation is constitutionally prohibited.
 

 
The Certified Governing Artifact Hash SHALL permanently bind the Capability Entry to the exact certified constitutional artifact from which it originated.
 
The Certified Contract Schema Hash SHALL permanently bind the Capability Entry to the exact certified execution contract.
 
Any modification producing a different certified artifact hash or certified schema hash SHALL require creation of a new Capability Entry with a new Capability Identifier and a new Capability Version.
 
Historical Capability Entries SHALL remain permanently auditable.
  
## 2.9 Constitutional Prohibitions
 
The following behaviors are constitutionally prohibited:
 
 
- Duplicate Capability Identifiers
 
- Reuse of retired Capability Identifiers
 
- Synthetic capabilities without constitutional origin
 
- Transport-generated capabilities
 
- Interface-owned capabilities
 
- Capabilities without governing constitutional artifacts
 
- Capabilities without declared lifecycle state
 
- Capabilities without declared certification state
 
- Silent semantic mutation of existing Capability Entries
 
- Modification of immutable intrinsic metadata after creation
 

 
Violations of these prohibitions SHALL constitute constitutional non-conformance and SHALL fail certification.

# Chapter 3 — Capability Graph Model
 
## 3.1 Purpose
 
This chapter defines the constitutional model governing the **Capability Graph**.
 
Where Chapter 2 defines the immutable **Capability Entry**, this chapter defines how those entries are assembled into an immutable Runtime capability graph.
 
This chapter governs:
 
 
- Graph construction
 
- Materialization
 
- Snapshot generation
 
- Snapshot identity
 
- Snapshot lineage
 
- Freshness
 
- Pinning
 
- Publication
 
- Graph invariants
 

 
This chapter does **not** govern:
 
 
- Identity-specific discovery
 
- Standing evaluation
 
- Policy evaluation
 
- Jurisdiction filtering
 
- Delegation
 
- Visibility
 

 
Those are defined by Chapter 4.
  
# 3.2 Constitutional Definition
 
The Capability Graph is the Runtime's immutable, materialized projection of all constitutional Capability Entries.
 
The Capability Graph is:
 
 
- Read-only
 
- Deterministic
 
- Materialized
 
- Content-addressed
 
- Auditable
 
- Transport-independent
 

 
It is **not** generated per consumer.
 
It is **not** generated per request.
 
It is **not** an authorization model.
 
It is **not** an identity projection.
 
It is the Runtime's canonical capability inventory.
  
# 3.3 Materialization Model
 
The Capability Graph SHALL be produced through constitutional materialization.
 
Materialization assembles Capability Entries into immutable Runtime Graph Snapshots.
 
The Runtime SHALL NOT construct the graph dynamically during capability discovery.
 
Graph construction SHALL occur only through governed materialization.
  
## 3.3.1 Materialization Epochs
 
Constitutional changes MAY occur continuously.
 
The Runtime SHALL batch governed changes into a **Materialization Epoch**.
 
A Materialization Epoch represents one atomic constitutional state transition.
 
A Graph Snapshot SHALL be materialized **only upon the successful closure of a Materialization Epoch**.
 
No snapshot SHALL be generated outside an Epoch closure.
 
Epoch batching exists solely to improve Runtime efficiency.
 
It SHALL NOT affect constitutional correctness.
  
# 3.4 Graph Snapshots
 
Every materialization produces one immutable Graph Snapshot.
 
Every Graph Snapshot SHALL possess its own constitutional identity.
 
Each snapshot SHALL contain:
 
 
- Snapshot Identifier
 
- Snapshot Version
 
- Parent Snapshot Identifier
 
- Creation Timestamp
 
- Publication Timestamp
 
- Content Hash
 
- Snapshot Status
 
- Freshness State
 
- Ordered Capability Entries
 

 
Snapshots SHALL be immutable after publication.
  
## 3.4.1 Snapshot Status
 
Every snapshot SHALL have exactly one constitutional status.
 
Permitted values are:
 
 
- Active
 
- Superseded
 
- Invalidated
 

 
Active represents the currently published Runtime graph.
 
Superseded represents historical snapshots retained for audit.
 
Invalidated represents snapshots constitutionally withdrawn due to governance or integrity failures.

# 3.5 Snapshot Lineage
 
Every snapshot SHALL reference its immediate predecessor.
 
Snapshots therefore form an immutable lineage chain.
 
The lineage SHALL be continuous.
 
Missing lineage constitutes constitutional corruption.
 
Historical lineage SHALL remain permanently auditable.
  
# 3.6 Freshness Model
 
Freshness describes cache validity.
 
Freshness does **not** describe constitutional validity.
  
## 3.6.1 Freshness States
 
Permitted freshness values:
 
 
- Fresh
 
- Potentially Stale
 
- Stale
 
- Expired
 

 
Fresh
 
 
- newest published snapshot
 

 
Potentially Stale
 
 
- Runtime has accepted a Materialization Epoch that changes constitutional state, but publication has not yet completed
 

 
Stale
 
 
- newer snapshot has been published
 

 
Expired
 
 
- snapshot exceeds constitutional retention policy
 

A snapshot transitions from **Fresh** to **Potentially Stale** immediately upon the Runtime's acceptance of a Materialization Epoch that changes constitutional state.
 
A snapshot transitions from **Potentially Stale** to **Stale** immediately upon publication of the subsequent Active Graph Snapshot.
 
A snapshot transitions from **Stale** to **Expired** according to the constitutional snapshot retention policy.
 
Freshness affects cache validity only.
 
Freshness SHALL NEVER affect constitutional correctness.

  
# 3.7 Snapshot Pinning
 
Consumers MAY pin a specific Graph Snapshot.
 
Pinning guarantees discovery stability.
 
Pinning SHALL NOT guarantee execution authorization.
 
If a capability contained within a pinned snapshot is subsequently suspended, revoked, or otherwise rendered unavailable, execution SHALL fail through constitutional Authorization Pre-flight.
 
Runtime authorization always supersedes pinned discovery state.
  
# 3.8 Graph Construction Rules
 
A Graph Snapshot SHALL include every Capability Entry eligible for publication.
 
Eligible entries include:
 
 
- Experimental
 
- Certified
 
- Deprecated
 
- Archived
 
- Retired
 

 
Capability Entries SHALL appear exactly once.
 
Composite Capability Entries SHALL appear independently.
 
Their constituent atomic Capability Entries SHALL also appear independently.
 
The graph SHALL never duplicate a Capability Entry.
  
# 3.9 Graph Invariants
 
Graph construction SHALL satisfy the following invariants.
 
Identical constitutional state SHALL always produce byte-identical snapshots.
 
Capability ordering SHALL be canonical.
 
Ordering SHALL be based upon Capability Identifier.
 
Snapshots SHALL therefore be deterministic.
 
Snapshots SHALL be content-addressable.
 
Snapshots SHALL be deterministically diffable.
 
Consumers MAY transition between snapshots using constitutional Delta Payloads rather than full graph downloads.
 
Canonical serialization SHALL follow the constitutional serialization specification.
  
# 3.10 Graph Mutation
 
Graph mutation occurs only through constitutional governance.
 
Consumers SHALL NEVER mutate snapshots.
  
## 3.10.1 Mutation Triggers
 
A new Materialization Epoch MAY include:
 
 
- New Capability Entry
 
- Capability retirement
 
- Capability restoration
 
- Lifecycle transition
 
- Certification transition
 
- Constitutional amendment
 
- Registry synchronization
 

 
Consumer-specific events SHALL NOT trigger graph materialization.
 
The following SHALL NEVER regenerate the graph:
 
 
- User Identity
 
- Workspace
 
- Standing
 
- Policy
 
- Delegation
 
- Jurisdiction
 
- Visibility
 

 
These are discovery concerns.
  
# 3.11 Snapshot Publication
 
Successfully materialized snapshots SHALL be published into the Runtime Registry.
 
Publication SHALL expose:
 
 
- Snapshot Identifier
 
- Snapshot Version
 
- Content Hash
 
- Publication Timestamp
 
- Snapshot Status
 

 
Publication is transport-independent.
 
Interfaces SHALL consume published snapshots.
 
Interfaces SHALL NEVER construct their own graphs.
  
# 3.12 Graph Verification
 
The constitutional materialization algorithm SHALL be deterministic.
 
Any compliant implementation SHALL be capable of independently reconstructing the Capability Graph from the Capability Entry ledger.
 
Independent reconstruction SHALL produce an identical Content Hash.
 
Mismatch SHALL constitute constitutional failure.
  
# 3.13 Graph Compaction
 
Historical auditability SHALL be preserved indefinitely.
 
Operational efficiency SHALL also be preserved.
 
The Runtime MAY generate **Compacted Graph Snapshots**.
 
Compaction removes historical retired Capability Entries from the active operational graph while preserving complete constitutional history.
 
Historical Capability Entries SHALL remain recoverable through:
 
 
- Snapshot Lineage
 
- Historical Graph Snapshots
 
- Cryptographic proofs
 

 
A Compacted Graph Snapshot SHALL be generated as a **new immutable Graph Snapshot**.
 
A Compacted Graph Snapshot SHALL possess its own:
 
 
- Snapshot Identifier
 
- Snapshot Version
 
- Parent Snapshot Identifier
 
- Creation Timestamp
 
- Publication Timestamp
 
- Content Hash
 

 
A Compacted Graph Snapshot SHALL reference the complete Graph Snapshot from which it was derived as its Parent Snapshot.
 
Compaction SHALL NEVER modify, replace, rewrite, or destroy any previously published Graph Snapshot.
 
Historical Graph Snapshots SHALL remain permanently verifiable.
  
  
# 3.14 Prohibited Behaviors
 
The following are constitutional violations:
 
 
- Per-request graph generation
 
- Mutable snapshots
 
- Snapshot editing
 
- Consumer-specific graph construction
 
- Interface-owned graphs
 
- Non-deterministic ordering
 
- Snapshot publication outside Materialization Epoch closure
 
- Duplicate Capability Entries
 
- Missing snapshot lineage
 
- Content Hash mismatch
 
- Unauthorized graph mutation
 

  
## Chapter Success Criteria
 
This chapter is successful if:
 
 
- Capability Entries become immutable Runtime Graph Snapshots.
 
- Graph construction is deterministic.
 
- Graph materialization occurs only through Materialization Epochs.
 
- Every snapshot has immutable identity and lineage.
 
- Snapshots are independently verifiable.
 
- Snapshots can be pinned safely.
 
- Graph publication is transport-independent.
 
- Discovery remains entirely separate from graph construction.
 
- Every interface consumes the same published Runtime graph.
