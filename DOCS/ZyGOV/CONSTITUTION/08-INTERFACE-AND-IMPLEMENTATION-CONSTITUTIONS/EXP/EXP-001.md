# EXP-001 — Experience Constitution
 
## Constitutional Specification
 
### Version 1.0 (Locked & Ratified)
  
# 1. Purpose
 
The Experience Layer (EXP) is the constitutional layer responsible for transforming one or more authorized Projections into an actor-specific interaction outcome.
 
**EXP exists to answer:**
 
 
> "Given these projections, this actor, this context, and this intent, what experience should be delivered?"
 
 
EXP does not own truth.
 
EXP does not compute reality.
 
EXP does not alter projections.
 
EXP governs interaction.
  
# 2. Constitutional Position
 
The Zyppi Constitutional Stack is:
````
 ZRM 
 ↓ 
 Reality Views 
 ↓ 
 PRJ 
 ↓ 
 EXP 
 ↓ 
 ZT 
 ↓ 
 SDK 
 ````
Responsibilities:
 
  
 Layer  | Responsibility
---|--- 
ZRM | Reality
Reality Views | Reality computation
PRJ | Projection generation
EXP | Experience composition
ZT | Interaction resolution
SDK | Rendering and execution

  
# 3. Constitutional Principles
 
## EXP-CP-001 — Reality Independence
 
Experiences SHALL NOT directly access Reality.
 
All Experience construction SHALL occur exclusively through authorized Projections.
  
## EXP-CP-002 — Projection Dependency
 
Every Experience MUST be composed from one or more Projections.
 
An Experience without a Projection dependency is invalid.
  
## EXP-CP-003 — Actor Specificity
 
Experiences are actor-specific.
 
The same Asset MAY generate different Experiences for different Actors.
  
## EXP-CP-004 — Intent Sensitivity
 
Experiences are intent-sensitive.
 
The same Asset and Actor MAY generate different Experiences based on intent.
  
## EXP-CP-005 — Ephemeral Nature
 
Experiences are transient.
 
Experiences SHALL NOT become system-of-record artifacts.
 
Reality remains authoritative.
  
## EXP-CP-006 — Manifest Output
 
EXP outputs Experience Manifests.
 
EXP never outputs UI implementations.
  
## EXP-CP-007 — Policy Separation
 
### Experience Policy governs:
- composition
- routing
- sequencing
- navigation
- affordances
 
### Projection Policy governs:
- visibility
- masking
- disclosure
- authorization

Experience Policy SHALL NOT override Projection Policy.
  
# 4. Actor Model
 
## EXP-LD-017 — Canonical Actor Model
 
An Actor SHALL be defined by:
````ts
 (   
 authenticated_identity,   
 authorization_role,   
 jurisdiction,   
 organization_context 
 ) 
 ````
### authenticated_identity
 
Identifies who is interacting.
 
**Examples:**
- user id
- service principal
- AI agent id
- device identity
 
### authorization_role
 
Defines permissions.
 
Examples:
- consumer
- technician
- regulator
- pharmacist
- auditor
 
### jurisdiction
 
Defines legal context.
 
**Examples:**
- EU
- US
- Egypt
- GCC
 
### organization_context
 
Defines represented organization.
 
**Examples:**
- Manufacturer
- Regulator
- Retailer
- Hospital
 
Any change to any component SHALL trigger policy re-evaluation.
  
# 5. Experience Identity
 
## EXP-LD-006 — Template vs Instance Separation
 
EXP distinguishes between:
 
### Experience Template
 
Stable governed definition.
````
 experience_template_id 
````
Examples:
- consumer_product_page
- regulatory_audit
- counterfeit_investigation
 
### Experience Instance
 
Runtime generated outcome.
````
 experience_signature 
 ````
Generated from:
````
 BLAKE2b(   
 template_id +   
 actor +   
 intent +   
 context_hash +   
 policy_hash +   
 temporal_scope 
 )
````
Each unique evaluation produces a unique instance.
  
# 6. Experience Manifest
 
## EXP-LD-007 — Manifest Principle
 
EXP SHALL output Experience Manifests.
 
Manifests are:
- declarative
- deterministic
- portable
- render-independent
 
Manifests SHALL NOT contain:
- HTML
- Flutter widgets
- React components
- native UI code
 
Rendering belongs exclusively to SDK implementations.
  
## Required Manifest Elements
 
Every Manifest SHALL contain:
````
experience_signature: experience_template_id: 
actor_context: 
intent: 
temporal_scope: 
localization_context: 
projection_references: 
sections: 
affordances: 
policy_context: 
generated_at: 
````
# 7. Multi-Projection Composition
 
## EXP-LD-003
 
Experiences MAY compose multiple projections.
 
Example:
````
consumer_product_page  
├─ gs1_identity 
├─ dpp_sustainability 
├─ recall_status 
└─ authenticity_check 
````
Experience composition SHALL NOT merge underlying Reality.
 
Composition occurs exclusively at the projection level.
  
# 8. Temporal Scope
 
## EXP-LD-010
 
Every Experience SHALL declare temporal scope.
 
Allowed values:
````
current 
historical 
audit_date 
as_of_timestamp
````
**Examples:**
````
temporal_scope:   
     type: historical   
     as_of: 
 2025-01-01T00:00:00Z 
 ````
Different temporal scopes generate different Experience identities.
  
# 9. Nested Experience Composition
 
## EXP-LD-011
 
Experiences MAY contain nested Experiences.
 
Example:
````
Building Experience  
├─ Floor Experience  
│   ├─ HVAC Experience  
│   └─ Lighting Experience  
└─ Safety Experience 
````
**Each nested Experience:**
- remains independently valid
- retains its own signature
- follows its own policy evaluation
 
Rendering strategy is SDK-specific.
  
# 10. Experience Policy
 
## EXP-LD-008
 
Experience Policy governs:
 
### Composition
 
Which projections participate.
 
### Routing
 
Which experience template activates.
 
### Sequencing
 
Order of presentation.
 
### Navigation
 
How sections relate.
 
### Affordances
 
Available actions.
  
Experience Policy SHALL NEVER expose data hidden by Projection Policy.
  
# 11. Role Escalation
 
## EXP-LD-012
 
Experience Policy MAY require role escalation.
 
Examples:
````
 consumer → pharmacist  
 
 technician → auditor 
 ````

**Role escalation requires:**
1. Re-authentication
2. Actor context update
3. Projection re-evaluation
4. Experience regeneration
 
Escalation SHALL NOT reuse projections generated for the previous role.
  
# 12. Missing Data Classification
 
## EXP-LD-013
 
Experience Manifests SHALL distinguish:
 
### incomplete
 
Reality lacks sufficient observations.

 `status: incomplete `  

### redacted
 
Data exists but policy hides it.

 `status: redacted `  

### not_applicable
 
Data category does not apply.

 `status: not_applicable `  

The distinction MUST be preserved.
 
SDKs MAY render them differently.
  
# 13. Conflict Resolution
 
## EXP-LD-014
 
Multiple projections MAY disagree.
 
Conflicts are not errors.
 
Conflicts are features of multi-perspective reality.
 
Experience Policy SHALL define:
````
priority_order: 
disclosure_mode: 
explanation_required:
````

**Example:**
````
priority_order: 
  - regulatory
     - dpp
        - gs1
````
**Allowed disclosure modes:**
````
primary_only 
primary_plus_sources 
all_equal
````
 
# 14. Experience Cache Invalidation
 
## EXP-LD-015
 
Experience caches SHALL invalidate when:
 
### Projection invalidation
 
Any dependent projection becomes invalid.
 
### Policy changes
 
Relevant policies change.
 
### Temporal expiry
 
Freshness window expires.
 
### Actor changes
 
Actor tuple changes.
  
Cached Experiences SHALL NOT outlive their dependent projections.
  
# 15. Action Affordances
 
## EXP-LD-016
 
Experience Manifests MAY contain actions.
 
Actions SHALL be declarative.
 
Actions SHALL NOT directly mutate Reality.
 
Example:
````
action:
    intent: 
activate_service
   method: POST
   payload:
        actor_id:     
        product_zid: 
````
Execution creates Intent Transactions.
 
Intent Transactions subsequently generate Observations.
  
`Experience → Intent → Observation`
 
NOT
 
`Experience → Observation`
  
# 16. Ephemeral State Isolation
 
## EXP-LD-004
 
Ephemeral state SHALL remain outside Reality.
 
Examples:
 
 
- filters
 
- sorting
 
- view mode
 
- language selection
 
- pagination
 
- zoom level
 

 
These SHALL NOT create Observations.
 
These SHALL NOT modify Projections.
 
These SHALL NOT affect Reality.
  
# 17. Disappearance Test
 
## EXP-LD-005
 
If EXP disappears entirely:
 
 
- Reality remains valid.
 
- Reality Views remain valid.
 
- Projections remain valid.
 

 
Only interaction orchestration disappears.
 
Therefore:
 
EXP is dependent on PRJ.
 
PRJ is not dependent on EXP.
  
# 18. zTouch Boundary
 
## EXP-LD-009
 
zTouch SHALL resolve interactions into Experiences.
 
Examples:
````
QR Scan 
NFC Tap 
BLE Touch 
Voice Trigger 
Vision Recognition 
API Invocation 
AI Agent Request 
````
All interaction channels ultimately resolve to:

 `Experience Manifest `  
 
# 19. Constitutional Boundaries
 
EXP SHALL NOT:
 
 
- store Reality
 
- compute Reality
 
- alter Reality
 
- generate Observations
 
- define UI code
 
- override Projection Policy
 
- replace SDK responsibilities
