# G-0812 — M04 Pipeline Mapping

## Council Decision Record — Final

**Verdict: RATIFIED — PRESERVE NINE-STAGE CONSTITUTIONAL PIPELINE WITH INTERNAL REFACTORING**

The Council should **not replace the M04 Runtime pipeline** and should not create a second M08-specific lifecycle.

M08 completes and gives semantic substance to the Runtime lifecycle already established and ratified in M04. The nine stages remain the externally meaningful constitutional execution stages; M08 implementation may refactor their internal orchestration, provided the stage boundaries and invariants remain intact.

This is consistent with the governing M08-GDR, which identifies G-0812 as the question of how M08 completes the existing M04 nine-stage pipeline and presents preservation with internal refactoring as the strongest candidate.

# 2. Constitutional Finding

The Council finds that **M08 is not a replacement Runtime architecture**.

M04 established the Runtime's lifecycle:

1. Admission

2. Bundle Discovery

3. Bundle Verification

4. Dependency Resolution

5. Compatibility Validation

6. ACV Activation

7. Resolution Graph Construction

8. Active Execution

9. Receipt Generation

The M08-GDR records these nine stages explicitly.

The M08 reconnaissance independently confirms that these stages already exist in `runInternalPipeline`, in this exact order.

Therefore:

**M08 shall complete the existing Runtime lifecycle; it shall not redefine the Runtime lifecycle.**

This preserves architectural continuity between M04 and M08.

# 3. The Critical Distinction: Stage ≠ Task ≠ Gate

The Council records an important clarification.

The following are **different architectural objects**:

### M04 Runtime Stage

A constitutional lifecycle stage defining **what phase of execution is occurring**.

### CAW-011 / AMS Task

An administrative implementation unit defining **what implementation work must be performed**.

### M08 Council Gate

A constitutional decision defining **what semantic rule the implementation must obey**.

They must not be treated as interchangeable.

Consequently, there is **no requirement for AMS-0801 through AMS-0805 to map one-to-one onto the nine Runtime stages**.

This is particularly important because G-0811 has already established that CAW-011 task numbering carries historical/administrative identity rather than causal ordering authority.

# 6. Important Correction to the Existing M04/M08 Relationship

The Council specifically rejects an interpretation in which M08 simply means:
`AMS-0801 = Stage 1 AMS-0802 = Stage 2 AMS-0803 = Stage 3 AMS-0804 = Stage 4 AMS-0805 = Stage 5 `
That would be architecturally false.

For example, CAW-011 defines:

- `IT-0801` — Wire ACV loading into pipeline

- `IT-0802` — Wire Evidence loading into pipeline

- `IT-0803` — Generate Execution Receipt

- `IT-0804` — Policy evaluation integration

- `IT-0805` — Pipeline replay tests.

After G-0811, the logical dependency is:
`AMS-0801 / AMS-0802           │           ▼       AMS-0804    Policy Evaluation           │           ▼       AMS-0803  Receipt Materialization           │           ▼       AMS-0805  Replay / Verification `
That dependency graph governs **implementation causality**.

The nine-stage pipeline governs **Runtime execution lifecycle**.

These are complementary, not competing, structures.

# 7. Stage Invariants

Preservation of the nine-stage architecture is conditional upon preserving the following invariants.

## 7.1 Stage Order

The nine constitutional stages remain ordered as ratified:
`1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9 `
Internal refactoring may change implementation structure but may not silently reorder their constitutional meaning.

## 7.2 No Stage May Invent Constitutional State

A stage may only operate on explicit inputs and state produced by preceding authorized stages.

No stage may obtain missing information from:

- system time;

- randomness;

- environment variables;

- filesystem;

- network;

- database;

- process state;

- hidden mutable state.

The M08 constitutional invariants explicitly prohibit those ambient dependencies inside Runtime.

## 7.3 Failure Is Part of the Pipeline

A stage that cannot satisfy its constitutional preconditions must fail deterministically.

It must not silently convert an unresolved requirement into:
`allow success trusted valid `
The M08-GDR expressly establishes fail-closed behavior as an invariant.

## 7.4 Receipt Is an Outcome of Execution

Stage 9 cannot become an independent source of policy semantics.

The receipt records the result of the execution that precedes it.

This is consistent with G-0811's ratified causal correction: policy evaluation precedes receipt materialization.

# 8. Existing Implementation Does Not Change the Constitutional Decision

The reconnaissance establishes that M04's pipeline already exists.

Stage 1 is implemented, while Stages 2–8 are currently stubbed and Stage 9 remains a deferred/stubbed receipt path.

The Council does **not** interpret these stubs as evidence that the nine-stage architecture should be discarded.

Rather:

The stubs are incomplete implementations of an already-established lifecycle.

M08 therefore supplies the semantic and implementation completion of those stages.

# 9. M06/M07 Composition Boundary

The Council also records that M08 does not own the entire upstream resolution system.

The reconnaissance identifies a current composition gap between:
`M06 GS1 Resolution        ↓ M05 Registry / ACV        ↓ M07 Evidence Engine        ↓ M08 ExecutionRequest        ↓ Runtime `
The components exist independently, but the orchestration bridge is not yet fully composed.

G-0812 does **not** authorize the Runtime to acquire those responsibilities.

The established architecture remains:

- Application orchestrates retrieval and composition.

- Persistence owns storage.

- Evidence infrastructure resolves and verifies evidence.

- Runtime receives explicit constitutional inputs.

- Runtime executes the nine-stage lifecycle.

The Runtime remains carrier-blind and infrastructure-independent. CAW-002 explicitly assigns ACV, Evidence, Runtime, Policy, and Receipt to the constitutional execution side while keeping storage outside the Runtime.

# 10. Rejected Directions

## Direction A — Complete Existing Stages Without Internal Refactoring

**Rejected as the final architectural constraint.**

The nine stages must remain, but requiring the current internal implementation structure to remain unchanged would unnecessarily freeze implementation details established during M04's skeleton phase.

M04 was a skeleton. M08 is where the pipeline becomes substantive.

The Council therefore preserves **stage semantics**, not incidental implementation structure.

## Direction B — Replace the M04 Stage Structure

**Rejected.**

This would create a second Runtime lifecycle and sever M08 from the ratified M04 architecture.

It would introduce:

- architectural duplication;

- migration ambiguity;

- competing lifecycle definitions;

- unnecessary implementation risk.

The existing M04 pipeline is explicitly recorded as a ratified nine-stage execution trace.

There is no constitutional basis for replacing it.

## Direction C — Preserve Stages but Permit Internal Refactoring

**SELECTED.**

This provides the correct separation:

**Constitutional lifecycle is stable; implementation architecture remains evolvable.**

The M08-GDR itself identifies this direction as the strong candidate.

# 12. Relationship to M12

M08's final stage and M08's replay work must not be confused with the M12 scale replay program.

CAW-011 defines M12 as **Deterministic Replay**, with `IT-1201` depending on `IT-0805` and subsequent work leading to the 10,000-run CI replay gate.

Therefore:

- M08 establishes the executable pipeline and its functional replay correctness.

- M12 establishes deterministic replay validation at scale.

- G-0812 does not transfer M12's responsibilities into the M08 lifecycle.

This decision grants **architectural direction**, not implementation authorization.

The implementation agent may proceed only through subsequently authorized M08 planning and AMS artifacts.

In particular, this decision does **not** authorize Jules to:

- redesign the Runtime lifecycle;

- create a second pipeline;

- infer unresolved gate semantics;

- finalize policy semantics;

- finalize receipt semantics;

- choose hash domains;

- choose timestamp semantics;

- choose budget semantics;

- modify constitutional contracts without their respective authorization.

The M08-GDR establishes that unresolved gate questions remain unresolved until ratified.

# 15. Final Council Resolution

The Zyppi Constitutional Council resolves:

1. **The M04 nine-stage Runtime pipeline is preserved.**

2. **M08 shall complete that pipeline rather than replace it.**

3. **The nine stages are constitutionally meaningful lifecycle stages, not implementation-task boundaries.**

4. **Internal Runtime refactoring is permitted**, provided the nine-stage semantic order and invariants remain intact.

5. **CAW-011 task identifiers do not map one-to-one to Runtime stages.**

6. **G-0811's causal dependency graph governs implementation sequencing among M08 work units.**

7. **G-0812's nine-stage mapping governs Runtime execution lifecycle.**

8. **M08 functional replay and M12 scale replay remain distinct responsibilities.**

9. **No Runtime stage may obtain hidden state or infrastructure data.**

10. **Failure remains deterministic and fail-closed where constitutional requirements are unresolved.**

11. **Receipt Generation remains the final Runtime lifecycle stage and is causally downstream of policy execution.**

12. **No second Runtime lifecycle may be introduced for M08.**
