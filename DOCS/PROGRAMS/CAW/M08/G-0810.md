# G-0810 — Receipt Persistence Boundary

## Zyppi Constitutional Council Decision Record

**Gate:** G-0810 **Subject:** Receipt Persistence **Milestone:** M08 — Execution Evidence & Receipt Integrity **Status:** CLOSED — DIRECTION B RATIFIED **Implementation Authority:** NONE **Decision Authority:** Zyppi Constitutional Council

## 1. Constitutional Question

G-0810 determines the constitutional boundary between:

1. the Runtime's production of the Execution Receipt; and

2. the downstream persistence of that receipt.

The question is not how Zyppi stores receipts.

The question is whether persistence is part of constitutional Runtime execution or a downstream responsibility acting upon the Runtime's materialized output.

## 2. Council Decision

The Council selects:

### **Direction B — Runtime Materialization; Application/Repository Persistence**

The Runtime shall materialize the constitutional Execution Receipt as part of the execution output.

The Runtime shall not persist the receipt and shall not depend upon persistence infrastructure for constitutional execution.

The Application/Repository layer may receive the Runtime's materialized output and persist it through an authorized persistence mechanism.

Therefore:

**The Runtime produces constitutional truth; an external Application/Repository layer may persist that truth. Persistence is a downstream operational responsibility and is not a constitutional Runtime execution step.**

## 3. Direction Assessment

### Direction A — Runtime Persistence

**REJECTED.**

The Runtime shall not perform receipt persistence.

Persistence introduces external I/O and infrastructure dependency into the Runtime execution boundary. This conflicts with the established Runtime isolation and deterministic-execution model.

The Runtime must remain capable of executing its constitutional function without database access, network access, storage access, or persistence infrastructure.

Receipt persistence therefore cannot be a Runtime responsibility.

### Direction B — Runtime Materialization; Application/Repository Persistence

**SELECTED.**

This direction preserves the constitutional boundary.

The Runtime:

- executes the constitutional pipeline;

- materializes the Execution Receipt;

- returns the resulting execution output.

The Application/Repository layer:

- receives the materialized output;

- may persist the receipt;

- may provide the operational retrieval mechanism for persisted receipts.

The Runtime has no knowledge of the persistence mechanism.

### Direction C — Defer Persistence

**REJECTED.**

The Council does not defer the persistence boundary indefinitely.

M08 contains an explicit receipt-persistence responsibility at the Application layer. Deferring the question would leave the Runtime-to-persistence boundary unresolved despite the constitutional corpus already establishing the required separation.

The decision is therefore to define the boundary now while leaving physical persistence implementation to its appropriate governing layer.

## 4. Constitutional Boundary

The following boundary is ratified:
`┌──────────────────────────────────────┐ │              Runtime                 │ │                                      │ │  Constitutional Execution            │ │  Receipt Generation                  │ │  Deterministic Output               │ │                                      │ │  ZERO persistence I/O                │ └──────────────────┬───────────────────┘                    │                    │ ExecutionOutput                    │ containing receipt                    ▼ ┌──────────────────────────────────────┐ │       Application / Repository       │ │                                      │ │  Receipt Handoff                     │ │  Persistence                         │ │  Retrieval / Operational Storage     │ └──────────────────────────────────────┘ `
The dependency direction remains outward from the Runtime result toward the persistence layer.

The Runtime shall not reverse that dependency by importing, invoking, or otherwise depending upon persistence infrastructure.

## 5. Execution Receipt Handoff

The Runtime's responsibility terminates with production of the materialized execution output.

The Application layer receives that output independently of the persistence mechanism.

The persistence boundary therefore has the following semantic contract:
`Runtime    │    │ produces    ▼ ExecutionOutput    │    │ contains    ▼ ExecutionReceipt    │    │ may be persisted by    ▼ Application / Repository `
The Runtime shall have no dependency on a `ReceiptRepository`, database adapter, storage client, queue, or equivalent persistence mechanism.

No persistence interface is introduced into the Runtime merely by this decision.

## 6. Persistence and Constitutional Truth

Persistence occurs **after** constitutional execution.

Consequently:

- persistence is not part of the Runtime's constitutional decision;

- persistence availability is not an input to constitutional execution;

- persistence latency does not determine constitutional execution;

- persistence failure does not alter the already-materialized Runtime result;

- loss of a persisted copy does not retroactively change the Runtime result that was produced.

The persistence layer is responsible for preserving the materialized constitutional artifact according to its governing persistence requirements.

## 7. Receipt Integrity at the Persistence Boundary

The persisted receipt shall preserve the constitutional meaning of the Runtime-produced receipt.

Persistence shall not:

- modify constitutional fields;

- substitute different semantic values;

- recompute constitutional meaning;

- silently normalize the receipt into a different semantic representation;

- introduce values that were not produced by the Runtime.

The cryptographic definition of receipt hashes, canonicalization, hash-domain membership, and related integrity mechanisms remains governed by **G-0809**.

G-0810 establishes no independent signing or hashing mechanism.

## 8. Persistence Representation

G-0810 does not ratify a physical database schema.

The physical representation of persisted receipts remains governed by the appropriate persistence/application authority, including CAW-008 where applicable.

A persistence implementation may map the Runtime receipt into a storage representation, provided that such mapping does not alter the constitutional meaning or prevent verification of the materialized receipt.

G-0810 does not prescribe:

- PostgreSQL table structure;

- ORM models;

- transaction strategy;

- queueing;

- replication;

- indexing;

- archival strategy;

- storage-specific identifiers.

These are implementation concerns outside the constitutional persistence boundary established here.

## 9. Persistence Failure

If persistence fails after the Runtime has produced its constitutional output, the failure is an operational persistence failure.

It shall not cause the Runtime to reinterpret or retroactively invalidate the constitutional execution result.

The Application layer may surface the persistence failure through its own operational contract.

Such operational handling is outside the Runtime's constitutional semantics.

## 10. Replay Boundary

Persistence is not part of deterministic Runtime replay.

Replay concerns reproduction and verification of constitutional execution from its authorized execution boundary.

The Runtime shall not require a persistence system in order to perform replay.

Persistence may provide historical material for an external replay workflow, but the act of reading from or writing to persistence is not itself part of the Runtime's deterministic execution semantics.

## 11. CAW-008 Alignment

The Council records the documented adapter-placement discrepancy identified during M08 reconnaissance.

Any CAW-008 language suggesting that persistence adapters belong inside the Runtime package shall be corrected to conform to the ratified Runtime isolation boundary.

Persistence adapters belong outside `packages/runtime`.

The correction is a documentation/architecture alignment requirement and does not expand G-0810 into a redesign of CAW-008's physical persistence schema.

## 12. Constitutional Invariants

### **E-0810-01 — Runtime Non-Persistence**

The Runtime shall not persist Execution Receipts or perform persistence I/O.

### **E-0810-02 — Materialization Before Persistence**

The constitutional Execution Receipt shall be materialized by the Runtime before any downstream persistence operation occurs.

### **E-0810-03 — External Persistence Authority**

Receipt persistence shall be performed, when required, by an Application/Repository layer outside the Runtime.

### **E-0810-04 — Persistence Independence**

The Runtime shall not depend upon persistence availability, latency, or infrastructure state to establish its constitutional execution result.

### **E-0810-05 — Receipt Integrity**

Downstream persistence shall preserve the constitutional meaning and verifiability of the Runtime-produced receipt.

### **E-0810-06 — Cryptographic Separation**

G-0810 shall not define cryptographic signing, hashing, canonicalization, or hash-domain semantics. These remain governed by G-0809.

### **E-0810-07 — Storage Scope Separation**

G-0810 shall not prescribe physical storage schemas or infrastructure mechanisms. Such concerns remain under the appropriate Application/Persistence authority.

### **E-0810-08 — No Runtime Persistence Dependency**

`packages/runtime` shall remain independent of persistence adapters, databases, storage clients, and equivalent external persistence mechanisms.

## 14. Final Council Ruling

**G-0810 is CLOSED.**

**Direction B — Runtime Materialization; Application/Repository Persistence is RATIFIED.**

The constitutional boundary is:

**Runtime execution produces and materializes the Execution Receipt. Persistence occurs downstream, outside the Runtime, and does not constitute part of constitutional execution.**

The Council further records:

1. Runtime persistence is constitutionally prohibited.

2. Application/Repository persistence is the authorized downstream model.

3. The Runtime-to-persistence handoff is through the materialized execution output.

4. Persisted representations must preserve the constitutional meaning and verifiability of the Runtime-produced receipt.

5. Cryptographic signing and hash-domain treatment remain under G-0809.

6. Physical persistence schema and infrastructure remain outside G-0810.

7. CAW-008 documentation shall be aligned with the ratified Runtime isolation boundary.

8. No implementation authority is granted or implied by this Decision Record.

**Disposition: CLOSED — DIRECTION B RATIFIED.**
