# 1. Executive Resolution

The Zyppi Constitutional Council resolves that the apparent M08 dependency inversion is **real and material**, but that it shall **not** be corrected by renumbering or rewriting the historical task identifiers.

The Council therefore ratifies:

**CAW-011 task identifiers and titles are administrative/historical identifiers and carry no inherent semantic or causal ordering authority.**

The Council further ratifies the following **logical dependency graph** as the governing M08 semantic dependency:
`AMS-0801 ─────┐               │ AMS-0802 ─────┼──► AMS-0804 ───► AMS-0803 ───► AMS-0805               │               └──────────────────────────────────────── `
Where:

- `AMS-0801` = ACV loading / admission-side execution input preparation;

- `AMS-0802` = Evidence loading / evidence-side execution input preparation;

- `AMS-0804` = Policy evaluation integration;

- `AMS-0803` = Full Execution Receipt generation;

- `AMS-0805` = Pipeline replay tests.

The graph expresses **semantic and causal dependency**, not a renumbering of the CAW-011 task ledger.

CAW-011 remains authoritative for the identity and historical title of each task. The corrected dependency graph is authoritative for determining which semantic result must exist before another semantic contract may be finalized or integrated.

# 2. Constitutional Question

G-0811 asks:

**Does M08 formally recognize the logical dependency between policy evaluation, receipt materialization, and replay/verification rather than treating the numerical order of CAW-011 task identifiers as semantic execution order?**

The Council answers:

**YES.**

Policy evaluation is upstream of receipt materialization wherever the receipt contains information whose meaning is produced by policy evaluation.

The current CAW-011 table nevertheless records:
`IT-0803 — Generate Execution Receipt (full) IT-0804 — Policy evaluation integration `
with `IT-0804` depending on `IT-0803`.

This relationship is therefore recognized as a **roadmap dependency defect**, not as a constitutional statement that receipt semantics precede policy semantics.

## 3.2 Receipt Data Dependency

The existing receipt contract contains policy-derived information, including `policyVersion` and `decisionSummary`, alongside execution, input, output, and evidence hashes.

Therefore, the semantic meaning of a complete receipt depends upon the policy evaluation semantics that determine those values.

A receipt may be structurally represented before policy semantics are closed, but its **complete constitutional semantics cannot be finalized independently of policy semantics**.

## 3.3 M08 Decision Structure

M08-GDR establishes that Council decisions precede implementation planning, and implementation planning precedes AMS execution:
`M08-PREP    ↓ M08-GDR    ↓ M08-PLAN    ↓ AMS-080x    ↓ Implementation `
The Council decision layer must therefore establish the dependency before implementation planning is allowed to encode it.

## 3.4 M08 Semantic Dependency

`AMS-0801 AMS-0802    │    ▼ AMS-0804 — Policy Evaluation    │    ▼ AMS-0803 — Receipt Materialization    │    ▼ AMS-0805 — Replay / Verification `
and identifies Direction C — preservation of task IDs with an amended dependency graph — as the strong candidate.

# 4. Finding: Administrative Order Is Not Causal Order

The Council formally distinguishes:

### 4.1 Administrative Identity

The `IT-080x` and `AMS-080x` identifiers provide:

- historical traceability;

- task identity;

- roadmap reference;

- implementation-unit reference.

They do **not**, merely by numerical value, establish:

- execution causality;

- semantic precedence;

- constitutional authority;

- data dependency;

- gate-resolution order.

### 4.2 Logical Dependency

A logical dependency establishes that one semantic result is required for another semantic artifact to be meaningfully finalized or verified.

Accordingly:
`Policy semantics       ↓ Receipt semantics       ↓ Replay verification `
is a semantic relationship independent of whether the associated administrative identifiers are numerically ordered in the same way.

# 6. Why Direction C Is Selected

Direction C provides the required separation between **historical task identity** and **architectural causality**.

It avoids two distinct failures.

### Failure A — Renumbering

Renumbering would make the historical identifier falsely appear to encode architecture.

That would create a precedent in which every architectural correction requires rewriting historical task references.

This is rejected.

### Failure B — Ignoring the Inversion

Treating the CAW-011 numerical order as executable causality would encourage an implementation agent to construct receipt semantics against policy semantics that have not yet been established.

This is also rejected.

### Direction C

Direction C retains historical integrity while making the causal relationship explicit where it belongs: in the Council-approved dependency model.

This is the least destructive and most constitutionally precise correction.

# 7. Semantic Dependency vs. Implementation Dependency

The Council records an important qualification.

The statement:

`AMS-0804 → AMS-0803`

does **not** mean that no receipt-related code may exist before G-0807 or AMS-0804 is complete.

It means:

**Receipt semantic finalization and policy-dependent receipt integration may not be treated as independent of the policy semantics they represent.**

Accordingly, implementation may distinguish:

### Permitted before upstream semantic closure

- structural scaffolding;

- isolated serializer infrastructure;

- type definitions that do not assert unresolved semantics;

- tests of already-ratified generic serialization behavior;

- non-semantic plumbing.

### Not permitted before upstream semantic closure

- inventing policy-derived receipt semantics;

- assigning provisional constitutional meanings to `policyVersion`;

- inventing `decisionSummary` semantics;

- treating placeholder policy output as authoritative receipt content;

- finalizing receipt/hash semantics around unresolved policy behavior;

- claiming the downstream AMS is semantically complete.

This distinction prevents G-0811 from unnecessarily freezing engineering work while still preventing implementation from becoming the author of unresolved constitutional semantics.

# 8. Replay Dependency

The Council confirms:
`Policy semantics       ↓ Receipt semantics       ↓ Replay verification `
for M08 functional replay.

Replay verification depends upon the existence of a defined replay target.

Therefore, `AMS-0805` is downstream of the semantic closure of the receipt represented by `AMS-0803`.

However, this decision does **not** transfer the M12 scale-replay responsibility into M08.

The CAW corpus separately assigns the large-scale replay validation responsibility to the later M12 validation layer. The M08 dependency concerns the **functional semantic replay contract**, not the later scale gate.

# 9. Reconnaissance Discrepancy Resolution

The reconnaissance describes an alternative mapping in which:
`IT-0803 = Policy IT-0804 = Receipt `

`IT-0803 = Receipt IT-0804 = Policy `
The reconnaissance therefore **must not be treated as an alternate task authority**.

**CAW-011 controls task identity and official task titles.**

The reconnaissance is evidence used to identify architectural relationships and contradictions, but it does not possess authority to redefine CAW-011 task identity.

The logical dependency ratified by this record therefore uses the official CAW-011 identifiers:
`AMS-0801 / AMS-0802         ↓ AMS-0804 — Policy Evaluation         ↓ AMS-0803 — Receipt         ↓ AMS-0805 — Replay `
