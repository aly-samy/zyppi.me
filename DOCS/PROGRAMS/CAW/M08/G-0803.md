# 1. Question Presented

The governing question for G-0803 is:

**What is the constitutional identity of an `ExecutionReceipt`, and how shall `receiptId` be established while preserving Runtime purity, determinism, replayability, and separation from execution identity?**

The Council is not deciding the cryptographic algorithm or final hash-domain construction in this gate.

Those matters belong to **G-0809 — Hash Domains**.

The Council is deciding the **semantic identity rule** for `receiptId`.

# 2. Authority and Evidence Basis

This decision is governed by:

1. Ratified Zyppi constitutional authorities;

2. Applicable CEngS requirements governing Runtime purity, determinism, replayability, and hidden-state prohibition;

3. `RI-006`;

4. `CAW-007 — Runtime Contracts`;

5. `CAW-003 — Domain Model`;

6. `CAW-011 — Commerce Atlas Wedge Build Order`;

7. M08 preparation and gate records;

8. M08 repository reconnaissance;

9. The ratified G-0808 — Execution Context Sufficiency decision;

10. The ratified G-0814 — Execution Identity decision.

The M08 corpus identifies four principal directions for `receiptId`:

- deterministic derivation;

- application-supplied identifier;

- deterministic identifier derived from explicit `executionId` plus canonical output;

- operational persistence identifier.

The corpus identifies Direction C as the strong candidate because it separates execution identity from receipt content while preserving deterministic derivation.

The repository reconnaissance confirms that the existing `ExecutionReceipt` contract contains distinct `receiptId` and `executionId` fields, but receipt generation and receipt identity remain unimplemented.

# 3. Constitutional Finding

The Council finds that:

**`receiptId` is the constitutional identity of a particular execution receipt produced from an identified constitutional execution.**

It is therefore distinct from:
`requestId executionId receiptId operational persistence identity `
These identities shall not be conflated.

The previously resolved G-0814 establishes `executionId` as the identity of the constitutional execution.

G-0803 establishes the next layer:
`executionId       │       ▼ constitutional execution result       │       ▼ ExecutionReceipt       │       ▼ receiptId `
`receiptId` identifies the receipt artifact resulting from that execution.

# 4. Selected Direction

## D-0803-01 — Deterministic Receipt Identity Bound to Execution Identity

**DECISION: SELECTED**

`receiptId` shall be deterministically derived from:

1. the established `executionId`; and

2. the canonical receipt/result material required to identify the resulting receipt.

Conceptually:
`receiptId = DeterministicIdentity(     executionId,     canonicalReceiptMaterial ) `
This is a **semantic rule only**.

The Council does not prescribe in G-0803:

- the hash algorithm;

- the hash-domain label;

- the exact byte encoding;

- the canonical serialization mechanism;

- the complete field inclusion set.

Those decisions belong to G-0809.

# 5. Why `executionId` Participates

The Council expressly rejects deriving `receiptId` solely from receipt content.

If receipt identity were based only on output/content, two distinct executions producing the same constitutional result could collapse onto the same receipt identity.

G-0814 has established that distinct executions possess distinct explicit `executionId` values.

Therefore:
`different executionId         + same resulting content         ≠ same receipt identity `
The execution identity provides the necessary distinction.

This preserves the separation:
`executionId = identity of the execution receiptId   = identity of the receipt produced by that execution `

# 6. Determinism

`receiptId` shall be deterministic.

Given:
`same executionId + same constitutionally relevant receipt material `
the Runtime shall produce:
`same receiptId `
This is required for deterministic replay and independent verification.

The Runtime shall not obtain receipt identity from:

- system time;

- ambient randomness;

- process identity;

- machine identity;

- memory address;

- execution history;

- filesystem state;

- network state;

- persistence state.

The existing M08 reconnaissance confirms that the Runtime currently has no system-clock, `Math.random()`, `crypto.randomUUID()`, network, filesystem, or asynchronous completion-order dependency.

# 7. Replay Semantics

A replay shall preserve the original `executionId`.

When the same explicit execution boundary and the same constitutionally relevant receipt material are replayed:
`executionId₁ = executionId₂ receipt material₁ = receipt material₂ `
then:
`receiptId₁ = receiptId₂ `
Replay therefore does not mint a new receipt identity merely because the Runtime is being evaluated again.

The replay operation verifies that the historical execution remains reproducible.

This is consistent with the M08 requirement that identical explicit inputs and authorized constitutional context produce deterministic results.

# 8. Receipt Identity Is Not Persistence Identity

`receiptId` is a **constitutional receipt identity**.

It is not inherently:

- a database primary key;

- a storage object identifier;

- a filesystem identifier;

- a distributed tracing identifier;

- a transport identifier.

Persistence concerns remain outside the Runtime and are governed separately by **G-0810**.

The Runtime may materialize a receipt containing `receiptId`.

The Runtime shall not persist the receipt merely because G-0803 establishes its identity.

# 9. Receipt ID Is Not Application-Supplied

## D-0803-02 — Application-Supplied Receipt Identifier

**DECISION: REJECTED**

The Application shall not supply `receiptId` as an independent constitutional input.

Reasons:

1. It would make receipt identity depend on caller behavior.

2. It would weaken deterministic replay semantics.

3. It would introduce a second identity authority for the receipt.

4. It would unnecessarily expand the execution boundary.

5. G-0814 already establishes the upstream execution identity required to distinguish executions.

The Application may retain its own operational identifiers, including `requestId`.

It does not thereby become the constitutional authority for receipt identity.

# 10. Receipt ID Is Not an Independent Random Identifier

## D-0803-03 — Random or Ambient Receipt Identity

**DECISION: REJECTED**

The Runtime shall not generate `receiptId` using:
`crypto.randomUUID() Math.random() system randomness wall-clock time machine identity process identity `
Such mechanisms would violate the Runtime's deterministic and pure execution model.

# 11. Receipt ID Is Not a Persistence-Assigned Identity

## D-0803-04 — Persistence Identity

**DECISION: REJECTED AS THE CONSTITUTIONAL RECEIPT ID**

An Application or persistence layer may assign its own storage identifier.

That identifier is operational and shall not replace the constitutional `receiptId`.

This preserves the layer boundary established by M08:
`Runtime   │   └── materializes constitutional receipt  Application / Persistence   │   └── may persist and assign operational storage identity `
The Runtime does not require persistence in order to establish receipt identity.

# 12. Circularity Prohibition

The Council expressly establishes the following rule:

**`receiptId` shall never be derived from a canonical representation that already contains the final `receiptId`.**

Therefore the derivation must conceptually operate over:
`executionId + receipt material excluding receiptId `
and produce:
`receiptId `
The resulting `receiptId` may then appear in the final serialized `ExecutionReceipt`.

This eliminates self-referential identity construction.

The exact canonical material and hash-domain construction are delegated to G-0809.

# 13. Relationship to `deterministicHash`

G-0803 does not define `deterministicHash`.

The Council records only the following distinction:
`receiptId     = identity of the receipt  deterministicHash     = cryptographic/deterministic binding of the applicable constitutional material `
They are therefore not presumed to be synonymous.

Neither field shall be defined recursively through the other.

Their exact relationship, if any, belongs to G-0809.

# 14. Relationship to `executionId`

The Council ratifies the following identity hierarchy:
`requestId    │    │ operational request identity    ▼ executionId    │    │ constitutional execution identity    ▼ ExecutionReceipt    │    │ constitutional receipt identity    ▼ receiptId `
The arrows represent semantic relationship, not necessarily a direct derivation function.

In particular:

- `requestId` does not determine `receiptId`;

- `executionId` is not synonymous with `receiptId`;

- `receiptId` does not replace `executionId`.

# 15. Canonical Material

The phrase **canonical receipt material** is used in this decision as a semantic category.

It means the constitutionally relevant receipt/result information that G-0809 subsequently authorizes for deterministic identity construction.

G-0803 does **not** establish the final field list.

Potential receipt fields currently documented in the M08 contract include:
`receiptId executionId runtimeVersion inputHash outputHash evidenceHash policyVersion decisionSummary executionTime deterministicHash `
The repository already provides deterministic canonical serialization for `ExecutionReceipt`, with a fixed field ordering, but the final semantic field participation remains a Council matter downstream.

Accordingly, no implementation agent shall infer the final hash input from this record.

# 16. Hashing Boundary

The Council explicitly delegates cryptographic construction to **G-0809**.

G-0809 shall determine:

1. the hash algorithm;

2. hash-domain labels;

3. canonical encoding;

4. field inclusion;

5. field ordering;

6. absence/null semantics;

7. treatment of nested material;

8. digest representation;

9. interaction between `receiptId` and other receipt hashes.

G-0803 establishes only the semantic requirement that the resulting receipt identity be deterministic and bound to `executionId` and the authorized receipt material.

This separation prevents G-0803 from becoming an accidental cryptography-design gate.

# 17. Constitutional Invariants

The Council ratifies the following invariants.

## E-0803-01 — Receipt Identity

`receiptId` identifies the constitutional receipt produced by an execution.

## E-0803-02 — Execution Separation

`receiptId` is distinct from `executionId`.

## E-0803-03 — Determinism

Identical authorized receipt material under the same `executionId` produces the same `receiptId`.

## E-0803-04 — Execution Binding

`receiptId` is derived in a manner that preserves the identity of the execution that produced the receipt.

## E-0803-05 — No Ambient Identity

`receiptId` shall not depend on ambient time, randomness, machine state, process state, filesystem state, network state, or execution history.

## E-0803-06 — No Application Authority

The Application shall not independently choose the constitutional `receiptId`.

## E-0803-07 — No Persistence Authority

Persistence shall not define or replace the constitutional `receiptId`.

## E-0803-08 — Replay Stability

Replay of the identical explicit execution boundary shall reproduce the same `receiptId`.

## E-0803-09 — No Circular Derivation

`receiptId` shall not be included in the material from which that same `receiptId` is derived.

## E-0803-10 — Cryptographic Deferral

The exact cryptographic construction of `receiptId` is delegated to G-0809.

# 21. Final Council Determination

The Council determines that **Direction C — Deterministic Identifier + Execution Identity** is the constitutionally appropriate direction for `receiptId`.

The Council rejects:

- application-supplied receipt identity;

- ambient/random receipt identity;

- persistence-assigned constitutional receipt identity;

- self-referential receipt identity.

The resulting identity model is:
`requestId     ↓ executionId     ↓ constitutional execution     ↓ ExecutionReceipt     ↓ receiptId `
with the important distinction that the relationship is semantic rather than a claim that every identity is mechanically derived from the preceding identifier.

# 23. Constitutional Principle Established

The Council records:

**A constitutional receipt shall possess a deterministic identity bound to the execution that produced it, without making receipt identity dependent upon ambient state, caller-selected receipt identifiers, persistence state, or self-referential hashing.**

And:

**Execution identity and receipt identity are distinct constitutional identities.**

These principles govern subsequent M08 receipt, hashing, and persistence decisions.
