# 1. Question Presented

The governing question for G-0814 is:

**What uniquely identifies a constitutional Runtime execution?**

G-0808 has already established that `executionId` is a required and distinct constitutional execution identifier within the explicit execution boundary.

G-0814 therefore determines the semantic treatment of that identifier.

This gate does **not** define:

- cryptographic hash domains;

- receipt construction;

- persistence identity;

- entropy semantics;

- temporal semantics;

- a global identity service;

- implementation-specific identifier algorithms.

Those matters remain within their respective gates.

# 2. Authority and Evidence Basis

This decision is governed by:

1. Ratified Zyppi constitutional authorities;

2. applicable CEngS requirements;

3. `CAW-007 — Runtime Contracts`;

4. `CAW-011 — Commerce Atlas Wedge Build Order`;

5. M08 preparation and gate records;

6. M08 repository reconnaissance;

7. the previously decided G-0808 architectural direction.

The M08-GDR identifies four candidate directions for `executionId`:

- Direction A — Application-Supplied;

- Direction B — Deterministically Derived;

- Direction C — Explicit Entropy-Derived;

- Direction D — Separate Execution Sequence.

The governing Runtime principles require deterministic execution and prohibit hidden identity dependencies such as ambient randomness, process identity, machine identity, wall-clock time, memory address, and execution history.

# 3. Constitutional Meaning of `executionId`

The Council establishes:

**`executionId` is the explicit identifier of one constitutional Runtime execution.**

It is part of the explicit execution boundary.

It is not:

- a receipt identifier;

- a request identifier;

- an operational trace identifier;

- a policy identifier;

- an entropy value;

- a Runtime-generated sequence number.

The distinction is therefore:
`requestId     = request identity executionId   = constitutional execution identity receiptId     = receipt identity trace identity = operational tracing identity `
These identities shall not be conflated.

# 4. Selected Direction

## D-0814-01 — Application-Supplied Execution Identity

**DECISION: SELECTED**

`executionId` SHALL be supplied explicitly to the Runtime as part of the execution boundary.

The Runtime SHALL NOT generate `executionId`.

The Runtime SHALL NOT derive `executionId` from:

- the execution payload;

- `requestId`;

- `entropy`;

- execution time;

- system state;

- execution history;

- any other ambient or internally generated value.

The Runtime receives the identifier and uses it as an explicit constitutional input.

This preserves the Runtime's purity and deterministic execution model.

# 5. Identity Provenance

The execution identifier exists **before Runtime evaluation begins**.

The component responsible for constructing the `ExecutionRequest` supplies the identifier.

This decision does not establish a separate constitutional identity authority, identity service, admission minting mechanism, or cryptographic identity protocol.

Such mechanisms are unnecessary for the semantic decision being made by this gate.

The important constitutional requirement is simply:

**The Runtime must receive the execution identity explicitly; it must not create it implicitly.**

# 6. Uniqueness

The Council does not establish a global uniqueness registry or Runtime-maintained sequence.

The Runtime is pure and does not maintain execution history.

Therefore:

**The Runtime does not enforce historical global uniqueness of `executionId`.**

The supplied `executionId` is treated as the explicit identifier of the execution boundary presented to the Runtime.

The mechanism by which an Application or other upstream component generates identifiers is an application/infrastructure concern unless separately elevated by a future constitutional decision.

No particular algorithm such as UUID, ULID, timestamp-based identity, or cryptographic digest is mandated by G-0814.

# 7. Relationship to `requestId`

`requestId` and `executionId` are distinct.

A `requestId` identifies the originating request.

An `executionId` identifies the constitutional Runtime execution represented by the admitted execution boundary.

The Runtime SHALL NOT substitute `requestId` for `executionId`.

The existence of both identifiers does not imply that every application request must produce multiple executions. It merely preserves the semantic distinction between request identity and execution identity.

# 8. Relationship to Entropy

`entropy` is independent of `executionId`.

G-0808 establishes that entropy is conditional and explicit: it is present only when a governed Runtime operation requires it.

Therefore:

**Entropy SHALL NOT be used as the identity mechanism for `executionId`.**

In particular, G-0814 does not require entropy to be present merely to create an execution identity.

This avoids coupling execution identity to an execution-control input whose presence is itself conditional.

# 9. Replay Semantics

Replay SHALL preserve the original `executionId`.

A replay of an execution therefore reuses the same explicit execution identity together with the same constitutionally relevant execution inputs.

Conceptually:
`Original execution:     executionId = X     explicit inputs = B         ↓     Runtime         ↓     receipt  Replay:     executionId = X     explicit inputs = B         ↓     Runtime         ↓     deterministic replay result `
Replay does not cause the Runtime to generate a replacement execution identity.

This is consistent with the governing deterministic-execution requirement that identical explicit inputs produce identical outputs and related deterministic artifacts.

# 10. Direction B — Deterministically Derived

**DECISION: REJECTED**

Deriving `executionId` from execution content would make execution identity substantially equivalent to content identity.

That would create ambiguity between:

- identity of the execution; and

- identity of the execution's explicit content.

It is unnecessary because the execution identifier is already an explicit execution-boundary value.

G-0814 therefore does not adopt content-derived execution identity.

# 11. Direction C — Explicit Entropy-Derived

**DECISION: REJECTED**

Entropy is an execution input, not an identity mechanism.

G-0808 expressly establishes that entropy is conditional rather than mandatory.

Using entropy to derive `executionId` would unnecessarily couple two separate concepts and would make identity semantics depend upon an input whose presence is operation-dependent.

No such coupling is required.

# 12. Direction D — Separate Execution Sequence

**DECISION: REJECTED**

A Runtime-maintained sequence would require execution history or mutable state.

That conflicts with the Runtime's purity and deterministic execution requirements.

An externally supplied sequence would simply become another form of supplied execution identity and is therefore unnecessary to establish as a distinct constitutional model.

G-0814 therefore does not establish a constitutional execution sequence.

# 13. Runtime Requirements

The following requirements are ratified:

### E-0814-01 — Explicit Identity

Every constitutional Runtime execution SHALL have an explicit `executionId`.

### E-0814-02 — Supplied Identity

`executionId` SHALL be supplied as part of the explicit execution boundary.

### E-0814-03 — No Runtime Minting

The Runtime SHALL NOT generate or derive `executionId`.

### E-0814-04 — Identity Separation

`executionId` SHALL remain distinct from `requestId`, `receiptId`, and operational trace identity.

### E-0814-05 — Entropy Independence

`executionId` SHALL NOT depend on `entropy` merely for identity purposes.

### E-0814-06 — No Ambient Identity

`executionId` SHALL NOT depend implicitly on clock time, randomness, process identity, machine identity, memory state, execution history, or other ambient Runtime state.

### E-0814-07 — Replay Preservation

Replay SHALL preserve the original `executionId`.

### E-0814-08 — Immutability During Execution

Once the execution boundary is admitted, `executionId` SHALL remain unchanged throughout that execution.

# 15. Relationship to G-0808

G-0808 established:
`requestId executionId constitutional execution boundary `
as distinct semantic concepts.

G-0814 now resolves the remaining question delegated to it:

**`executionId` is an explicit supplied execution identity, not a Runtime-derived value.**

The Hybrid Explicit Context Binding direction established by G-0808 therefore remains unchanged.

No amendment to the G-0808 architectural direction is required.

# 16. Relationship to G-0803

G-0803 may now use `executionId` as a stable semantic input when determining receipt identity.

G-0814 does not determine the construction of `receiptId`.

That construction remains the responsibility of G-0803, subject to the cryptographic decisions of G-0809.

# 17. Relationship to G-0809

G-0814 establishes the **meaning** of `executionId`.

It does not determine:

- whether `executionId` enters `inputHash`;

- whether it enters `deterministicHash`;

- whether it enters `receiptId` derivation;

- which hash domain contains it;

- which canonical serialization is used for those domains.

Those are G-0809 decisions.

This preserves the distinction between semantic identity decisions and cryptographic construction.

# 18. Final Council Determination

The Council determines that the simplest constitutionally sufficient model is:
`Upstream execution construction             │             │ supplies executionId             ▼      ExecutionRequest             │             ▼      Runtime Admission             │             │ validates explicit boundary             ▼        Execution             │             ▼         Receipt `
No additional identity authority, admission minting protocol, entropy-derived identity mechanism, execution sequence, or identity registry is required by G-0814.

The constitutional requirement is satisfied by an explicit, supplied, immutable execution identifier.

# 19. Disposition

**G-0814 — CLOSED**

**Selected Direction: Direction A — Application-Supplied Execution Identity**

The Council considers the semantic question resolved.

No implementation authority is granted by this record.

Any implementation change arising from this decision SHALL require an appropriate subsequent implementation mandate and SHALL conform to the final contracts and cryptographic decisions established by the applicable M08 gates.

## Council Principle Established

**Execution identity is explicit, supplied, immutable, and distinct from request, receipt, and operational identities. The Runtime consumes execution identity; it does not create it.**
