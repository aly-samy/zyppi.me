## Objective

Implement `AuthorityRecord` in `packages/domain` as a pure, immutable, JSON-safe Domain representation of the minimal authority grant defined by CAW-008. This is a **structural record of a granted scope over a time window** — not an authority engine, not a delegation system, not a policy evaluator.

## Constitutional Grounding

CAW-003 defines Authority as:

> Who/what is permitted to assert or approve a given fact — minimal wedge scope, enough to satisfy policy evaluation for the demo dataset, not a full authority engine.

CAW-008 defines the wedge's `authorities` storage row as:

```text
id
subject_id
scope
valid_from
valid_to
```

The Domain representation maps these storage names to the established TypeScript naming convention:

```text
id          → authorityId
subject_id  → subjectId
scope       → scope
valid_from  → validFrom
valid_to    → validTo
```

`subjectId` is an opaque reference to whatever holds the authority (in this wedge, an Identity). This task does not import `IdentityRecord`, require `subjectId` to be a valid `identityId`, or check that the referenced subject exists — same structural/referential boundary already established by `identityId` in `EvidenceRecord` (AMS-0303).

## Explicitly Rejected Scope (read before implementing)

CAW-003's M03 planning note explicitly excluded full AI-agent delegation modeling from this wedge — distinct Agent/Sponsor/Organization identity layers, cascading revocation, non-repudiable agent provenance, multi-level delegation chains. This is the task where that exclusion is most likely to be silently reintroduced, because "Authority" is the natural place someone reaches for that machinery. **Do not.**

Do not add:

- a `delegatedBy` / `grantedBy` / `sponsorId` field or any delegation-chain reference
- a `delegationDepth` or hierarchy field
- revocation status, revocation reason, or revocation cascade logic
- agent-vs-human subject discrimination
- any reference to POL-001's full Authority lifecycle (Established/Active/Suspended/Revoked) — this wedge's `AuthorityRecord` has no status field at all; validity is expressed purely through `validFrom`/`validTo`

If a loaded governing source appears to require any of the above, stop and report the exact source and conflict — do not implement it under this mandate. This exclusion was a deliberate Chair-level scope decision, not an oversight.

## Required Domain Shape

```typescript
export type AuthorityRecord = {
  readonly authorityId: string;
  readonly subjectId: string;
  readonly scope: string;
  readonly validFrom: string;
  readonly validTo: string;
};
```

Do not add fields beyond these five. Do not add `createdAt`/`updatedAt` — CAW-008's `authorities` table does not include them, same reasoning AMS-0302 applied to `ReferentRecord`.

## Field Contracts

### `authorityId`

- Required, string, non-empty after trimming.
- Preserve the supplied value exactly. No UUID enforcement unless a governing source explicitly requires it.

### `subjectId`

- Required, string, non-empty after trimming.
- Preserve exactly. Do not query whether the referenced subject exists — Registry/Application concern, not Domain.

### `scope`

- Required, string, non-empty after trimming.
- Preserve exactly. **Open string, not a closed union** — CAW-003/CAW-008 define the field but no ratified finite scope vocabulary exists (same treatment as `evidenceType` in AMS-0303). Do not invent literals such as `"read:product"` or `"approve:evidence"`. Record the absence of a ratified vocabulary as a bounded implementation note, same as AMS-0303 did.

### `validFrom` / `validTo`

- Required, strict ISO-8601 UTC timestamp, valid calendar date/time.
- Preserve exactly — do not normalize, reformat, or regenerate.
- Reuse the existing timestamp-validation logic from AMS-0301 if exported and suitable. Do not duplicate the calendar-validation algorithm a fourth time.
- **Nullability of `validTo` is an unresolved specification gap** — CAW-008's table doesn't state whether an authority can be open-ended (no expiry). Default assumption for this task: `validTo` is **required**, not nullable, matching the wedge's general preference for explicit, non-speculative fields (Evidence explicitly excluded expiration/lifecycle modeling for the same reason). If the exact loaded CAW-008 source or another governing document contradicts this, stop and report before implementing — do not silently decide the field is optional.
- **Ordering check** (reasonable implementation inference, not a directly-cited requirement): `validTo` must not be chronologically before `validFrom`. This is a pure structural comparison between two already-supplied fields, not a referential/external check, so it stays in Domain's validation boundary. If a governing source is found that contradicts this, report it rather than removing the check silently.

## Validation Contract

```typescript
export function validateAuthorityRecord(
  candidate: unknown,
): ValidationResult<AuthorityRecord, AuthorityValidationError>;

export type AuthorityValidationErrorCode =
  | "INVALID_AUTHORITY_ID"
  | "INVALID_SUBJECT_ID"
  | "INVALID_SCOPE"
  | "INVALID_VALID_FROM"
  | "INVALID_VALID_TO"
  | "VALID_TO_BEFORE_VALID_FROM";

export type AuthorityValidationError = {
  readonly code: AuthorityValidationErrorCode;
  readonly field: keyof AuthorityRecord;
  readonly message: string;
};
```

Reuse the existing `ValidationResult<T, E>` convention — do not create a second generic result abstraction (this is the fourth entity; if a fourth abstraction attempt happens, that's a signal to stop and check the existing one rather than proceed). For a non-object or `null` root input, return the same first-field error convention established in AMS-0303 (`code: "INVALID_AUTHORITY_ID"`, `field: "authorityId"`).

`VALID_TO_BEFORE_VALID_FROM` reports against `field: "validTo"`.

Validation must not throw, must not perform I/O or cross-record lookups, must be deterministic.

## Canonical Serialization

```typescript
export function serializeAuthorityRecord(record: AuthorityRecord): string;
```

Alphabetical key order, matching every prior entity's convention:

```text
authorityId
scope
subjectId
validFrom
validTo
```

Deterministic, insertion-order independent, round-trips through `JSON.parse` → `validateAuthorityRecord` without value changes.

## Test Requirements

Create `packages/domain/src/authority.test.ts`. At minimum:

**Valid records** — a fully valid `AuthorityRecord`; preservation of original string representations; valid strict ISO-8601 UTC timestamps; `validFrom === validTo` (zero-duration, boundary case — confirm this is accepted, not rejected, since the rule is "not before," not "strictly after").

**Invalid root values** — `null`, `undefined`, primitives, arrays, malformed objects; confirm structured error, no throw.

**Field validation** — for each field: missing, wrong type, empty string, whitespace-only string (where applicable). For `validFrom`/`validTo`: malformed syntax, non-UTC, invalid month/day, invalid leap-day, valid leap-year timestamp.

**Ordering** — `validTo` before `validFrom` is rejected with `VALID_TO_BEFORE_VALID_FROM`; `validTo` after `validFrom` is accepted; `validTo` equal to `validFrom` is accepted.

**Serialization** — exact alphabetical key order, deterministic repeated output, insertion-order independence, round-trip fidelity, no mutation of the original object.

**Regression** — run the complete existing Domain test suite; confirm AMS-0301/0302/0303 behavior is unchanged.
