## Objective

Configure Vitest as Zyppi’s repository-wide runtime test framework.

The resulting test foundation SHALL provide:

- Consistent TypeScript test discovery across the monorepo
- Deterministic test execution
- Strict test-state and mock isolation
- Serial execution as the M01 baseline
- A single root test command suitable for local development and CI
- A minimal, extensible root configuration

Vitest SHALL be responsible for runtime assertions only. TypeScript project references and `tsc -b` remain the authoritative mechanisms for static type validation and compile-time dependency verification.

---

## Background

IT-0103 established the TypeScript project-reference graph. IT-0104 established static linting and architectural import-boundary enforcement. IT-0105 established repository-wide formatting.

IT-0106 establishes the runtime testing foundation required before constitutional packages and implementation behavior are introduced in M02 and M03.

Testing is an implementation-quality mechanism and an early source of verifiable engineering evidence. It SHALL support deterministic and isolated execution without prematurely implementing Runtime, policy, registry, API, web, or edge behavior.

The current repository contains only foundational scaffolding. Therefore, this mandate SHALL establish only the minimum stable testing infrastructure required to verify that the monorepo can discover and execute TypeScript tests.

## Scope

The executing agent SHALL:

### 1. Install Vitest

Install the current stable Vitest release as a root workspace development dependency.

Install only the dependencies required to satisfy this mandate.

Do not add:

- Browser-testing frameworks
- End-to-end testing frameworks
- Cloudflare Worker testing packages
- Database testing packages
- Container-based testing tools
- External-service emulators
- Vitest type-checking packages

### 2. Create Root Vitest Configuration

Create a root Vitest configuration using the current stable configuration format appropriate to the installed Vitest version.

The root configuration SHALL:

- Be repository-wide
- Remain minimal
- Contain only shared test orchestration and shared test defaults
- Avoid workspace-specific conditional logic
- Avoid application-specific configuration
- Avoid future Worker-specific configuration

The root configuration SHALL be structured so that future workspace-specific testing can be introduced without converting the root configuration into a monolithic switchboard.

Do not create `vitest.workspace.ts` during this task unless the installed Vitest version requires it for the basic repository-wide configuration. No current repository requirement justifies introducing workspace-specific Vitest configuration.

### 3. Configure Test Discovery

Configure TypeScript test discovery under:

```text
packages/**
apps/**
edge/**
```

Support the following test-file conventions:

```text
*.test.ts
*.spec.ts
```

Exclude generated and non-source paths, including:

```text
node_modules/
dist/
build/
coverage/
.git/
```

Exclude TypeScript build-information files and generated declaration outputs where applicable.

### 4. Configure the Default Environment

Configure the default test environment as:

```text
node
```

Do not add:

- `jsdom`
- Browser environments
- Cloudflare Worker environments
- Custom environments

Worker-specific testing SHALL be introduced only when M10 contains actual Worker behavior requiring it.

### 5. Enforce Strict Test-State Isolation

The Vitest configuration SHALL explicitly enable:

```text
clearMocks: true
mockReset: true
restoreMocks: true
```

These settings SHALL be configured in the shared root test configuration rather than relying on developer convention.

The configuration SHALL prevent test suites from depending on mock history or mock implementations created by earlier tests.

### 6. Enforce Serial Execution for M01

Configure the M01 test baseline so test files do not execute in parallel.

The implementation SHALL explicitly disable file-level parallelism using the supported configuration mechanism of the installed Vitest version.

If the selected Vitest configuration also requires a pool or worker limit to guarantee serial execution, configure the minimum supported setting necessary to achieve that result.

Serial execution is the M01 baseline, not a permanent prohibition on future parallel testing.

Any future relaxation of this baseline SHALL require:

- An explicit engineering decision
- Demonstrated deterministic behavior
- Review of test isolation
- An intentional configuration change

The agent SHALL NOT leave parallelism dependent on implicit Vitest defaults.

### 7. Preserve Temporal Determinism

The initial test configuration and fixture SHALL NOT:

- Read the system clock
- Depend on the current date
- Depend on elapsed wall-clock time
- Use uncontrolled randomness
- Depend on execution order outside the explicitly configured serial baseline

Future tests may use controlled time mechanisms, such as Vitest fake timers or explicit system-time configuration, when a specific implementation requires them.

This task SHALL not add global time mocking because no current behavior requires it.

### 8. Configure Root Test Commands

Add or update root package scripts so:

```bash
pnpm test
```

runs the complete repository test suite in non-watch mode.

The command SHALL be suitable for:

- Local verification
- Automated execution
- CI use

If a separate CI-specific command is added, it SHALL invoke the same repository-wide test configuration and SHALL NOT create a second divergent test path.

### 9. Configure Coverage

Configure a root coverage command using Vitest’s supported coverage mechanism.

The coverage command SHALL execute successfully against the current test suite.

Do not:

- Set coverage thresholds
- Fail CI based on coverage percentages
- Add coverage policy
- Add coverage reporting requirements beyond the minimum supported output

Coverage thresholds and constitutional coverage requirements belong to a later implementation milestone after meaningful production behavior exists.

### 10. Add One Minimal Test Fixture

Add the minimum TypeScript test fixture necessary to prove that:

- Vitest discovers TypeScript tests
- The root test command executes successfully
- The Node environment is operational
- The configured isolation defaults do not prevent normal test execution

The fixture SHALL:

- Be trivial
- Be deterministic
- Avoid wall-clock access
- Avoid randomness
- Avoid network access
- Avoid environment secrets
- Avoid external services
- Avoid production behavior

The fixture SHALL NOT introduce:

- Domain models
- Runtime behavior
- Registry behavior
- Policy behavior
- API behavior
- Web behavior
- Edge behavior

Do not create production source code merely to provide something for the test to import.

## Constraints

### 1. Root-Owned Test Infrastructure

Vitest SHALL be configured as shared repository infrastructure at the root during M01.

Individual packages SHALL NOT receive independent Vitest configurations unless a demonstrated technical requirement makes one necessary.

No current repository requirement justifies package-specific Vitest configuration.

### 2. Root Configuration Shall Remain Orchestrational

The root configuration SHALL contain:

- Shared test discovery
- Shared environment defaults
- Shared isolation defaults
- Shared execution defaults
- Shared exclusions

It SHALL NOT contain:

- Application behavior
- Runtime behavior
- Domain-specific setup
- Worker-specific branching
- Package-specific conditional logic
- Environment-specific implementation logic

### 3. No Production Logic in the Root

The repository root SHALL contain tooling, configuration, and orchestration only.

Production behavior SHALL remain inside its constitutionally owned package or application.

### 4. Determinism

The test foundation SHALL support deterministic execution.

The configuration and initial fixture SHALL NOT require:

- Internet access
- External services
- Databases
- Cloud credentials
- Environment-specific secrets
- Machine-specific paths
- Wall-clock values
- Uncontrolled randomness

### 5. Static and Runtime Validation Shall Remain Separate

The validation authorities are:

| Validation Concern                         | Authoritative Mechanism |
| ------------------------------------------ | ----------------------- |
| Type correctness                           | `tsc -b`                |
| TypeScript project-reference graph         | `tsc -b`                |
| Static import and architectural boundaries | ESLint                  |
| Source formatting                          | Prettier                |
| Runtime behavior                           | Vitest                  |

Vitest SHALL NOT be configured to duplicate TypeScript project-reference validation or repository-wide static type checking.

### 6. Architectural Boundaries

Vitest configuration SHALL NOT weaken, bypass, or replace:

- TypeScript project-reference boundaries established by IT-0103
- ESLint architectural boundaries established by IT-0104
- Repository ownership and import rules defined by CAW-004

No boundary exceptions SHALL be added preemptively.

### 7. Minimal Configuration

Use the smallest stable configuration that satisfies this mandate.

Do not add:

- Plugins
- Custom reporters
- Global setup files
- Path aliases
- Transforms
- Framework adapters
- Browser environments
- Workspace-specific configuration

unless a demonstrated requirement of the current repository makes one necessary.

## Acceptance Criteria

The task is accepted only when all of the following are true:

1. Vitest is installed as a root workspace development dependency.

2. A root Vitest configuration exists and is committed.

3. The root configuration supports TypeScript test discovery under:

   ```text
   packages/**
   apps/**
   edge/**
   ```

4. The following test naming conventions are supported:

   ```text
   *.test.ts
   *.spec.ts
   ```

5. The default test environment is:

   ```text
   node
   ```

6. The configuration explicitly enables:

   ```text
   clearMocks: true
   mockReset: true
   restoreMocks: true
   ```

7. File-level parallel test execution is explicitly disabled.

8. `pnpm test` executes in non-watch mode and completes successfully.

9. At least one minimal TypeScript test is discovered and passes.

10. The test suite requires no:

- Network access
- External services
- Databases
- Cloud credentials
- Environment-specific secrets

1. A root coverage command exists and executes successfully.
2. No coverage threshold is introduced.
3. Vitest type-checking is not installed or configured.
4. `pnpm exec tsc -b` succeeds with zero errors.
5. `pnpm lint` succeeds with zero errors.
6. `pnpm format:check` succeeds with zero formatting issues.
7. No production Runtime, domain, registry, policy, API, web, or edge behavior is added.
8. No constitutional dependency boundary is weakened.
9. The root Vitest configuration remains minimal and does not contain speculative Worker or application-specific logic.

## Required Verification

The executing agent SHALL run and report the results of:

```bash
pnpm test
pnpm exec tsc -b
pnpm lint
pnpm format:check
```

And the configured coverage command.

The agent SHALL verify and report:

- Number of test files discovered
- Number of tests executed
- Number of tests passed
- Number of tests failed
- Whether tests ran in serial mode
- Whether the configured mock-isolation settings are active
- Whether the coverage command completed successfully

The final report SHALL include:

- Files created
- Files modified
- Dependencies added
- Package scripts added or changed
- Commands executed
- Pass/fail result for every command
- Number of tests discovered
- Number of tests passed
- Any deviations from this mandate
- Any assumptions made

## Definition of Done

AMS-0106 is complete only when:

- Vitest is installed and configured at the repository root.
- Repository-wide TypeScript test discovery is operational.
- The Node environment is the default test environment.
- Mock clearing, resetting, and restoration are explicitly enabled.
- File-level parallel execution is explicitly disabled.
- `pnpm test` passes in non-watch mode.
- At least one minimal TypeScript test is discovered and passes.
- The coverage command executes successfully.
- Vitest type-checking has not been added.
- `tsc -b` remains green.
- ESLint remains green.
- Prettier verification remains green.
- No production behavior has been introduced.
- No constitutional dependency boundary has been weakened.
- The root configuration remains minimal and orchestrational.
- All changes are committed in one focused implementation commit.
