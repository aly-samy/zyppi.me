# ZYPPI CONSTITUTIONAL COUNCIL

# G-0809 — Council Decision Record

**Gate:** G-0809 — Hash Domains **Program:** CAW-011 — Commerce Atlas Wedge **Milestone:** M08 — Runtime Verification Pipeline **Decision Status:** **RATIFIED** **Selected Direction:** **Direction A — JCS + SHA-256** **Decision Authority:** Zyppi Constitutional Council **Implementation Authority:** Consequence of ratification only; no independent semantic invention authorized **Date:** August 9, 2026

## 1. Constitutional Question

G-0809 determines:

**What exact canonical cryptographic construction governs the constitutional hash fields of the M08 execution receipt?**

The active `ExecutionReceipt` contract contains four cryptographic fields:

`inputHash · outputHash · evidenceHash · deterministicHash`

G-0804 expressly delegates their cryptographic construction to G-0809 and requires that `deterministicHash` not be interpreted as recursive self-hashing.

The M08 reconnaissance confirms that the current implementation has not yet constructed these fields; the existing values are presently placeholders. The current repository nevertheless already contains canonical serializers for several relevant domain objects.

G-0809 therefore establishes the **constitutional cryptographic semantics**, not the implementation mechanism.

# 2. Council Decision

The Council **RATIFIES Direction A — JCS + SHA-256.**

The constitutional hash system SHALL use:

1. **SHA-256** as the constitutional digest algorithm.

2. **UTF-8** as the byte encoding of canonical serialized material.

3. **JSON Canonicalization Scheme (JCS), RFC 8785**, as the authoritative canonicalization scheme.

4. Explicit **domain separation** between the four constitutional hash domains.

5. A strictly **non-circular** construction for `deterministicHash`.

6. Deterministic treatment of unordered semantic collections.

7. Explicit semantic treatment of absent and `null` values.

8. Hashing of **defined constitutional semantic material**, not implementation traces, storage artifacts, or incidental serialization state.

No second canonicalization regime is established.

No repository-specific serializer is constitutionally authoritative merely because it currently exists.

# 3. Direction Assessment

## Direction A — JCS + SHA-256

**DECISION: SELECTED AND RATIFIED**

JCS provides a published, language-independent canonical representation suitable for independent verification.

SHA-256 provides a single, established digest algorithm for M08.

This combination preserves the constitutional requirement that equivalent execution material produce reproducible cryptographic results independently of the implementation language or internal serializer implementation.

The repository's existing serializers may be used as implementation mechanisms only where they conform to the ratified constitutional representation.

They do not acquire independent constitutional authority.

## Direction B — Zyppi Canonical Serializer

**DECISION: REJECTED**

The Council rejects the proposition that internal repository serialization rules should themselves constitute the permanent cryptographic standard.

The current reconnaissance confirms that canonical serializers already exist, including serializers for `ExecutionRequest`, `ExecutionContext`, `EvidenceBundle`, `ExecutionReceipt`, and `Outcome`. However, the existence of those serializers is an implementation fact, not a constitutional requirement that the cryptographic system remain permanently coupled to them.

Internal serializers may therefore implement the constitutional rule but may not redefine it.

## Direction C — Hybrid Canonicalization

**DECISION: REJECTED**

The Council rejects multiple competing canonicalization regimes for constitutional hashing.

A hybrid system would introduce unnecessary questions concerning:

- which serializer governs which material;

- nested serializer boundaries;

- divergent null semantics;

- divergent ordering semantics;

- future interoperability;

- historical verification.

M08 requires one constitutional canonicalization authority.

That authority is JCS.

# 4. Constitutional Cryptographic Principle

The Council establishes:

**Cryptographic hashing binds constitutionally defined semantic material. It does not define the meaning of that material.**

Therefore:

`G-0809` may hash a field established by another gate, but it shall not redefine that field.

The semantic authorities remain separate:

- **G-0803** — `receiptId`

- **G-0814** — `executionId`

- **G-0815** — `policyVersion`

- **G-0816** — `decisionSummary`

- **G-0817** — Diagnostics

- **G-0801 / G-0802** — `executionTime`

- **G-0804** — receipt membership

G-0809 determines how those already-defined semantic artifacts participate in cryptographic binding.

# 5. Hash Algorithm

## D-0809-01 — SHA-256

**DECISION: RATIFIED**

All four constitutional digest fields SHALL use SHA-256:

`SHA-256`

No algorithm-selection mechanism or runtime-configurable cryptographic agility is introduced by M08.

A future change of constitutional digest algorithm requires an explicit constitutional decision.

The Runtime SHALL NOT select a digest algorithm dynamically.

# 6. Canonicalization Authority

## D-0809-02 — JCS

**DECISION: RATIFIED**

All material entering a constitutional hash domain SHALL be represented using the **JSON Canonicalization Scheme (JCS), RFC 8785**.

The canonical byte sequence SHALL then be encoded as UTF-8 before SHA-256 processing.

Conceptually:

`Digest = SHA-256(UTF-8(JCS(domainMaterial)))`

JCS is the constitutional authority.

Internal serializers are implementation mechanisms and must conform to the ratified representation.

The repository's current use of deterministic serializers does not alter this constitutional decision.

# 7. Domain Separation

## D-0809-03 — Independent Hash Domains

**DECISION: RATIFIED**

The four hash fields SHALL represent four distinct constitutional domains:

- `inputHash`

- `outputHash`

- `evidenceHash`

- `deterministicHash`

Material from one domain SHALL NOT be interpreted as material from another domain merely because its canonical representation happens to be identical.

Each domain SHALL therefore carry an explicit, stable domain identifier as part of its cryptographic preimage.

The exact implementation encoding of the domain identifier is an implementation consequence of this decision and SHALL conform to the canonical domain definition established by the applicable AMS.

The domain identifier SHALL be stable and deterministic.

# 8. `inputHash`

## D-0809-04 — Input Binding

`inputHash` SHALL cryptographically bind the constitutional execution input.

Its semantic material SHALL be the canonical `ExecutionRequest` established by the applicable execution-context and request authorities.

Conceptually:

`inputHash = SHA-256(UTF-8(JCS(InputDomain(ExecutionRequest))))`

The input domain SHALL contain the explicit execution material required to establish the execution boundary.

G-0809 does not independently add fields to `ExecutionRequest`.

In particular, G-0809 SHALL NOT invent:

- a second execution identifier;

- a second ACV identifier;

- a timestamp;

- a policy version;

- operational metadata.

Those belong to their respective semantic authorities.

# 9. ACV Treatment

## D-0809-05 — No Independent ACV Hash Required

The Council rejects unnecessary expansion of the hash architecture.

`ActiveConstitutionalView` does not receive a separate receipt-level cryptographic field merely because it participates in `inputHash`.

Where ACV is part of the constitutionally defined `ExecutionRequest`, its canonical representation is included as part of that request's canonical material.

Therefore:

`ExecutionRequest → inputHash`

is sufficient.

G-0809 does **not** establish:

`ACV → acvHash → inputHash`

as an additional constitutional chain.

If another gate requires an independently canonicalizable ACV representation, that requirement remains a domain-model/semantic requirement and does not create an additional M08 receipt hash.

This preserves the bounded receipt architecture established by G-0804.

# 10. `outputHash`

## D-0809-06 — Constitutional Output Binding

`outputHash` SHALL bind the constitutionally relevant execution result material produced by the Runtime.

The output hash SHALL NOT hash the `ExecutionReceipt` recursively or simply hash an implementation-specific object graph.

The semantic material eligible for the output domain consists of the constitutional execution-output components established by the upstream gates.

These may include, as governed by their respective semantic authorities:

- `Outcome`;

- `TrustResult`;

- `PolicyDecision[]`;

- `Diagnostics`;

- constitutionally relevant evidence references.

The output domain SHALL NOT independently redefine these structures.

The receipt itself is excluded from the output-domain material.

Thus:

`ExecutionOutput semantic material → outputHash`

and not:

`ExecutionReceipt → outputHash → ExecutionReceipt`

The precise field-level mapping SHALL follow the ratified upstream contracts and the implementation mandate.

# 11. `evidenceHash`

## D-0809-07 — Evidence Bundle Binding

`evidenceHash` SHALL cryptographically bind the constitutionally relevant `EvidenceBundle`.

Conceptually:

`evidenceHash = SHA-256(UTF-8(JCS(EvidenceDomain(EvidenceBundle))))`

The evidence hash represents the canonical evidence material.

It does not represent:

- database location;

- object-storage location;

- retrieval URL;

- persistence identifier;

- operational logging information.

The current repository already provides deterministic evidence serialization with lexicographic ordering by `evidenceId`. This implementation behavior is consistent with the constitutional determinism requirement, but the constitutional authority remains JCS.

# 12. Relationship Between `outputHash` and `evidenceHash`

## D-0809-08 — Independent Sibling Domains

`outputHash` and `evidenceHash` SHALL remain independent constitutional hash domains.

The Council does not establish a nested construction such as:

`outputHash = H(output + evidenceHash)`

unless a future constitutional decision explicitly requires such coupling.

The execution receipt provides the relationship between the two values.

This preserves an acyclic and inspectable cryptographic structure.

# 13. `deterministicHash`

## D-0809-09 — Non-Circular Receipt Binding

`deterministicHash` SHALL cryptographically bind the defined receipt material **excluding `deterministicHash` itself**.

Conceptually:

`deterministicHash = SHA-256(UTF-8(JCS(DeterministicReceiptDomain(receiptWithoutDeterministicHash))))`

The `deterministicHash` field SHALL NEVER occur in its own preimage.

This directly implements the anti-circularity requirement already established by G-0804.

The Council therefore rejects any construction equivalent to:

`deterministicHash = H(complete receipt containing deterministicHash)`

# 14. Receipt Material Participating in `deterministicHash`

The receipt surface established by G-0804 remains authoritative:

`receiptId` `executionId` `runtimeVersion` `inputHash` `outputHash` `evidenceHash` `policyVersion` `decisionSummary` `executionTime` `deterministicHash`

G-0809 establishes the following cryptographic rule:

**All semantically defined receipt fields participating in the deterministic receipt binding SHALL be included according to their ratified receipt semantics, except `deterministicHash` itself.**

The following are therefore conceptually within the deterministic-hash material:

- `receiptId`

- `executionId`

- `runtimeVersion`

- `inputHash`

- `outputHash`

- `evidenceHash`

- `policyVersion`

- `decisionSummary`

- `executionTime`

`deterministicHash` itself is excluded.

G-0809 does not redefine the semantics of any of these fields.

# 15. Identity Separation

## D-0809-10 — Hashing Does Not Create Identity

The Council explicitly rejects any interpretation under which hashing automatically becomes semantic identity.

Therefore:

`hash(material) ≠ identity(material)`

unless the governing gate explicitly establishes that relationship.

In particular:

- `inputHash` is not `executionId`;

- `outputHash` is not `receiptId`;

- `policyVersion` is not a cryptographic hash merely because it participates in a hash;

- `deterministicHash` is not the semantic identity of the receipt unless separately established by the appropriate authority.

This preserves the identity distinctions established by G-0814, G-0815, and G-0803.

# 16. Collection Ordering

## D-0809-11 — Deterministic Collection Representation

Where a constitutional collection is semantically unordered, its canonical representation SHALL NOT depend upon incidental insertion or traversal order.

The canonical representation SHALL therefore establish deterministic ordering using the stable semantic identity applicable to that collection.

Examples include:

- evidence records ordered by `evidenceId`;

- policy records ordered by `policyId`, where the collection is semantically unordered;

- other collections ordered according to their governing domain semantics.

Positionally meaningful arrays SHALL retain their semantic order.

G-0809 SHALL NOT arbitrarily reorder a collection whose order itself carries meaning.

This distinction preserves semantics while eliminating incidental serialization nondeterminism.

# 17. Object Key Ordering

## D-0809-12 — Canonical Object Representation

Object key ordering SHALL be governed by JCS.

The Runtime SHALL NOT rely on incidental JavaScript object insertion order as a constitutional serialization rule.

The reconnaissance specifically identifies default `JSON.stringify()` as a potential future determinism hazard if used without canonicalization.

Accordingly:

**`JSON.stringify()` is not itself a constitutional canonicalization authority.**

An implementation may use it internally only where the resulting representation is demonstrably compliant with the ratified JCS boundary.

# 18. Null and Absent Values

## D-0809-13 — Explicit Semantic Representation

The constitutional hash system SHALL preserve the semantic distinction between:

- an absent property; and

- an explicitly present `null` value,

where the governing domain permits both.

JCS SHALL serialize the resulting semantic object.

G-0809 does not globally redefine domain semantics by prohibiting `null`.

Instead, each domain contract determines whether `null` is semantically valid.

An implementation SHALL NOT silently convert:

`null → absent`

or:

`absent → null`

before canonicalization where that conversion changes domain meaning.

# 19. Empty Collections

## D-0809-14 — Empty Collection Preservation

An explicitly represented empty constitutional collection SHALL remain distinguishable from an absent collection where the domain semantics distinguish them.

For example:

`[]`

shall not be silently converted into:

`absent`

merely to shorten the hash material.

Canonicalization preserves the semantic representation supplied by the governing domain contract.

# 20. Nested Canonical Material

## D-0809-15 — Single Canonical Boundary

Nested constitutional objects SHALL participate in the enclosing JCS representation as part of the same canonical semantic structure.

G-0809 does not establish multiple competing nested serialization regimes.

The constitutional rule is:

**One hash domain → one semantic material structure → one JCS canonical representation → one SHA-256 digest.**

This is preferred over introducing independently hashed nested objects without a constitutional requirement.

# 21. Cryptographic Dependency Graph

The Council establishes the following conceptual dependency structure:
`ExecutionRequest       │       ▼   inputHash  EvidenceBundle       │       ▼  evidenceHash  Constitutional Execution Output       │       ▼   outputHash  Receipt semantic material       │       ├── inputHash       ├── outputHash       ├── evidenceHash       ├── receiptId       ├── executionId       ├── runtimeVersion       ├── policyVersion       ├── decisionSummary       └── executionTime               │               ▼       deterministicHash `
The dependency graph SHALL be acyclic.

No constitutional hash may depend directly or indirectly upon itself.

# 22. Replay Equivalence

## D-0809-16 — Cross-Implementation Determinism

For identical constitutionally defined semantic material, conforming implementations SHALL produce identical canonical bytes and therefore identical SHA-256 digests.

Conceptually:

`same semantic material + same JCS rules + same domain = same digest`

This requirement applies across:

- Runtime instances;

- machines;

- supported implementation languages;

- internal serializer implementations.

The constitutional hash therefore survives ordinary implementation refactoring.

# 23. Historical Verification

## D-0809-17 — Stable Constitutional Rules

Historical verification SHALL depend upon the ratified constitutional hash rules, not on the continued existence of a particular repository serializer implementation.

A future implementation may replace:

- TypeScript serializers;

- internal helper functions;

- object construction strategies;

- repository modules;

without changing historical cryptographic meaning, provided the implementation continues to conform to the applicable constitutional JCS and domain rules.

No separate implementation-serializer version becomes a required receipt field under G-0809.

If the constitutional cryptographic rules themselves are changed in the future, that change requires a separate constitutional decision and appropriate historical-version governance.

# 25. Rejected Over-Expansion

The Council explicitly rejects the following interpretations.

### R1 — Repository Serializer as Constitutional Authority

Rejected.

Internal serializers implement the constitutional rule; they do not define it.

### R2 — Hybrid Cryptographic Canonicalization

Rejected.

M08 uses one canonicalization authority.

### R3 — Standalone ACV Receipt Hash

Rejected.

ACV participation in `inputHash` does not require a new receipt field or intermediate constitutional digest.

### R4 — Trace Digest

Rejected.

Operational traces are outside the Runtime's constitutional hash material unless a future gate explicitly establishes otherwise.

### R5 — Runtime-Generated Trace Commitment

Rejected.

G-0809 does not authorize the Runtime to observe, store, or hash operational telemetry.

### R6 — Recursive Receipt Hashing

Rejected.

`deterministicHash` SHALL NOT appear in its own preimage.

### R7 — Hash-As-Identity

Rejected.

Cryptographic binding and semantic identity remain distinct.

### R8 — Algorithm Agility in M08

Rejected.

No runtime-selectable cryptographic algorithm mechanism is introduced.

### R9 — Arbitrary Collection Reordering

Rejected.

Only semantically unordered collections may be canonically reordered.

### R10 — Global Null Erasure

Rejected.

G-0809 does not silently convert semantic values merely to simplify serialization.
