# G-0802 — Council Decision Record

## `ExecutionReceipt.executionTime` Semantics

**Milestone:** M08 — Runtime Closure **Gate:** G-0802 **Question:** What does `ExecutionReceipt.executionTime` represent? **Status:** **CLOSED — WITH FOLLOW-UP AMENDMENTS** **Decision:** **Direction D — Remove or Replace the Field** **Effective:** Upon Council ratification of this record **Implementation Authority:** None granted by this record

# 1. Executive Decision

The Zyppi Constitutional Council resolves that the existing field:
`executionTime: number `
**shall not remain as a constitutional receipt field under its present name or semantics.**

The term `executionTime` is insufficiently precise because it permits two materially different interpretations:

1. the temporal coordinate under which constitutional evaluation occurred; or

2. the elapsed duration consumed by execution.

These concepts are constitutionally distinct and shall not share one field.

The Council therefore selects **Direction D — Remove or Replace the Field**.

The constitutional receipt shall carry an explicitly named **evaluation temporal coordinate**, whose exact semantic model and representation are inherited from the authoritative G-0801 decision.

The Council does **not**, through G-0802, independently prescribe that this coordinate must be an ISO timestamp, Unix timestamp, logical sequence, or any other representation.

That determination belongs to G-0801.

# 2. Constitutional Problem

The existing repository contract defines:
`readonly executionTime: number; `
The current M08-GDR identifies four possible interpretations:

- Direction A — Constitutional Execution Timestamp

- Direction B — Deterministic Logical Execution Time

- Direction C — Elapsed Duration

- Direction D — Remove or Replace the Field

The Council finds that the ambiguity is not merely naming-related.

A temporal coordinate answers:

**Under what temporal state was constitutional evaluation performed?**

An elapsed duration answers:

**How much operational time did computation consume?**

These are different semantic dimensions.

A single field cannot constitutionally represent both.

# 3. Selected Direction

## Direction D — Remove or Replace the Field

The existing `executionTime` field is replaced by a semantically explicit field representing the **temporal coordinate of constitutional evaluation**.

For purposes of this decision, the semantic concept is designated:
`evaluationCoordinate `
The exact representation of `evaluationCoordinate` SHALL be inherited from the final G-0801 temporal model.

### Important limitation

G-0802 does **not** decide that `evaluationCoordinate` must be:

- an ISO-8601 timestamp;

- an RFC 3339 value;

- an epoch number;

- a nanosecond integer;

- a logical sequence;

- or any other specific encoding.

Those are representation questions dependent upon the temporal model established by G-0801.

This prevents G-0802 from silently deciding G-0801 by implementation choice.

# 4. Rejected Directions

## Direction A — Preserve `executionTime` as Constitutional Execution Timestamp

**Rejected as the final contract form.**

The underlying semantic concept is valid: a receipt should be capable of recording the temporal coordinate under which constitutional evaluation occurred.

However, retaining the name `executionTime` creates an avoidable semantic ambiguity between:

- an instant/coordinate; and

- elapsed execution duration.

The Council therefore rejects the existing field name while preserving the valid underlying concept.

## Direction B — Deterministic Logical Execution Time

**Rejected as an independent G-0802 model.**

Introducing a new logical clock or execution-time system would create a second temporal model alongside G-0801.

G-0802 must consume the temporal semantics established by G-0801 rather than create a competing temporal ontology.

If G-0801 ultimately determines that the constitutional temporal coordinate is represented through a logical mechanism, `evaluationCoordinate` may carry that representation. G-0802 itself does not invent it.

## Direction C — Elapsed Duration

**Rejected as constitutional receipt semantics.**

Execution duration is operational information.

It depends upon implementation environment, processor speed, scheduling, infrastructure load, and other operational conditions. Treating such a measurement as constitutional execution material would conflict with the deterministic Runtime model.

The Runtime must therefore not generate a constitutional receipt value whose meaning is:

"How long this computation physically took."

If operational duration is required later, it shall be represented separately and classified as operational metadata.

It shall not silently become part of constitutional replay identity.

# 5. Formal Semantic Definition

The Council establishes the following definition:

**`evaluationCoordinate` is the explicit temporal coordinate associated with the constitutional evaluation represented by an ExecutionReceipt.**

It records **which temporal state governed the evaluation**, not how long the Runtime took to execute.

The value:

- is not obtained from an ambient system clock by the Runtime;

- is not an execution-duration measurement;

- is not independently generated by the receipt;

- is not a second temporal authority;

- must correspond to the temporal model established by G-0801.

The receipt therefore preserves the temporal context of the constitutional evaluation without creating a second source of temporal truth.

# 6. Relationship to G-0801

G-0801 is the semantic authority for the meaning of constitutional time.

G-0802 is subordinate to that decision.

The dependency is:
`G-0801 Temporal Semantics       │       ▼ Defines the constitutional temporal model       │       ▼ G-0802 Receipt representation of that temporal coordinate `
Therefore:

**G-0802 SHALL NOT redefine the temporal model established by G-0801.**

If G-0801 establishes an explicit timestamp, `evaluationCoordinate` shall carry that timestamp.

If G-0801 establishes another deterministic temporal coordinate, `evaluationCoordinate` shall carry that coordinate instead.

This is the principal amendment to the earlier Gemini recommendation.

# 7. Input / Receipt Relationship

The receipt's `evaluationCoordinate` is not an independently generated temporal fact.

It is a receipt representation of the temporal coordinate actually used by the execution.

Conceptually:
`Execution Admission        │        ▼ Explicit Constitutional Temporal Coordinate        │        ▼ Constitutional Evaluation        │        ▼ ExecutionReceipt.evaluationCoordinate `
The receipt therefore provides an independently inspectable statement of the temporal context used by the execution.

The receipt must not contain a second, independently generated "receipt time" that could diverge from the execution's governing temporal coordinate.

# 8. Determinism and Replay

For executions having identical constitutional inputs and identical authorized context:
`evaluationCoordinate₁ ≡ evaluationCoordinate₂ `
The receipt value must therefore be replay-stable.

The Runtime SHALL NOT obtain the value by calling:
`Date.now() new Date() performance.now() system clock `
or any equivalent ambient temporal source.

The M08 constitutional framework already establishes Runtime purity and deterministic execution as invariants.

# 9. Execution Duration

The Council explicitly separates:

### Constitutional temporal coordinate

`evaluationCoordinate `
Meaning:

The temporal coordinate under which constitutional evaluation occurred.

### Operational execution duration

Potential future operational metadata such as:
`executionDuration `
Meaning:

The measured computational duration of the execution.

These values SHALL NOT be conflated.

If execution-duration telemetry is subsequently required, its semantics, representation, and lifecycle must be governed separately.

It is not part of this gate.

# 10. Type and Representation

The current:
`executionTime: number `
is therefore deprecated.

The replacement contract shall use a dedicated semantically named field:
`evaluationCoordinate `
Its concrete TypeScript type SHALL be determined by the final G-0801 temporal representation.

G-0802 deliberately does not prescribe a primitive type.

This prevents the contract from encoding an unresolved temporal decision.

# 11. Hash-Domain Consequence

The Council determines that `evaluationCoordinate` is **constitutional execution material** because it identifies the temporal context under which constitutional evaluation occurred.

Accordingly, its potential participation in constitutional cryptographic domains SHALL be handed to G-0809.

G-0802 does **not** determine:

- the exact hash domain;

- canonical serialization;

- field ordering;

- encoding;

- digest construction.

Those remain G-0809 responsibilities.

The semantic hand-off is:

If a hash domain represents the constitutional execution state, the temporal evaluation coordinate must not be silently excluded from that state merely because the field is located on the receipt.

# 12. Receipt Self-Containment

The receipt must preserve sufficient information to establish the temporal context of the represented execution without requiring an auditor to infer that context from an unrelated operational clock.

This supports the existing architectural principle that the receipt is a proof-bearing execution artifact rather than merely an operational log.

The receipt serializer already contains `executionTime` among its canonical fields, confirming that the field is part of the existing receipt surface requiring semantic resolution.

The replacement therefore constitutes a semantic contract amendment, not an incidental implementation rename.

# 13. Boundary With G-0801

G-0802 accepts the following as binding:

1. Constitutional time must be explicit rather than ambient.

2. The receipt must not manufacture a competing temporal value.

3. Replay must preserve the temporal coordinate.

4. The exact temporal representation belongs to G-0801.

G-0802 does **not** decide:

- how temporal validity is evaluated;

- how historical constitutional state is selected;

- whether the temporal coordinate is a timestamp or another model;

- its precision;

- its encoding.

Those questions remain outside this gate.

# 14. Boundary With G-0809

G-0809 owns:

- canonical serialization;

- hash-domain membership;

- byte-level representation;

- deterministic digest construction.

G-0802 supplies only the semantic fact:

`evaluationCoordinate` represents constitutional temporal evaluation state.

G-0809 shall determine how that fact participates in each applicable hash domain.

The existing M08 dependency framework explicitly places hash-domain construction downstream of receipt semantic resolution.

# 15. Boundary With G-0804

G-0804 remains responsible for the final constitutional receipt field set.

G-0802 therefore establishes the semantic disposition of the existing field but does not independently finalize the entire receipt schema.

G-0804 shall reconcile:
`executionTime `
with:
`evaluationCoordinate `
and incorporate the resulting field into the final receipt contract.

# 16. Boundary With G-0813

G-0813 governs execution budget and resource-consumption semantics.

It does not inherit responsibility for temporal semantics merely because execution duration is operationally measurable.

The Council therefore rejects the proposal that G-0804 or G-0813 should absorb a constitutional meaning of "elapsed execution time."

If resource consumption requires time-based measurement, that is a separate operational resource concept.

It must not be confused with the constitutional evaluation coordinate.

# 18. Required Contract Amendments

The following amendments are required:

1. Deprecate `ExecutionReceipt.executionTime`.

2. Introduce the semantically precise `evaluationCoordinate`.

3. Bind `evaluationCoordinate` to the temporal coordinate defined by G-0801.

4. Do not independently select its primitive type before G-0801's representation is authoritative.

5. Remove any interpretation of `executionTime` as elapsed duration from constitutional receipt semantics.

6. Update the canonical receipt serializer accordingly.

7. Update affected tests and contract references after the semantic contract is amended.

8. G-0804 shall incorporate the field into the final receipt-field decision.

9. G-0809 shall determine its precise cryptographic participation.

No implementation of these amendments is authorized merely by this decision record.

# 19. Accepted Costs and Risks

The Council accepts:

- a breaking semantic change to the existing receipt contract;

- downstream serializer and test reconciliation;

- coordination with G-0801;

- additional explicit distinction between constitutional and operational time.

These costs are accepted because retaining an ambiguous field would create a more serious long-term constitutional risk.

The Council specifically rejects optimizing for short-term contract stability at the expense of semantic precision.

# 20. Primary Advantages

The selected direction:

1. eliminates ambiguity between temporal coordinate and duration;

2. prevents G-0802 from creating a second temporal model;

3. preserves deterministic replay;

4. maintains Runtime purity;

5. allows the receipt to preserve its constitutional temporal context;

6. keeps temporal representation under G-0801;

7. keeps cryptographic construction under G-0809;

8. preserves clean separation between constitutional and operational concerns.

# 21. Cross-Gate Consequences

### G-0801 — Temporal Semantics

Must define the temporal model consumed by `evaluationCoordinate`.

### G-0804 — Final Receipt Field Set

**Downstream reconciliation.**

### G-0809 — Hash Domains

**Cryptographic hand-off.**

### G-0813 — Execution Budget

**No semantic absorption.**

Must not use `executionTime` as an implicit budget or duration mechanism.

### G-0815 / G-0816 / G-0817

May depend on the finalized receipt schema but receive no semantic authority from G-0802.

# 22. Closure Conditions

G-0802 is considered semantically resolved by this record.

The following follow-up amendments remain mandatory:

1. G-0801 must establish the authoritative temporal model.

2. The receipt contract must replace `executionTime` with `evaluationCoordinate`.

3. G-0804 must reconcile the final receipt field set.

4. G-0809 must determine cryptographic participation.

5. The serializer and affected tests must subsequently be aligned with the ratified contract.

These are **follow-up implementation/document amendments**, not grounds for reopening the semantic decision unless G-0801 establishes a temporal model fundamentally incompatible with the `evaluationCoordinate` abstraction.

# 23. Final Council Resolution

The Zyppi Constitutional Council resolves:

**`ExecutionReceipt.executionTime` shall cease to be a constitutional field because its terminology permits an unacceptable conflation of temporal coordinate and execution duration.**

**The receipt shall instead carry `evaluationCoordinate`, representing the temporal coordinate under which constitutional evaluation occurred.**

**G-0802 shall not prescribe the underlying temporal model or representation; those remain governed by G-0801.**

**Elapsed execution duration, if required, shall remain a separate operational concern and shall not become constitutional execution material by implication.**

This decision preserves the critical architectural distinction:
`WHEN WAS THE CONSTITUTIONAL STATE EVALUATED?                     ≠ HOW LONG DID THE MACHINE TAKE? `
The first is constitutional.

The second is operational.

They shall never share one semantic field.

**G-0802 — CLOSED WITH FOLLOW-UP AMENDMENTS.**

**No implementation authority is granted or implied by this decision.**
