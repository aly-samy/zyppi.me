# 2. Constitutional Purpose

## 2.1 Objective

AMS-0108 SHALL establish Zyppi’s first Runtime-specific constitutional verifier.

The validator SHALL operate as a fail-closed, AST-backed structural purity gate that enforces Runtime constraints which are mechanically knowable through repository and source-code analysis.

The validator SHALL produce explicit, inspectable evidence that the current `packages/runtime` implementation satisfies the bounded structural rules defined by this mandate.

## 2.2 Constitutional Role

This validator is a constitutional CI gate. It is not a general-purpose developer linting tool and SHALL NOT replace ESLint.

The separation of responsibility SHALL remain explicit:

- **ESLint** provides broad developer-facing code-quality and architectural feedback.
- **AMS-0108** provides a dedicated Runtime-specific constitutional verification gate.
- **TypeScript project references** enforce compile-time dependency structure.
- **Future Runtime capability controls** SHALL enforce execution-time restrictions and complete sandbox behavior.

AMS-0108 SHALL NOT duplicate general linting policy merely because a rule can also be represented in ESLint.

## 2.3 Bounded Scope

AMS-0108 SHALL enforce only the structural purity and static determinism properties explicitly defined in this mandate.

Passing AMS-0108 SHALL NOT be interpreted as proof of complete Runtime determinism.

Passing AMS-0108 SHALL NOT imply that all sources of entropy, host access, side effects, dynamic code loading, or execution-time capability leakage have been eliminated.

Complete deterministic execution and execution-time capability enforcement remain responsibilities of future Runtime and sandbox layers.

# 3. Scope

## 3.1 In Scope

The implementation SHALL include:

1. A repository-owned Runtime purity validator.
2. Manifest validation for `packages/runtime/package.json`.
3. TypeScript Compiler API parsing and AST traversal.
4. Runtime source-file discovery and analysis.
5. Internal workspace import governance.
6. External production dependency allow-list enforcement.
7. Static detection of the explicitly prohibited deterministic violations.
8. Permanent validator fixtures and automated validator tests.
9. A repository-owned `pnpm runtime:purity` command.
10. Integration of the command into GitHub Actions CI.
11. Clear, deterministic failure output.
12. A documented limitation statement regarding the boundary of static analysis.

## 3.2 Out of Scope

The implementation SHALL NOT introduce:

- A Runtime sandbox.
- Runtime global-object shadowing.
- Runtime freezing or replacement of `Math`, `Date`, `process`, or other host objects.
- Execution-time capability enforcement.
- Cloudflare Worker behavior.
- Application behavior.
- API behavior.
- Web behavior.
- Edge behavior.
- Registry behavior.
- Policy evaluation logic.
- Runtime execution logic.
- Production domain models.
- Coverage thresholds.
- New constitutional dependencies.
- A new monorepo framework.
- Nx or another workspace dependency-graph platform.
- A bespoke JavaScript or TypeScript parser.
- Regex- or string-search-based source analysis as the authority for validation.

# 4. Validator Architecture

## 4.1 Validator Location

The validator SHALL be implemented as a dedicated repository-owned tool.

Preferred location:

```text
tools/validate-runtime-purity.mjs
```

A TypeScript implementation MAY be used if it can be executed through the existing repository toolchain without introducing unnecessary execution infrastructure.

The implementation SHALL remain small, explicit, and narrowly scoped.

## 4.2 Parsing Authority

The validator SHALL use the installed TypeScript Compiler API as the authoritative mechanism for:

- Parsing TypeScript source files.
- Traversing source-file ASTs.
- Inspecting import declarations.
- Inspecting import expressions where supported by the implemented AST rules.
- Detecting the explicitly prohibited direct expressions defined by this mandate.
- Reporting source locations for violations.

The validator SHALL NOT use:

- Regular expressions as the authority for source analysis.
- Raw text searching as the authority for source analysis.
- Hand-written syntax parsing.
- Tokenization implemented outside the TypeScript Compiler API.
- Heuristic string matching as a substitute for AST analysis.

String comparison MAY be used after AST nodes have been structurally identified, such as comparing an already-resolved module-specifier value against an approved policy entry.

## 4.3 Deterministic Analysis

Given the same:

- Repository source tree;
- Runtime manifest;
- Validator version;
- Validator policy configuration;

the validator SHALL produce the same pass/fail result and equivalent violation classifications.

The validator SHALL NOT depend on:

- Wall-clock time.
- Current date.
- Random values.
- Network access.
- External services.
- Environment-specific repository state.
- Non-deterministic file ordering.

Source files SHALL be processed in a stable, deterministic order.

# 5. Runtime Manifest Policy

## 5.1 Constitutional Default Denial

The Runtime production manifest SHALL operate under Default Denial.

For `packages/runtime/package.json`:

- `dependencies` SHALL default to denied.
- `peerDependencies` SHALL default to denied.
- Any package not explicitly authorized by the validator policy SHALL cause validation failure.

The absence of a package from the allow-list SHALL be interpreted as denial.

The validator SHALL NOT infer permission from:

- Package popularity.
- Package type.
- Package naming.
- Existing installation in the lockfile.
- Existing use elsewhere in the repository.
- A package being described as “utility,” “pure,” or “lightweight.”

## 5.2 Initial External Production Allow-List

The initial external production dependency allow-list SHALL be empty unless the current repository already contains a separately approved and constitutionally justified pure dependency.

The implementation agent SHALL NOT add an approved external package merely to demonstrate allow-list functionality.

If the Runtime package currently has no production dependencies, the validator SHALL confirm that the manifest satisfies the empty allow-list policy.

## 5.3 Dependencies

If `packages/runtime/package.json` declares a production dependency:

1. The validator SHALL read the dependency name.
2. The validator SHALL compare it against the explicit external production allow-list.
3. The validator SHALL fail if the dependency is not explicitly authorized.
4. The failure output SHALL identify:
   - The manifest path;
   - The dependency category;
   - The dependency name;
   - The reason for rejection.

## 5.4 Peer Dependencies

If `packages/runtime/package.json` declares a peer dependency:

1. The validator SHALL read the peer dependency name.
2. The validator SHALL compare it against the explicit peer dependency allow-list.
3. The validator SHALL fail if the peer dependency is not explicitly authorized.
4. The initial peer dependency allow-list SHALL be empty unless an existing constitutional authority explicitly requires otherwise.

## 5.5 Development Dependencies

`devDependencies` SHALL NOT be treated as Runtime production authority.

The validator MAY report Runtime development dependencies for diagnostic purposes, but SHALL NOT fail solely because a development dependency is absent from the production allow-list.

This exception SHALL NOT authorize a development dependency to be imported by Runtime production source code.

Production source imports remain subject to the source-level import governance defined below.

# 6. Runtime Import Governance

## 6.1 Internal and External Imports

The validator SHALL distinguish between:

1. Approved internal workspace imports;
2. Denied internal workspace imports;
3. External package imports;
4. Relative imports;
5. Host or platform module imports.

The validator SHALL evaluate imports using explicit policy categories rather than a single mixed deny-list.

## 6.2 Initial Allowed Internal Imports

Subject to reconciliation with the current repository architecture, the initial allowed internal Runtime imports are:

```text
@zyppi/domain
@zyppi/shared
```

These entries represent explicit constitutional permission, not inferred permission.

## 6.3 Initial Denied Internal Imports

The following SHALL be denied unless an existing constitutional authority explicitly establishes a different dependency relationship:

```text
@zyppi/contracts
@zyppi/testing
```

The validator SHALL also reject:

- All other `@zyppi/*` packages not explicitly allowed;
- Imports into any `apps/*` source;
- Imports into any `edge/*` source;
- Direct references to application or edge source trees;
- Relative imports that escape the Runtime package boundary.

## 6.4 Required Architectural Reconciliation

Before implementing the final internal import policy, the agent SHALL inspect:

- `CAW-004`;
- The current TypeScript project-reference graph;
- The current workspace package names;
- The current Runtime package manifest;
- The current Runtime source imports.

The agent SHALL determine whether the initial policy above matches the repository’s existing constitutional dependency authority.

If a conflict exists, the agent SHALL:

1. Stop before silently changing the architecture.
2. Report the exact conflict.
3. Identify the conflicting source documents or project references.
4. Explain the implementation impact.
5. Request a constitutional decision if the conflict cannot be resolved from existing repository authority.

The agent SHALL NOT modify CAW-004, TypeScript project references, package relationships, or Runtime architecture merely to make AMS-0108 pass.

## 6.5 Relative Import Boundaries

Relative imports SHALL be permitted only when they remain inside the Runtime package boundary.

The validator SHALL reject any relative import that resolves outside:

```text
packages/runtime/
```

The validator SHALL use normalized, resolved filesystem paths for this determination.

The validator SHALL NOT rely solely on counting `../` segments.

## 6.6 External Source Imports

Any external package imported by Runtime production source SHALL be subject to the external production allow-list.

An external import SHALL fail when:

- The package is not explicitly approved;
- The package is approved in the manifest but not approved for source import;
- The package is not declared according to the repository’s dependency policy;
- The package resolves to a prohibited host, platform, or I/O capability.

The implementation SHALL not create a broad external package allow-list.

# 7. Static Runtime Determinism Policy

## 7.1 Layer 1 Static Guardrails

The validator SHALL enforce the following direct, statically identifiable prohibitions through TypeScript AST analysis.

The validator SHALL reject:

```ts
Math.random();
Date.now();
new Date();
```

The validator SHALL report:

- The source-file path;
- The line number;
- The column number where available;
- The violation classification;
- A concise explanation.

## 7.2 Direct-Usage Boundary

The initial implementation SHALL detect the direct AST forms explicitly defined by this mandate.

The validator is not required in AMS-0108 to prove detection of every indirect or aliased equivalent, including examples such as:

```ts
const clock = Date;
clock.now();
```

or:

```ts
const random = Math.random;
random();
```

The validator SHALL NOT claim that direct AST checks detect all possible entropy or time access.

## 7.3 Host and Platform Imports

The validator SHALL reject direct imports of prohibited host-I/O or platform modules where they are statically identifiable through the implemented AST policy.

The exact prohibited module policy SHALL be explicit and repository-owned.

The agent SHALL derive the initial module policy from the constitutional Runtime purity requirements and the current repository architecture. It SHALL NOT silently add broad or speculative restrictions unrelated to existing authority.

At minimum, the implementation SHALL evaluate whether direct imports representing the following capability categories are prohibited:

- Filesystem access;
- Network and HTTP access;
- Process or child-process execution;
- Operating-system access;
- Database access;
- Cloud-provider execution or infrastructure SDKs;
- Platform-specific Worker or application execution APIs.

The validator SHALL distinguish between:

- A module that is explicitly prohibited;
- A module that is not authorized;
- A module that cannot be classified under the current policy.

Unknown external production imports SHALL fail under Default Denial.

## 7.4 Required Limitation Statement

The validator’s successful output SHALL include the following statement verbatim:

> Static analysis detects only the prohibited constructs represented by the implemented AST rules. Passing AMS-0108 does not prove complete runtime determinism and does not replace future runtime capability control or sandbox-level enforcement.

This statement SHALL be displayed only after all validation checks pass.

A failure result SHALL prioritize the actionable violations and SHALL NOT obscure them with a misleading success-oriented disclaimer.

# 8. Validator Output and Failure Behavior

## 8.1 Fail-Closed Behavior

Any constitutional violation detected by the validator SHALL produce:

- A non-zero process exit code;
- Clear failure output;
- A deterministic violation classification;
- Enough source or manifest information to identify the violation.

The validator SHALL NOT:

- Continue with a successful exit code after finding violations;
- Convert violations into warnings;
- Suppress violations through environment variables;
- Provide a permissive mode;
- Provide a “best effort” success mode;
- Automatically modify source files or manifests;
- Automatically add dependencies to an allow-list.

## 8.2 Output Requirements

Each violation SHALL include, where applicable:

```text
[VIOLATION_CODE] path:line:column
Rule: <constitutional rule or validator rule>
Reason: <why the construct is prohibited>
```

Example structure:

```text
[RUNTIME_NONDETERMINISM] packages/runtime/src/example.ts:12:3
Rule: Direct entropy access is prohibited
Reason: Math.random() is not permitted in Runtime production source.
```

The exact violation-code names MAY be finalized during implementation, but they SHALL be stable, explicit, and suitable for automated verification.

## 8.3 Successful Output

A successful validation result SHALL provide a concise summary of:

- Runtime manifest validation status;
- Runtime source-file count analyzed;
- Import governance status;
- Static determinism status;
- Overall pass result;
- The required static-analysis limitation statement.

The output SHALL NOT include unnecessary verbose repository dumps.

# 9. Permanent Validator Verification

## 9.1 Verification Principle

AMS-0108 SHALL include permanent automated verification proving that the validator:

- Rejects prohibited conditions;
- Accepts valid conditions;
- Produces the expected violation classifications.

Manual temporary edits SHALL NOT be the sole evidence that the validator works.

## 9.2 Fixture Location

Validator fixtures SHALL be isolated from production Runtime source.

Recommended structure:

```text
tools/
  validate-runtime-purity.mjs
  runtime-purity/
    fixtures/
      valid/
      invalid/
    validate-runtime-purity.test.ts
```

An equivalent structure MAY be used if it is consistent with the repository’s existing testing organization.

The fixture directory SHALL make it clear that invalid source files are intentional test artifacts.

Invalid fixtures SHALL NOT be placed in:

```text
packages/runtime/src/
```

## 9.3 Required Negative Fixtures

The automated validator tests SHALL include isolated fixtures representing at least:

1. An unapproved external production dependency.
2. A prohibited internal package import.
3. An import into an `apps/*` source tree.
4. An import into an `edge/*` source tree.
5. A relative import that escapes `packages/runtime`.
6. A direct `Math.random()` call.
7. A direct `Date.now()` call.
8. A direct `new Date()` expression.
9. A prohibited direct host or platform module import, if represented by the finalized policy.

Each fixture SHALL assert that validation fails for the correct rule or violation classification.

## 9.4 Required Valid Fixture

The automated validator tests SHALL include at least one valid pure Runtime fixture.

The valid fixture SHALL:

- Use only permitted imports;
- Avoid prohibited host access;
- Avoid prohibited entropy access;
- Avoid prohibited wall-clock access;
- Remain inside the Runtime package boundary.

The test SHALL assert successful validation.

## 9.5 Fixture Isolation

The fixture tests SHALL NOT require:

- Network access;
- External services;
- Real databases;
- Cloud credentials;
- Application execution;
- Edge execution;
- Runtime sandbox implementation.

The fixture suite SHALL remain deterministic and local.

# 10. Repository Command

## 10.1 Required Command

The root `package.json` SHALL include:

```json
{
  "scripts": {
    "runtime:purity": "<validator command>"
  }
}
```

The exact command MAY differ based on the final implementation language.

The command SHALL:

- Execute the Runtime purity validator;
- Return a non-zero exit code on any violation;
- Return zero only when all required checks pass;
- Require no network access;
- Require no interactive input.

## 10.2 Command Authority

`pnpm runtime:purity` SHALL be the canonical repository command for this constitutional gate.

The CI workflow SHALL invoke the repository-owned command rather than duplicating validator logic inside YAML.

The GitHub Actions workflow SHALL remain a thin executor of repository-owned commands.

# 11. Continuous Integration Integration

## 11.1 Required CI Placement

The GitHub Actions CI workflow SHALL execute:

```text
pnpm runtime:purity
```

after the TypeScript project build and before the test suite.

The required validation sequence SHALL be:

```text
Install dependencies
→ Check formatting
→ Run ESLint
→ TypeScript project build
→ Run Runtime purity validation
→ Run tests
```

## 11.2 Strict Failure

The Runtime purity step SHALL fail the workflow when the validator exits non-zero.

The workflow SHALL NOT contain:

```text
continue-on-error
|| true
```

or any equivalent:

- Failure masking;
- Conditional suppression;
- Ignored exit status;
- Non-blocking constitutional validation;
- Alternate permissive execution path.

## 11.3 No CI Logic Duplication

The workflow SHALL NOT duplicate:

- Dependency allow-lists;
- Import allow-lists;
- Prohibited module lists;
- AST rules;
- Runtime purity logic.

All Runtime purity policy and validation logic SHALL remain repository-owned and executed through `pnpm runtime:purity`.

# 14. Acceptance Criteria

AMS-0108 SHALL be considered complete only when all of the following are true:

## Validator Architecture

- A dedicated repository-owned Runtime purity validator exists.
- The validator uses the TypeScript Compiler API for source parsing and AST traversal.
- The validator does not use regexes, raw text searching, or bespoke parsing as the authority for source analysis.
- Source processing is deterministic.
- The validator requires no network access.

## Manifest Governance

- Runtime `dependencies` are governed by explicit Default Denial.
- Runtime `peerDependencies` are governed by explicit Default Denial.
- The initial external production dependency allow-list is empty unless an existing approved dependency is documented.
- The validator does not invent approved dependencies.
- Unauthorized Runtime production dependencies fail validation.
- Unauthorized Runtime peer dependencies fail validation.

## Import Governance

- Internal workspace imports are governed by an explicit allow-list.
- The final internal import policy has been reconciled with CAW-004 and the TypeScript project-reference graph.
- Any unresolved architectural conflict is reported rather than silently changed.
- Unauthorized `@zyppi/*` imports fail validation.
- Imports into `apps/*` fail validation.
- Imports into `edge/*` fail validation.
- Relative imports escaping `packages/runtime` fail validation.
- Unauthorized external production imports fail validation.

## Static Determinism

- Direct `Math.random()` usage is detected and rejected.
- Direct `Date.now()` usage is detected and rejected.
- Direct `new Date()` usage is detected and rejected.
- The implemented direct host or platform import policy is enforced.
- Violations include source location and rule classification.
- Successful output includes the required static-analysis limitation statement verbatim.
- The validator does not claim to prove complete Runtime determinism.

## Permanent Verification

- Permanent validator tests exist.
- Invalid fixtures are isolated from production Runtime source.
- An unapproved external dependency fixture fails correctly.
- A prohibited internal import fixture fails correctly.
- An application import fixture fails correctly.
- An edge import fixture fails correctly.
- An escaping relative import fixture fails correctly.
- A `Math.random()` fixture fails correctly.
- A `Date.now()` fixture fails correctly.
- A `new Date()` fixture fails correctly.
- A valid pure Runtime fixture passes.
- Fixture verification is automated.

## Repository and CI Integration

- Root `package.json` exposes `pnpm runtime:purity`.
- `pnpm runtime:purity` fails closed.
- GitHub Actions invokes `pnpm runtime:purity`.
- Runtime purity validation runs after TypeScript build and before tests.
- The CI workflow contains no failure masking.
- Runtime purity policy is not duplicated inside GitHub Actions YAML.
- The CI workflow remains a thin executor of repository-owned commands.

## Regression Safety

- `pnpm install --frozen-lockfile` succeeds.
- `pnpm format:check` succeeds.
- `pnpm lint` succeeds.
- `pnpm exec tsc -b` succeeds.
- `pnpm runtime:purity` succeeds against the production Runtime package.
- The validator test suite succeeds.
- `pnpm test` succeeds.
- No application, API, web, edge, registry, policy, or Runtime execution behavior is introduced.
- No constitutional boundary is weakened.
- No unrelated architectural change is introduced.

# 15. Definition of Done

AMS-0108 is complete only when:

1. The Runtime package is protected by a fail-closed, AST-backed constitutional purity validator.
2. Runtime production dependencies and peer dependencies are governed by explicit Default Denial.
3. Runtime internal imports are governed by explicit constitutional authority.
4. The validator detects the required direct static entropy and wall-clock constructs.
5. Permanent automated fixtures prove both rejection and acceptance behavior.
6. The validator is exposed through `pnpm runtime:purity`.
7. The validator is a mandatory GitHub Actions CI gate.
8. All existing repository verification commands remain green.
9. The implementation does not claim to prove complete Runtime determinism.
10. No Runtime sandbox or execution-time capability system is prematurely introduced.

# 16. Final Constitutional Boundary

AMS-0108 establishes **Layer 1: static repository enforcement**.

It does not establish **Layer 2: runtime capability enforcement**.

The constitutional boundary SHALL remain explicit:

> AMS-0108 mechanically enforces repository-visible Runtime purity constraints. Complete deterministic execution requires future Runtime-level capability controls and sandbox enforcement.

The successful completion of AMS-0108 SHALL therefore be interpreted as evidence that the current Runtime source and manifest satisfy the bounded structural rules implemented by this validator—not as proof that the complete Runtime execution environment is deterministic or fully sandboxed.
