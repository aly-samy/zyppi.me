## AMS-0504-IS-A01 — Chair Amendment: Canonical JSON Boundary, Trust-Key Identification, and Transaction Timeout
 
**Instrument ID:** `AMS-0504-IS-A01` **Parent Instrument:** `AMS-0504-IS — Registry Seed System Implementation Specification` **Authority:** Chair, Zyppi Constitutional Council **Status:** **BINDING AMENDMENT — EFFECTIVE UPON RATIFICATION** **Scope:** This amendment modifies and clarifies the implementation contract of `AMS-0504-IS`. It does not authorize implementation by itself and does not authorize production seed content.
  
# 1. Purpose
 
This amendment closes three implementation ambiguities identified during Council review:
 
 
1. the boundary between Domain values, manifest JSON values, and RFC 8785 canonicalization;
 
2. the identification and algorithm binding of trusted seed-signing keys;
 
3. the timeout behavior governing Registry seed transactions.
 

 
These matters shall not be delegated to implementation inference.
 
The amendment preserves the governing principles already established by `AMS-0504-CDR` and `AMS-0504-IS`:
 
 
- the seed system is a controlled materialization mechanism and never an author of constitutional truth;
 
- manifest authority must be verified before database mutation;
 
- canonicalization must be deterministic and must not introduce semantic transformation;
 
- unknown or invalid authority must fail closed;
 
- seed execution must be atomic;
 
- seed execution must not silently retry, repair, reconcile, update, or delete Registry state.
 

  
# 2. Amendment Rule
 
Where this amendment conflicts with, narrows, or clarifies any provision of `AMS-0504-IS`, this amendment shall govern.
 
All provisions of `AMS-0504-IS` not expressly amended remain in full force.
 
This amendment introduces no new production seed records, no new constitutional facts, and no authority to materialize production seed content.
  
# 3. Amendment A — RFC 8785 Canonicalization Input Boundary
 
## 3.1 Replacement of Any Implicit Runtime-Value Projection
 
Any provision in `AMS-0504-IS` that permits, implies, or leaves open the possibility that `canonicalizeJcs()` may convert Domain runtime values into JSON values is hereby superseded.
 
`canonicalizeJcs()` shall perform **canonical serialization only**.
 
It shall not:
 
 
- project;
 
- coerce;
 
- normalize;
 
- repair;
 
- infer;
 
- omit;
 
- substitute;
 
- round;
 
- stringify non-JSON values by custom convention; or
 
- otherwise alter the semantic representation supplied to it.
 

 
RFC 8785 canonicalization is a serialization operation, not a semantic transformation layer.
  
## 3.2 Strict JSON Value Boundary
 
Before JCS canonicalization is invoked, the manifest payload shall have passed explicit validation as a strict JSON value.
 
For the purposes of `AMS-0504`, a valid canonicalization input consists only of:
 
 
- JSON objects;
 
- JSON arrays;
 
- strings;
 
- booleans;
 
- `null`; and
 
- finite JSON numbers representable under the governing JSON and RFC 8785 requirements.
 

 
The following values are prohibited as direct canonicalization inputs:
 
 
- `Date` objects;
 
- `BigInt` values;
 
- `Map` objects;
 
- `Set` objects;
 
- `Buffer` values;
 
- typed arrays;
 
- functions;
 
- symbols;
 
- class instances;
 
- `undefined`;
 
- `NaN`;
 
- positive or negative infinity;
 
- cyclic object graphs;
 
- values dependent on prototype behavior;
 
- values whose serialization depends on implementation-specific hooks; and
 
- any other non-JSON runtime value.
 

 
The presence of a prohibited value shall cause deterministic refusal. The implementation shall not convert the value into an alternative representation.
  
## 3.3 Manifest Representation Is Authoritative
 
Where a Domain concept has a JSON representation, that representation shall be explicitly defined by the ratified manifest contract.
 
Examples include:
 
 
- timestamps represented as manifest strings in the required canonical timestamp format;
 
- identifiers represented as manifest strings;
 
- large numeric identifiers represented as strings where the manifest contract requires string representation.
 

 
Such representations are properties of the **manifest contract**, not behaviors invented by the JCS canonicalizer.
 
The implementation shall validate the manifest representation before canonicalization and before persistence.
 
The implementation shall not accept a runtime `Date` and decide how to serialize it. It shall not accept a `BigInt` and decide whether to serialize it as a JSON number or string.
  
## 3.4 Required Verification Sequence
 
For every seed manifest, the implementation sequence shall be:
 
 
1. load the manifest as untrusted input;
 
2. validate the manifest envelope and required fields;
 
3. validate that the payload presented for canonicalization is a strict JSON value;
 
4. apply RFC 8785 JCS canonicalization without semantic transformation;
 
5. compute and verify the required integrity digest;
 
6. verify manifest authority and cryptographic signature under the authorized trust set;
 
7. validate manifest records against the authorized manifest and Domain contracts;
 
8. begin the database transaction only after all preceding verification stages have succeeded;
 
9. inspect, compare, and, where authorized, materialize Registry state atomically.
 

 
No database write may occur before completion of steps 1 through 7.
  
## 3.5 Domain Helper Boundary
 
Any Domain capability authorized for JCS support shall remain:
 
 
- pure;
 
- deterministic;
 
- synchronous;
 
- side-effect free;
 
- independent of files, environment variables, database clients, network services, and cryptographic key stores.
 

 
The canonicalization capability shall not contain Domain-specific projection rules.
 
If the current Domain model cannot be represented by the ratified manifest JSON contract without transformation, implementation shall halt for constitutional review. The adapter shall not introduce a compatibility layer.
  
## 3.6 Failure Mapping
 
Failure to satisfy the strict JSON boundary shall be treated as follows:
 
 
- malformed or structurally invalid manifest content → `ValidationRefusal`;
 
- prohibited runtime or non-JSON value encountered in the canonicalization payload → `ValidationRefusal`;
 
- failure of the computed JCS digest to match `integrityDigest` → `IntegrityRefusal`;
 
- inability of a conforming implementation to perform canonicalization because the manifest representation is constitutionally underspecified → implementation halt and Chair review before implementation proceeds.
 

 
No fallback serialization may be used.
  
# 4. Amendment B — Trust-Key Identifier and Algorithm Binding
 
## 4.1 Binding Key Identifier Convention
 
Every trusted seed-signing key shall have a stable `keyId` conforming to the following convention:
 `zyppi-seed-<algorithm>-<year>-v<version> ` 
The components are defined as:
 
 
- `zyppi-seed` — fixed namespace prefix;
 
- `<algorithm>` — the normalized algorithm identifier approved by the governing cryptographic specification;
 
- `<year>` — the four-digit year in which the trust-key version was introduced;
 
- `v<version>` — a positive integer version within that key lineage.
 

 
An example conforming identifier is:
 `zyppi-seed-ed25519-2026-v1 ` 
The identifier is an authority-routing and trust-set selection value. It is not itself cryptographic proof.
  
## 4.2 Key Identifier Validation
 
A `keyId` shall be rejected if it is:
 
 
- absent;
 
- empty;
 
- malformed;
 
- outside the required namespace;
 
- syntactically nonconforming;
 
- unknown to the immutable application trust set;
 
- marked revoked;
 
- not active for the requested verification operation; or
 
- associated with an algorithm incompatible with the manifest’s declared cryptographic algorithm.
 

 
Any such condition shall result in:
 `AuthorityRefusal ` 
The implementation shall not:
 
 
- guess a key;
 
- select a default key;
 
- fall back to another trusted key;
 
- infer an algorithm from signature length;
 
- search external key registries dynamically; or
 
- accept a key solely because it can verify a signature.
 

  
## 4.3 Immutable Application Trust Set
 
The authoritative seed-verification trust set shall be:
 
 
- bounded by application-controlled, version-reviewed trust material;
 
- immutable for the lifetime of a running application artifact;
 
- independent of the Registry database;
 
- independent of deployment environment variables as a source of trust membership; and
 
- auditable through the normal Zyppi source-review and deployment process.
 

 
Environment configuration may provide operational information required to execute the application, but it shall not determine which public keys are constitutionally trusted.
 
Private signing keys shall remain outside the application repository and outside the seeder binary.
  
## 4.4 Algorithm Binding
 
The manifest cryptographic envelope shall declare its signature algorithm explicitly.
 
The implementation shall verify all of the following:
 
 
1. the declared algorithm is recognized and authorized;
 
2. the `keyId` resolves to a trusted key entry;
 
3. the resolved key entry is authorized for the declared algorithm;
 
4. the key’s actual cryptographic type is compatible with the declared algorithm;
 
5. the signature encoding is valid for the declared algorithm;
 
6. the signature verifies against the exact ratified canonical payload.
 

 
Successful verification of a signature under an algorithm other than the declared and authorized algorithm shall not be accepted.
 
Algorithm mismatch shall result in:
 `AuthorityRefusal `  
## 4.5 Algorithm Agility
 
The `keyId` convention is designed to permit future cryptographic migration without allowing implementation-time algorithm selection.
 
Adding a new algorithm family, trust key, or key lineage requires:
 
 
1. a formal specification amendment or successor instrument;
 
2. explicit authorization of the algorithm;
 
3. explicit definition of its key and signature encodings;
 
4. review of its canonical signed-payload boundary;
 
5. addition to the immutable application trust set through reviewed source change; and
 
6. deployment of an application artifact containing the newly authorized trust material.
 

 
The seeder shall not implement algorithm agility through permissive negotiation or runtime discovery.
  
## 4.6 Key Rotation and Revocation
 
Key rotation and revocation shall be explicit trust-set state changes.
 
A key rotation shall not replace an existing trusted key implicitly. A new key shall receive a distinct `keyId`.
 
A revoked key shall remain identifiable for audit purposes but shall not be accepted for new manifest verification.
 
The implementation shall not infer revocation from key age, certificate expiration, or deployment date unless such behavior is expressly defined by a future governing instrument.
  
# 5. Amendment C — Transaction Timeout and Failure Behavior
 
## 5.1 Mandatory Explicit Transaction Bound
 
Registry seed execution shall operate under an explicit, finite transaction timeout.
 
The implementation shall not rely solely on:
 
 
- PostgreSQL server defaults;
 
- driver defaults;
 
- operating-system socket defaults;
 
- cloud-provider defaults; or
 
- unbounded transaction behavior.
 

 
The timeout value shall be specified as a named implementation constant in the ratified implementation contract or its formally approved execution configuration.
 
The timeout shall have a single authoritative definition. The implementation shall not create competing timeout values across the CLI, seeder, repository, or database adapter.
  
## 5.2 Timeout Ceiling
 
The implementation shall define a hard transaction timeout ceiling before implementation authorization.
 
The selected value must:
 
 
- be finite;
 
- be explicit;
 
- be deterministic;
 
- be documented;
 
- be covered by automated verification where technically feasible; and
 
- be appropriate to the bounded Registry seed workload.
 

 
The timeout value shall not be chosen ad hoc by the implementation agent.
 
If `AMS-0504-IS` already contains an authoritative transaction timeout value, that value shall be used. If it does not, the value remains an implementation-contract item requiring Chair approval before the implementation mandate is issued.
 
No arbitrary value is ratified by this amendment.
  
## 5.3 Timeout Enforcement
 
The timeout control shall apply to the database transaction itself, including:
 
 
- state inspection;
 
- semantic comparison;
 
- dependency-ordered insertion;
 
- constraint evaluation;
 
- commit; and
 
- any database operation required to complete the atomic seed transaction.
 

 
The implementation may use PostgreSQL transaction-local controls, driver-level controls, or a combination of both, provided that the resulting behavior satisfies the single authoritative timeout contract and does not weaken atomicity.
 
A timeout mechanism shall not permit partial commit.
  
## 5.4 Timeout Outcome
 
A transaction timeout, statement timeout, connection timeout, or equivalent infrastructure interruption shall produce:
 `InfrastructureFailure ` 
The transaction shall be rolled back or otherwise confirmed not committed before the seeder reports the terminal outcome.
 
The implementation shall not:
 
 
- automatically retry;
 
- continue from the interrupted operation;
 
- resume a partially completed manifest;
 
- downgrade the failure to success;
 
- reinterpret the failure as `PartialStateAnomaly` without a subsequent independent state inspection; or
 
- perform automatic repair.
 

 
A later, separately initiated seed execution may inspect the resulting database state according to the normal state taxonomy.
  
## 5.5 Serialization and Concurrency Failures
 
The governing transaction isolation level and fail-closed concurrency requirements of `AMS-0504-IS` remain unchanged.
 
A serialization failure, deadlock, lock timeout, or transaction timeout shall:
 
 
1. terminate the current execution;
 
2. prevent commit;
 
3. produce `InfrastructureFailure`; and
 
4. require an explicit subsequent invocation if another attempt is desired.
 

 
No automatic retry loop is authorized.
  
# 6. Consolidated Implementation Constraints
 
After this amendment, the implementation agent shall have no discretion to:
 
 
- project `Date`, `BigInt`, or other runtime values during JCS canonicalization;
 
- use `JSON.stringify()` as a substitute for RFC 8785;
 
- introduce custom serialization fallbacks;
 
- infer or default a trusted signing key;
 
- select a key based only on successful signature verification;
 
- dynamically add trust keys through environment configuration;
 
- negotiate or discover cryptographic algorithms at runtime;
 
- use an unspecified or unbounded transaction timeout;
 
- automatically retry serialization, lock, deadlock, or timeout failures;
 
- update or delete Registry records during a seed rerun;
 
- repair partial state automatically; or
 
- materialize production seed content.
 

  
# 7. Ratification Effect
 
Upon ratification, `AMS-0504-IS-A01` shall be incorporated into `AMS-0504-IS` as a binding amendment.
 
The resulting implementation status shall be:
 `CONSTITUTIONAL MECHANICS: AUTHORIZED IMPLEMENTATION SPECIFICATION: AMENDED IMPLEMENTATION AUTHORIZATION: PENDING FINAL CONSOLIDATION PRODUCTION SEED CONTENT: NOT RATIFIED ` 
The implementation mandate for Jules shall not be issued until:
 
 
1. the amended `AMS-0504-IS` is consolidated into a single non-contradictory specification;
 
2. the exact transaction timeout value is formally specified, unless already authoritatively present in the IS;
 
3. the cryptographic envelope fields and encodings are fully defined;
 
4. the trust-set representation is specified consistently with the immutable application trust-set rule; and
 
5. the consolidated specification receives final Chair ratification.
 

  
# 8. Chair Determination
 
The Council review is accepted in part and amended as follows:
 
 
- **Canonicalization concern:** accepted, but resolved by enforcing a strict JSON boundary rather than authorizing Domain-value projection inside `canonicalizeJcs()`.
 
- **Key identifier concern:** accepted and converted into a binding, versioned `keyId` convention with explicit algorithm compatibility requirements.
 
- **Transaction timeout concern:** accepted. An explicit bounded timeout is mandatory, but no arbitrary duration is ratified without an authoritative operational basis.
 

 
**Disposition:** `AMS-0504-IS-A01 — APPROVED FOR INCORPORATION AND FINAL CONSOLIDATION.`
