# AMS-0206 — Create `apps/api`

**Implements:** IT-0206
**Milestone:** M02 — Constitutional Package Structure
**Size:** XS
**Depends On:** IT-0108 ☑, AMS-0201 merged, AMS-0202 complete, AMS-0203 complete, AMS-0204 complete, AMS-0205 complete
**Status:** ☐ Planned

## Load

CEngS-000, CEngS-001, CEngS-002, CAW-000, CAW-004, CAW-006, and **AMS-0201 through AMS-0205**.

This mandate establishes the API application node within the constitutional workspace graph.

Do not copy the library-package pattern mechanically. `apps/api` is an application execution target, not a publishable workspace library.

## Objective

Establish `apps/api` as a private, independently compilable ESM workspace application with a minimal TypeScript module entry point and no premature runtime, framework, transport, or application behavior.

This task establishes application structure only.

It does **not** implement:

- an HTTP server;
- Fastify initialization;
- API routes;
- request handling;
- authentication;
- Runtime orchestration;
- Domain behavior;
- Contract behavior;
- application startup behavior;
- application-specific boundary verification.

## Constitutional Application Role

Per CAW-004:

- `apps/api` is an application execution target.
- It is authorized to consume the constitutional package graph when a governing implementation mandate requires that consumption.
- It is not itself a reusable library package.
- It SHALL NOT expose a library-style public package boundary merely to mirror `packages/*`.

The API application will eventually serve as an orchestration and transport boundary. That future role does not authorize premature framework installation, dependency declarations, TypeScript references, startup logic, routes, handlers, or Runtime behavior during M02.

Authorization to import a package in the future does not itself establish an active compile-time or production dependency.

Actual dependencies and TypeScript project references SHALL be introduced Just-in-Time by the mandate that first requires them.

## Apply the M02 Application Pattern

Create or normalize the following application structure:

```text
apps/api/
├── package.json
├── src/
│   └── main.ts
└── tsconfig.json
```

The application SHALL remain structurally minimal.

Do not add configuration, source files, tests, framework files, route directories, adapters, or placeholders merely to make the application appear more complete.

## 1. Application Manifest

`apps/api/package.json` SHALL contain the established private ESM application baseline:

```json
{
  "name": "@zyppi/api",
  "version": "<canonical repository version>",
  "private": true,
  "type": "module",
  "scripts": {
    "build": "tsc -b"
  },
  "dependencies": {},
  "peerDependencies": {}
}
```

Use the repository’s existing canonical workspace version rather than inventing or incrementing a version.

The application manifest SHALL:

- declare the application name as `@zyppi/api`;
- use the canonical repository version;
- remain private;
- declare `"type": "module"`;
- provide an independently executable TypeScript build command;
- contain `"dependencies": {}` exactly;
- contain `"peerDependencies": {}` exactly.

Do not add:

- Fastify;
- Node.js framework dependencies;
- HTTP libraries;
- validation libraries;
- database libraries;
- logging libraries;
- environment-management libraries;
- `@zyppi/runtime`;
- `@zyppi/domain`;
- `@zyppi/contracts`;
- `@zyppi/shared`;
- `@zyppi/testing`;
- any external production or peer dependency.

The production and peer dependency baselines are explicitly Default-Deny.

### Application Manifest Boundary

Do **not** add library-oriented publication fields:

```json
"main"
"types"
"exports"
```

`apps/api` is an application execution target. It is not a publishable library boundary and SHALL NOT declare a synthetic public package API during M02.

Do not add package self-resolution checks intended for workspace libraries.

## 2. Application Entry Point

`apps/api/src/main.ts` SHALL contain exactly:

```ts
export {};
```

This establishes an explicit TypeScript ESM module boundary without inventing application behavior.

Do not add:

- a startup function;
- an asynchronous bootstrap function;
- a `main()` function;
- framework initialization;
- Fastify imports;
- HTTP server creation;
- listeners;
- ports;
- environment reads;
- process access;
- logging;
- shutdown hooks;
- route registration;
- dependency injection;
- Runtime invocation;
- Domain imports;
- Contract imports;
- Shared imports;
- comments;
- placeholder constants;
- temporary exports;
- self-executing code;
- behavior intended only to make the application appear executable.

The absence of runtime behavior is intentional.

M02 establishes application topology, not application execution.

## 3. TypeScript Configuration

`apps/api/tsconfig.json` SHALL establish an independently compilable application project while preserving the repository’s canonical TypeScript configuration.

The configuration SHALL preserve or establish the repository-standard application settings equivalent to:

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"],
  "references": []
}
```

Preserve any existing canonical repository settings that are required for consistency, provided they do not introduce unauthorized dependencies or project references.

The TypeScript project-reference baseline SHALL be:

```json
"references": []
```

Do not add references to:

- `packages/runtime`;
- `packages/domain`;
- `packages/contracts`;
- `packages/shared`;
- `packages/testing`;
- any application;
- Edge;
- infrastructure;
- tooling;
- any other workspace project.

CAW-004 authorizes future API consumption of designated constitutional packages. That authorization does not require unused project references during M02.

When a future implementation mandate introduces an actual import, that mandate SHALL establish the corresponding TypeScript project reference and production dependency according to the repository’s then-current dependency and build rules.

If the existing repository project graph conflicts with this requirement, stop and report the exact conflict rather than silently changing the architecture.

## Application Boundary Verification

Do **not** run `apps/api` through the shared library package verifier.

The existing generic verifier:

```bash
node tools/verify-package-boundary.mjs --package=<package-path>
```

was established for publishable workspace library packages with explicit public ESM export boundaries.

`apps/api` is an application execution target and does not declare:

- `main`;
- `types`;
- `exports`;
- a library public surface.

Do not:

- modify `tools/verify-package-boundary.mjs` to support `apps/api`;
- weaken the verifier;
- add application-specific exceptions to the verifier;
- create an API-specific boundary verifier;
- copy the verifier into `apps/api`;
- fabricate library export metadata merely to satisfy the verifier;
- introduce an `api:boundary` command during M02.

Application-specific dependency and architectural boundary enforcement SHALL be defined under **IT-0208 — Enforce dependency boundaries, CAW-004 table**.

This mandate SHALL NOT predefine or implement those verification semantics.

## Root Integration

The application SHALL be recognized by the existing workspace and TypeScript build configuration.

Do not modify the root `ci` script.

Do not add:

```json
"api:boundary"
```

Do not add an application-specific root verification command before its semantics are formally established.

Do not add application behavior to root scripts.

The required M02 integration is successful participation in the repository’s existing workspace installation, formatting, linting, TypeScript build, testing, and validation processes.
