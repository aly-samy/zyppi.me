# AMS-0802 — Wire Evidence Loading into Pipeline

**Program:** CAW-011 — Commerce Atlas Wedge **Milestone:** M08 — Runtime Verification Pipeline **Task:** IT-0802 — Wire Evidence loading into pipeline **Mandate:** AMS-0802 **Status:** IMPLEMENTATION AUTHORIZED **Authority:** Zyppi Constitutional Council **Constitutional Basis:** Final and Closed M08 Council Gates G-0801 through G-0817 **Implementation Authority:** GRANTED by this AMS **Depends On:** AMS-0801 / IT-0801 and existing M07 evidence contracts **Logical Dependency:** AMS-0802 supplies evidence state required by AMS-0804; AMS-0801 and AMS-0802 are parallel prerequisites for AMS-0804.

# 1. Mandate Purpose

AMS-0802 authorizes implementation of:

**Wire Evidence Loading into the existing M08 Runtime execution pipeline.**

The implementation SHALL connect the existing M07 Evidence Engine to the M08 Application/Runtime boundary so that constitutional execution receives the required evidence material through explicit authorized input.

The implementation SHALL preserve the existing architectural boundary:
`Application     │     │ retrieve / resolve / assemble / transport     ▼ Explicit ExecutionRequest     │     ▼ Constitutional Runtime     │     │ independently verify / evaluate     ▼ ExecutionResult `
The Application layer performs physical evidence retrieval.

The Runtime performs constitutional verification.

Application-layer retrieval success SHALL NOT be treated as constitutional evidence validity.

# 5. Scope

AMS-0802 SHALL implement the Application-layer evidence composition required to connect:
`Active Constitutional View         │         ▼ Evidence References         │         ▼ Registry Evidence Resolution         │         ▼ EvidenceBundle         │         ▼ Evidence Payload Retrieval         │         ▼ Evidence Verification         │         ▼ Explicit Runtime Input         │         ▼ M08 Runtime Pipeline `
The implementation SHALL use the existing M07 evidence contracts and components rather than creating a parallel evidence architecture.

# 6. Existing M07 Evidence Boundary

The implementation SHALL integrate the existing M07 evidence chain.

The established composition is:
`Registry State     │     ▼ RegistryEvidenceResolver.resolve()     │     ▼ EvidenceBundle     │     ▼ Evidence Payload Provider     │     ▼ Evidence Payload Map     │     ▼ verifyEvidenceBundle()     │     ▼ BundleVerificationReport     │     ▼ M08 ExecutionRequest / Runtime execution `
The repository's existing concrete implementation may use:
`ObjectStorageEvidencePayloadProvider `
The mandate does not authorize replacement of that implementation merely for naming abstraction.

Infrastructure-specific implementations SHALL remain outside `packages/runtime`.

# 7. Application-Layer Responsibilities

The Application layer SHALL be responsible for:

1. obtaining the ACV/evidence-reference state;

2. extracting the required evidence references;

3. resolving those references through the existing M07 evidence resolver;

4. retrieving required evidence payloads through the authorized provider;

5. assembling the evidence material deterministically;

6. constructing the explicit Runtime input;

7. invoking the Runtime with the assembled input.

The Application layer MAY perform infrastructure I/O required for these operations.

The Application layer SHALL NOT declare evidence constitutionally valid merely because retrieval succeeded.

# 8. Runtime Responsibilities

The Runtime SHALL remain responsible for constitutional evidence verification.

The Runtime SHALL:

- receive evidence through explicit input;

- independently verify supplied evidence according to the existing evidence-verification contract;

- reject invalid evidence;

- reject missing required evidence;

- reject integrity/hash mismatches;

- preserve deterministic failure behavior;

- produce no constitutional result from unverified evidence.

The Runtime SHALL NOT:

- access PostgreSQL;

- access object storage;

- access the network;

- access the filesystem;

- retrieve evidence;

- retrieve evidence payloads;

- consult infrastructure metadata;

- use ambient clocks;

- use ambient randomness;

- persist evidence;

- trust an Application-provided `verified` flag as constitutional proof.

# 9. Evidence Verification Boundary

Application retrieval and Runtime verification SHALL remain semantically distinct.

The following distinction is mandatory:
`Retrieved     ≠ Verified     ≠ Constitutionally Trusted `
An Application-layer indication that a payload was successfully retrieved is operational information only.

The Runtime SHALL independently establish the constitutional evidence state.

No Application-layer shortcut may bypass Runtime verification.

# 10. Evidence Bundle Integrity

AMS-0802 SHALL preserve the existing `EvidenceBundle` contract.

The implementation SHALL NOT:

- redefine EvidenceBundle semantics;

- introduce alternative evidence hash semantics;

- invent a second evidence-verification algorithm;

- bypass `verifyEvidenceBundle`;

- alter registered evidence digests;

- treat payload retrieval as verification.

Where the existing M07 verification implementation is reused, AMS-0802 SHALL wire it into the M08 execution boundary rather than duplicate it.

# 11. Evidence Ordering

Evidence ordering SHALL be deterministic.

The implementation SHALL preserve the canonical ordering established by the existing evidence serializer.

Where evidence records are serialized as an `EvidenceBundle`, records SHALL be ordered lexicographically by:
`evidenceId `
Retrieval order SHALL NOT determine constitutional ordering.

Ordering SHALL NOT depend on:

- database row-return order;

- object-storage response order;

- network timing;

- asynchronous completion order;

- incidental JavaScript object iteration;

- concurrent retrieval completion order.

Application-level concurrency MAY be used as an implementation optimization provided that canonical assembly remains deterministic.

# 12. Evidence Hash Boundary

AMS-0802 SHALL preserve the G-0809 hash architecture.

The constitutional evidence hash is:
`evidenceHash         │         ▼ canonical EvidenceBundle `
The implementation SHALL use the ratified:
`SHA-256 + JCS / RFC 8785 + UTF-8 + explicit domain separation + non-circular preimage construction `
AMS-0802 SHALL NOT introduce an alternative hashing mechanism.

Hash construction belonging to receipt generation remains subject to AMS-0803.

AMS-0802 is responsible only for supplying the correctly assembled and verifiable evidence material required by the pipeline.

# 13. Retrieval Failure Semantics

Evidence retrieval failures SHALL NOT be silently converted into successful or trusted constitutional state.

If the Application cannot obtain required evidence material, it SHALL NOT:

- silently omit the required evidence;

- fabricate a payload;

- fabricate an evidence digest;

- substitute unrelated evidence;

- mark the evidence as constitutionally verified;

- convert the failure into `ALLOW`, `TRUSTED`, or equivalent success.

The Application SHALL preserve sufficient deterministic failure information for the execution boundary to fail closed according to the applicable existing contracts.

AMS-0802 SHALL NOT invent a new constitutional `ResolutionFailed` EvidenceBundle member or other evidence token unless such a contract already exists in the governing source-of-truth.

Infrastructure-specific HTTP, storage, SDK, or transport error codes SHALL NOT be introduced into constitutional evidence semantics.

# 14. Payload Size and Resource Boundaries

AMS-0802 SHALL NOT invent a new constitutional payload-size rule, gas schedule, computational pricing model, or Runtime memory quota.

The implementation SHALL respect any existing repository, infrastructure, contract, or operational limits already authorized by higher-level governance.

No such limit may be represented as a new constitutional semantic merely for implementation convenience.

The Runtime SHALL remain synchronous and in-memory as required by the constitutional Runtime boundary.

# 15. Application Provider Boundary

The Application implementation SHALL preserve infrastructure independence at the constitutional Runtime boundary.

The concrete provider may remain infrastructure-specific, including the existing:

`packages/runtime packages/domain `

- changing the EvidenceBundle contract.

If an implementation abstraction is required to preserve the existing Application boundary, it shall be introduced only at the Application/infrastructure layer and shall not alter constitutional evidence semantics.

# 16. Runtime Pipeline Integration

AMS-0802 SHALL wire evidence into the existing M04 nine-stage pipeline.

The implementation SHALL preserve:
`1. Admission 2. Bundle Discovery 3. Bundle Verification 4. Dependency Resolution 5. Compatibility Validation 6. ACV Activation 7. Resolution Graph Construction 8. Active Execution 9. Receipt Generation `
AMS-0802 primarily advances the evidence-related portions of:
`Stage 2 — Bundle Discovery Stage 3 — Bundle Verification `
It SHALL NOT replace the M04 lifecycle with a new M08 pipeline.

Any later stage that remains unavailable after AMS-0802 SHALL continue to fail closed according to its existing deterministic typed behavior.

An unavailable implementation SHALL NOT be represented as constitutional success.

# 17. ExecutionRequest Boundary

AMS-0802 SHALL consume the ExecutionRequest contract established by AMS-0801 and the final M08 constitutional decisions.

# 18. No Hidden State

The implementation SHALL preserve Runtime determinism.

The evidence path SHALL NOT depend constitutionally upon:
`Date.now() new Date() Math.random() crypto.randomUUID() process identity machine identity memory address database-generated identifiers storage-generated ordering network timing Promise completion order `
The Application may use asynchronous I/O internally, but the assembled constitutional input supplied to Runtime SHALL be deterministic.
