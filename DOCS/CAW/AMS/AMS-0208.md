# 3. Why This Task Is Different From IT-0201–IT-0207

IT-0201 through IT-0207 established the individual workspace nodes.

AMS-0208 establishes the constitutional enforcement mechanism for the **edges between those nodes**.

This task validates the whole workspace—including libraries and applications—rather than validating one package in isolation.

This is not package scaffolding.

It is a repository-level enforcement implementation involving:

- manifest dependency validation;
- TypeScript project-reference validation;
- TypeScript AST analysis;
- workspace-boundary enforcement;
- production/dev authorization separation;
- direct, non-transitive authorization;
- dependency-cycle detection;
- recursive package-boundary execution;
- CI integration;
- deterministic negative validation fixtures.

The task remains correctly sized as **M**.

# 4. Objective

Create a fail-closed, repository-level constitutional dependency validator that enforces the complete CAW-004 v2.1 ownership and import rules against the actual repository state.

The validator must evaluate every constitutional workspace member, including:

- `packages/domain`
- `packages/shared`
- `packages/contracts`
- `packages/runtime`
- `packages/testing`
- `apps/api`
- `apps/web`
- `edge/worker`

The validator must inspect and reconcile three dependency layers:

1. `package.json` dependency declarations;
2. `tsconfig.json` project references;
3. actual TypeScript source-level imports.

The validator must reject:

- unauthorized direct dependencies;
- unauthorized project references;
- unauthorized source imports;
- production use of dev-only authority;
- workspace-boundary bypass through relative imports;
- unauthorized application-to-application or application-to-edge coupling;
- dependency cycles;
- attempts to derive direct authority transitively.

The validator must remain fail-closed:

> If a workspace edge cannot be identified, classified, or authorized from CAW-004 v2.1, the validator must reject it rather than infer permission.

# 5. Relationship to Existing Validators

The repository must retain three distinct validation concerns.

| Validator                           | Constitutional question                                                                        | Responsibility                                                                      |
| ----------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `tools/validate-runtime-purity.mjs` | Does `packages/runtime` satisfy its additional purity and deterministic-execution constraints? | Runtime-specific purity and prohibited capability enforcement                       |
| `tools/verify-package-boundary.mjs` | Is an individual publishable library package internally well-formed?                           | Package manifest, exports, and local package-boundary structure                     |
| `tools/verify-dependency-graph.mjs` | Does the complete workspace obey CAW-004 v2.1’s permitted dependency graph?                    | Repository-wide dependency authorization, graph integrity, and boundary enforcement |

Do not merge the new graph validator into either existing validator.

Do not duplicate runtime-purity rules that are already enforced by `validate-runtime-purity.mjs`.

Do not force `apps/api`, `apps/web`, or `edge/worker` through `verify-package-boundary.mjs`.

Applications and edge execution targets are not publishable libraries. Their constitutional dependency boundaries must be evaluated by the repository-level graph validator rather than by library-export validation.

## 6.3 Validate `package.json` Dependency Declarations

For every constitutional workspace member, inspect:

```json
{
  "dependencies": {},
  "devDependencies": {},
  "peerDependencies": {}
}
```

The validator must identify workspace dependencies represented by `@zyppi/*` package names and validate them against the CAW-004 v2.1 authorization matrix.

### Production Dependency Context

The following must be treated as production dependency declarations:

- `dependencies`;
- `peerDependencies`.

Every workspace edge declared in either field must be authorized by the source member’s **production** authorization column.

A dev-only edge must not be declared in either production dependency field.

### Development Dependency Context

Workspace dependencies declared in:

```json
"devDependencies"
```

must be authorized by the source member’s dev-only authorization rules.

A package may not use `devDependencies` to bypass a prohibition that CAW-004 does not authorize as a dev-only relationship.

### No Obligation Rule

The validator must not fail merely because a constitutionally permitted dependency is absent.

CAW-004 defines the maximum authorized dependency surface, not a required dependency checklist.

---

## 6.4 Validate TypeScript Project References

For every constitutional workspace member, inspect:

```json
{
  "references": []
}
```

Every project reference that resolves to another constitutional workspace member must correspond to an edge authorized by CAW-004 v2.1.

The validator must:

- resolve project references to their workspace members;
- reject references to unauthorized workspace members;
- reject references that imply production authority where only dev-only authority exists;
- reject references that cannot be classified deterministically;
- permit an empty `references` array;
- permit an authorized edge to remain absent.

Do not require a project reference merely because CAW-004 permits the corresponding import.

Authorization is not obligation.

---

## 6.5 Validate Actual TypeScript Source Imports

Source-level import analysis must use the **TypeScript Compiler API**.

Regex-based import scanning is prohibited.

The validator must walk the TypeScript AST for every applicable `.ts` source file within each constitutional workspace member.

The implementation must inspect all relevant static module relationships supported by the selected TypeScript API, including standard import declarations and other statically resolvable module references where applicable.

The validator must identify imports targeting:

- `@zyppi/*` workspace packages;
- other constitutional workspace members;
- relative paths that cross the source member’s workspace boundary.

### Direct Authorization

Every direct workspace import must be checked against the importing member’s own CAW-004 v2.1 row.

Authority must never be inherited from another package.

Example:

If:

```text
apps/api
→ packages/runtime
→ packages/shared
```

then `apps/api` does **not** automatically gain authority to import:

```text
@zyppi/shared
```

unless CAW-004 v2.1 explicitly authorizes that direct edge.

### Production and Development Context

The validator must classify source files into production or development context using explicit, deterministic repository rules.

The classification mechanism must be documented in the implementation and must not rely on filename guesswork alone where repository configuration provides stronger evidence.

A dev-only-authorized import must fail when used from production source.

The validator must permit the same edge only when it is used within a recognized development or test context and the source member’s CAW-004 v2.1 dev-only authorization explicitly permits it.

If the repository does not yet contain an authoritative convention sufficient to classify a source file deterministically, stop and report the ambiguity rather than inventing a permanent convention.

### Relative Boundary-Skipping

The validator must reject any relative import that escapes the importing workspace member and enters another constitutional workspace member without using the authorized package boundary.

Examples include patterns equivalent to:

```ts
import { value } from "../../packages/domain/src/index.js";
```

or:

```ts
import { value } from "../../../apps/api/src/main.js";
```

The exact number of `../` segments is not the rule.

The rule is:

> A relative import must not escape its owning workspace member and enter another constitutional workspace member.

The validator must resolve paths rather than relying only on textual detection of `../../`.

---

## 6.6 Enforce Infrastructure and Execution Isolation

The graph validator must enforce repository-level workspace boundaries without duplicating the specialized runtime-purity validator.

The validator must reject source-level workspace-boundary bypasses that allow pure constitutional packages to reach infrastructure, application, edge, migration, routing, configuration, or I/O-bearing implementation code through relative paths or unauthorized workspace imports.

This requirement applies to actual repository boundary relationships governed by CAW-004 v2.1.

Do not invent a new universal external-package allowlist or denylist inside the graph validator.

Existing runtime-specific external capability restrictions remain the responsibility of:

```text
tools/validate-runtime-purity.mjs
```

The graph validator’s responsibility is to ensure that workspace topology cannot be used to bypass constitutional ownership boundaries.

---

## 6.7 Reject Dependency Cycles

Build the realized constitutional workspace dependency graph in memory from confirmed repository edges.

The graph must include relevant edges discovered from:

- `package.json` production dependencies;
- `package.json` development dependencies;
- `package.json` peer dependencies;
- TypeScript project references;
- actual source-level workspace imports.

The validator must detect directed cycles.

Any cycle must cause validation failure, regardless of whether every individual edge in the cycle is independently authorized.

Cycle detection must identify the cycle path in the diagnostic whenever practical.

Example:

```text
packages/domain
→ packages/contracts
→ packages/domain
```

The validator must not assume that authorized edges are necessarily acyclic.

Acyclicity is an independent constitutional invariant.

---

## 6.8 Enforce Non-Transitive Authorization

Authorization must be evaluated edge-by-edge.

The validator must not infer that a source member may import a target merely because:

- one of its authorized dependencies imports that target;
- the target is a transitive package-manager dependency;
- the target is reachable through another authorized workspace node;
- the target appears in a project-reference chain.

Every direct dependency must have direct constitutional authorization in the importing member’s CAW-004 v2.1 row.

# 8. Acceptance Criteria

## 8.1 Positive Validation

The following must pass against the compliant repository state:

```bash
pnpm graph:validate
```

The validator must pass when:

- all present workspace dependencies are directly authorized;
- all present project references are authorized;
- all source-level workspace imports are authorized;
- all dev-only edges remain in valid development context;
- no relative import crosses a workspace boundary;
- no dependency cycle exists;
- permitted-but-unused edges remain absent.

---

## 8.2 Complete Negative-Test Suite

The implementation must include a deterministic, automated negative-test strategy.

Do not rely on a manual workflow of:

> insert a violation → run the validator → remember to remove the violation.

Use temporary fixtures, isolated test repositories, controlled fixture mutation, or another deterministic approach consistent with the repository’s existing validation-testing pattern.

Each case must be introduced independently, must cause validation failure with a specific diagnostic, and must leave production repository state clean.

### Test 1 — Unauthorized Manifest Dependency

Introduce an unauthorized workspace dependency into a member’s `package.json`.

Example:

```text
packages/domain
→ any other workspace package
```

Expected result:

- `pnpm graph:validate` fails;
- the diagnostic identifies the source member;
- the diagnostic identifies the unauthorized target;
- the diagnostic identifies the dependency field;
- the diagnostic identifies the violated production or development authorization rule.

---

### Test 2 — Unauthorized TypeScript Project Reference

Introduce a TypeScript project reference to a workspace member not authorized by CAW-004 v2.1.

Expected result:

- validation fails;
- the diagnostic identifies the source member;
- the diagnostic identifies the referenced target;
- the diagnostic identifies the project-reference rule violation.

---

### Test 3 — Unauthorized `@zyppi/*` Source Import

Introduce a direct source import of a workspace package not authorized for the importing member.

Expected result:

- validation fails;
- the diagnostic identifies the importing source member;
- the diagnostic identifies the imported package;
- the diagnostic identifies the source file and import location where practical;
- the diagnostic identifies the violated authorization rule.

---

### Test 4 — Relative Import Escaping a Workspace Boundary

Introduce a relative source import that exits one constitutional workspace member and enters another member directly.

Example:

```ts
import { value } from "../../packages/domain/src/index.js";
```

Expected result:

- validation fails;
- the diagnostic identifies the source file;
- the diagnostic identifies the resolved target path;
- the diagnostic identifies the boundary-skipping rule violation.

---

### Test 5 — Manufactured Dependency Cycle

Introduce a temporary dependency relationship that creates a directed cycle.

The cycle may be created through authorized-looking or otherwise valid individual edges.

Expected result:

- validation fails independently of individual edge authorization;
- the diagnostic identifies that the violation is a cycle;
- the diagnostic displays the detected cycle path where practical.

---

### Test 6 — Production Use of a Dev-Only Edge

Introduce a production-context import or dependency using an edge authorized only for development.

Example:

```text
apps/api
→ packages/testing
```

from a production source or production dependency field.

Expected result:

- validation fails;
- the diagnostic identifies that the edge is dev-only;
- the diagnostic identifies the production context where it was used.

---

### Test 7 — Transitive Authority Violation

Introduce a direct import from `apps/api` to `packages/shared` while relying on the fact that `apps/api` is authorized to depend on `packages/runtime` and `packages/runtime` is authorized to depend on `packages/shared`.

Example:

```text
apps/api
→ packages/runtime
→ packages/shared
```

while also introducing:

```text
apps/api
→ packages/shared
```

Expected result:

- validation fails;
- the diagnostic identifies the direct `apps/api → packages/shared` edge;
- the diagnostic explicitly states that transitive reachability does not grant direct authorization.

The validator must evaluate the direct edge against the `apps/api` row only.

---

### Test 8 — Infrastructure or Execution-Boundary Bleed

Introduce a source-level boundary bypass that causes a constitutionally pure package to reach infrastructure, application, edge, migration, routing, configuration, or I/O-bearing implementation code through an unauthorized workspace relationship or a relative path crossing workspace boundaries.

The fixture must use an actual repository boundary pattern rather than inventing a new constitutional package category.

Expected result:

- validation fails;
- the diagnostic identifies the source member;
- the diagnostic identifies the escaped or unauthorized target;
- the diagnostic identifies whether the violation occurred through an unauthorized workspace import or a boundary-escaping relative import.

This test validates repository-topology enforcement.

It must not duplicate the external capability denylist already enforced by `validate-runtime-purity.mjs`.

---

### Test 9 — Sibling Application or Edge Contamination

Introduce a direct source import from `apps/web` into a sibling application or edge execution target.

Examples:

```text
apps/web
→ apps/api
```

or:

```text
apps/web
→ edge/worker
```

Expected result:

- validation fails;
- the diagnostic identifies the source and target execution nodes;
- the diagnostic identifies the violation as unauthorized sibling application or edge coupling;
- the validator does not treat applications as implicitly importable merely because they share the same workspace.
