# 1. Constitutional Purpose

AMS-0201 establishes `packages/runtime` as a recognized, independently buildable, and structurally verifiable Zyppi workspace package.

This mandate establishes the **package boundary before Runtime behavior**.

The Runtime package SHALL acquire:

1. a canonical workspace identity;
2. a minimal package manifest;
3. a deterministic TypeScript build boundary;
4. an explicit public entry-point map;
5. a manifest-driven artifact verification mechanism;
6. native Node.js verification of its public package boundary;
7. an explicit default-deny dependency baseline.

This mandate SHALL NOT introduce Runtime execution behavior, lifecycle models, identity models, capability models, policy logic, state management, host capabilities, or domain behavior.

The purpose is to establish a trustworthy package shell without manufacturing APIs or authority before those concepts are constitutionally required.

# 5. Runtime Package Manifest

## 5.1 Package Identity

The existing `packages/runtime/package.json` SHALL be extended into the canonical Runtime package manifest.

The manifest SHALL declare:

```json
{
  "name": "@zyppi/runtime",
  "version": "0.1.0",
  "private": true,
  "type": "module"
}
```

If the repository-wide locked version differs from `0.1.0` in the current authoritative baseline, the agent SHALL preserve the repository-aligned version and report the discrepancy rather than silently changing the repository versioning model.

## 5.2 Public Package Boundary

The manifest SHALL define an explicit `exports` field.

The `exports` field SHALL be the authoritative public module-resolution contract for the Runtime package.

The public package boundary SHALL expose only the package entry point required by this mandate.

The agent SHALL use the repository’s established ESM package conventions. The final `exports` map SHALL resolve to the built Runtime artifact rather than directly exposing source files.

The package SHALL NOT expose internal source directories, implementation files, fixtures, tests, scripts, or undeclared subpaths.

The `exports` field establishes the package’s explicit public module-resolution boundary under Node.js package-resolution rules. It SHALL NOT be described as a cryptographic boundary.

## 5.3 Dependency Default Denial

The Runtime package SHALL explicitly contain:

```json
{
  "dependencies": {},
  "peerDependencies": {}
}
```

Both fields SHALL exist and SHALL be exactly empty objects.

The following are prohibited during AMS-0201:

- external production dependencies;
- external peer dependencies;
- `@zyppi/domain`;
- `@zyppi/shared`;
- any other internal workspace package;
- any dependency added solely because it may be permitted in a future architectural layer.

The fact that AMS-0108 permits `@zyppi/domain` and `@zyppi/shared` as potential Runtime imports is an **allowable boundary**, not a present authority grant.

Dependency authority SHALL be granted just in time when a future mandate introduces concrete Runtime behavior that constitutionally requires the dependency.

No dependency SHALL be declared merely to pre-wire future architecture.

## 5.4 Package Scripts

The manifest SHALL contain only scripts required to establish and verify the package structure under this mandate and any scripts required by existing repository conventions.

The package SHALL provide:

- a deterministic package build command;
- a package-local structural verification command;
- any existing standard command required by the repository’s package conventions.

The agent SHALL inspect the existing workspace package conventions before defining the final script names.

The agent SHALL NOT invent scripts that are not required by this mandate or existing repository standards.

The package SHALL NOT use:

- `true`;
- no-op commands;
- placeholder commands;
- failure suppression;
- `|| true`;
- ignored exit codes;
- artificial commands designed only to make CI appear green.

# 6. Runtime Entry Point

The Runtime package SHALL contain:


This SHALL be the package’s sole public source entry point for the M02 foundation.

## 6.2 Minimal Structural State

The entry point SHALL remain behavior-free.

The entry point MAY contain:


or an equivalently minimal TypeScript module declaration consistent with the repository’s compiler and module conventions.

The entry point SHALL NOT introduce:

- `RuntimeIdentity`;

- lifecycle interfaces;
- capability interfaces;
- factories;
- placeholder runtime objects;
- artificial runtime values;
- functions with no constitutional purpose;
- types created solely to satisfy a test;
- behavior created solely to make the package appear non-empty.

TypeScript type erasure SHALL NOT be worked around by manufacturing runtime exports.

The absence of Runtime behavior is the intended M02 state.

# 8. Deterministic Build Requirements

The Runtime package build SHALL be deterministic.

The build configuration SHALL NOT intentionally inject:

- absolute local filesystem paths;
- developer-specific information;
- machine-specific identifiers;
- local timestamps;
- environment-dependent hashes;
- environment-variable values;
- nondeterministic build metadata.

The agent is not required to implement artifact hashing or byte-for-byte reproducibility verification under AMS-0201.

However, the agent SHALL NOT introduce a build tool or configuration that knowingly produces environment-specific variation in the Runtime package artifacts.

The package build SHALL produce the artifacts required by the package’s declared public contract.

# 9. Package-Local Structural Attestation

## 9.1 Purpose

AMS-0201 SHALL establish package-local structural verification without inventing Runtime behavior or relying on dummy assertions.

The attestation SHALL verify the package boundary as a consumer experiences it.

It SHALL NOT be a behavioral test.

## 9.2 Verification Mechanism

The package-local structural attestation SHALL execute through a raw Node.js process.

The consumer-boundary verification SHALL NOT rely on:

- Vitest module aliases;
- Vite resolution;
- test-runner module transformations;
- test-runner-specific path mapping;
- framework-level module-loader behavior.

Vitest MAY continue to verify Runtime behavior in future milestones when actual behavior exists.

Vitest SHALL NOT be used as the authority for the M02 native package-boundary proof.

## 9.3 Native Package Self-Resolution

The verification SHALL resolve the Runtime package through its declared package name:

```text
@zyppi/runtime
```

The verification SHALL NOT use an internal relative source import such as:

```text
../src/index.ts
```

or:

```text
../src/index.js
```

The verification SHALL exercise the package’s declared public resolution boundary.

The implementation SHALL use Node.js package self-referencing through the package’s explicit `exports` map where required by the repository’s ESM and workspace configuration.

The verifier SHALL NOT depend on Vitest aliases, Vite aliases, or hidden source-path resolution.

## 9.4 Manifest-Driven Artifact Verification

The structural verifier SHALL parse the Runtime package manifest and verify the package’s declared public artifact contract.

The verifier SHALL:

1. read `packages/runtime/package.json`;
2. verify that `name` is exactly `@zyppi/runtime`;
3. verify that `type` is consistent with the repository’s ESM package convention;
4. verify that an explicit `exports` map exists;
5. derive the declared public artifact path or paths from the manifest;
6. verify that every public artifact declared by the manifest exists physically after the package build;
7. verify any required declaration artifact declared by the manifest or repository convention;
8. verify that the public package boundary resolves successfully through native Node.js package resolution;
9. fail with a non-zero exit code if any verification condition fails.

The verifier SHALL NOT hardcode `dist/index.js` as its sole authority when the manifest already declares the public artifact contract.

The manifest SHALL remain the source of truth for public artifact verification.

## 9.5 Dependency Baseline Attestation

The structural verifier SHALL parse the Runtime package manifest and assert that:

```json
{
  "dependencies": {},
  "peerDependencies": {}
}
```

Both fields SHALL:

- exist;
- be objects;
- contain zero keys.

Absent fields SHALL NOT be treated as equivalent to empty objects for AMS-0201.

Any dependency addition SHALL cause structural verification to fail.

This check establishes a deterministic lock on the Runtime package’s M02 just-in-time authority baseline.

## 9.6 Verification Script Design

The package-local verification logic MAY be placed under the Runtime package if required for package-local execution.

The verifier SHALL:

- remain small;
- remain deterministic;
- be manifest-driven;
- avoid Runtime behavior;
- avoid hardcoded assumptions that duplicate manifest authority;
- avoid package-specific logic where a generic manifest-driven mechanism is practical.

The implementation SHOULD be structured so that it can be elevated to a repository-level package-boundary validator in a future mandate without requiring a full rewrite.

Such future generalization is explicitly outside the scope of AMS-0201.

Before proceeding, one required refinement has been adopted for the shared boundary verifier.

`tools/verify-package-boundary.mjs` must be **generic from inception** and must not be hardcoded to `@zyppi/runtime` or `packages/runtime`. AMS-0202 and the remaining M02 package-scaffolding mandates will reuse this tool after AMS-0201 is merged.

Implement the verifier with an explicit package-directory argument, for example:

```
node tools/verify-package-boundary.mjs --package=packages/runtime
```

The verifier must derive the package name, manifest metadata, public exports, and artifact targets from the supplied package’s own `package.json`. It must not maintain a hardcoded mapping of package names or package-specific rules.

Keep its responsibility narrowly structural and manifest-driven. It should:

- validate the supplied package directory safely within the repository;
- parse that package’s `package.json`;
- verify `private: true` and `type: "module"`;
- require `dependencies` and `peerDependencies` to be explicitly present and exactly `{}`;
- read the `exports` map dynamically;
- verify that every public artifact declared by the manifest exists after build;
- perform the required native Node public-boundary resolution check without Vitest, Vite aliases, or TypeScript path mappings;
- produce deterministic, package-specific diagnostics and fail non-zero on violations.

Do **not** add package-specific architectural policies to this shared verifier. In particular, do not hardcode permitted TypeScript project references or evaluate each package’s `tsconfig.json` reference policy. Those rules differ by package and remain governed by the relevant package mandate and the repository project graph.

Update the package scripts accordingly:

- `packages/runtime/package.json`:
  `"verify": "node ../../tools/verify-package-boundary.mjs --package=packages/runtime"`
- Root `package.json`:
  `"runtime:boundary": "node tools/verify-package-boundary.mjs --package=packages/runtime"`

The final validation sequence must include:

`pnpm format:check`
`pnpm lint`
`pnpm exec tsc -b`
`pnpm runtime:purity`
`pnpm runtime:boundary`

With this generic-tool refinement incorporated, the AMS-0201 plan is approved and you may proceed with implementation.
