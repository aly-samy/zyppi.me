## 1. Objective

Implement **IT-0801 — Wire ACV loading into pipeline**.

The objective is to connect the existing Application-layer ACV retrieval capability to the existing M04 Runtime pipeline so that an authorized `ActiveConstitutionalView` can enter Runtime execution as an **explicit constitutional input** and be processed through the existing Runtime lifecycle without introducing infrastructure access, hidden state, or a parallel Runtime architecture.

The completed implementation SHALL establish this constitutional flow:
`Application / M05 Registry         │         │ existing authorized ACV retrieval         ▼ Application-layer composition         │         │ explicit ExecutionRequest / authorized Runtime input         ▼ packages/runtime         │         ├── Admission         ├── Bundle Discovery         ├── Bundle Verification         ├── Dependency Resolution         ├── Compatibility Validation         └── ACV Activation         │         ▼ ACV available to downstream Runtime execution `
AMS-0801 does **not** implement policy evaluation, receipt generation, evidence retrieval, or replay.

# 3. Council Decisions Directly Governing AMS-0801

The following decisions are already final and CLOSED. Jules SHALL implement them as constraints and SHALL NOT reopen or reinterpret them.

### G-0801 — Temporal Semantics

Temporal validity uses an explicit temporal coordinate supplied through authorized execution input.

Runtime SHALL NOT obtain time from:

- system clock;

- `Date.now()`;

- `new Date()`;

- host environment;

- infrastructure metadata.

AMS-0801 SHALL preserve explicit transport of the authorized temporal coordinate where the existing execution contract requires it.

AMS-0801 SHALL NOT invent a clock implementation.

### G-0808 — Hybrid Explicit Context Binding

Execution-specific values are represented explicitly.

Authoritative state owned elsewhere is bound by reference rather than duplicated.

`executionId` and the constitutional temporal coordinate are explicit execution inputs.

AMS-0801 SHALL NOT introduce a generic `versions[]` mechanism or silently expand `ExecutionContext`.

### G-0814 — Execution Identity

`executionId` is supplied by the upstream component constructing the `ExecutionRequest`.

The Runtime SHALL NOT:

- generate it;

- derive it;

- replace it;

- mutate it.

AMS-0801's Application-layer composition SHALL preserve the supplied value unchanged.

### G-0811 — Causal Ordering

AMS-0801 is an upstream dependency of policy evaluation:
`AMS-0801 ─┐ AMS-0802 ─┼──► AMS-0804 ─► AMS-0803 ─► AMS-0805           │           └── ACV / Evidence inputs `
AMS-0801 SHALL NOT implement downstream task semantics merely because the existing repository currently exposes incomplete pipeline behavior.

### G-0812 — M04 Pipeline Mapping

M08 completes the existing nine-stage M04 Runtime pipeline:
`1. Admission 2. Bundle Discovery 3. Bundle Verification 4. Dependency Resolution 5. Compatibility Validation 6. ACV Activation 7. Resolution Graph Construction 8. Active Execution 9. Receipt Generation `
AMS-0801's responsibility is limited to the ACV/admission portion required to establish the authorized input for downstream execution.

No stage may silently succeed because it is unavailable.

If an implementation gap encountered by AMS-0801 belongs to a later AMS, Jules SHALL report it rather than implementing it opportunistically.

# 4. ACV Loading Boundary

The fundamental architectural rule is:
`Infrastructure      │      ▼ Application / Registry layer      │      │ retrieve and assemble      ▼ Explicit constitutional input      │      ▼ packages/runtime `
The Runtime SHALL receive an explicit ACV.

The Runtime SHALL NOT retrieve the ACV itself.

Therefore:

### Application layer MAY

- invoke existing M05 Registry capabilities;

- retrieve the authorized ACV through existing interfaces;

- map the retrieved result into the already-authorized Runtime input contract;

- construct or complete the Application-side composition required to invoke Runtime;

- provide explicit execution-specific inputs required by the ratified contracts;

- pass the ACV into Runtime.

### Application layer SHALL NOT

- invent a replacement ACV model;

- duplicate authoritative ACV state unnecessarily;

- bypass existing M05 contracts;

- modify M05 persistence semantics;

- create a second Registry implementation;

- treat Application retrieval as Runtime verification;

- inject infrastructure state directly into `packages/runtime`.

### Runtime SHALL

- accept the ACV only through explicit input;

- perform the Runtime-side validation/activation required by its constitutional lifecycle;

- remain deterministic and synchronous;

- remain zero-I/O;

- preserve the ACV as constitutional execution state for downstream stages.

# 5. Runtime Purity Boundary

AMS-0801 SHALL preserve the existing Runtime purity boundary.

The Runtime must remain:
`Pure Deterministic Synchronous Zero-I/O Infrastructure-independent Explicit-input driven `

# 9. ACV Integrity and Activation

The Runtime SHALL not treat "an object was supplied" as sufficient proof of successful constitutional activation.

AMS-0801 SHALL connect the ACV to the appropriate existing Runtime lifecycle stages so that:

- the ACV is present when required;

- required structural validation occurs;

- invalid/incomplete ACV input fails closed;

- successful ACV activation produces deterministic Runtime state;

- downstream stages receive the activated constitutional view through explicit state;

- no fallback ACV is silently selected.

Jules SHALL use existing validation and contract mechanisms where they already exist.

Do not create an alternative ACV validation framework unless the existing implementation is demonstrably incapable of satisfying the ratified contract.

# 10. Fail-Closed Requirements

The following conditions SHALL NOT produce successful constitutional execution:

- missing ACV;

- malformed ACV;

- structurally invalid ACV;

- incompatible ACV;

- unavailable required ACV information;

- invalid execution input;

- unauthorized fallback ACV;

- hidden infrastructure-derived ACV state.

Failure SHALL be:

- explicit;

- deterministic;

- typed where the existing error architecture provides typed errors;

- attributable to the appropriate Runtime stage;

- reproducible under equivalent inputs.

No failure may silently degrade into:
`ALLOW TRUSTED VALID SUCCESS `
unless that result is actually established by governing semantics.

# 11. Determinism

For identical authorized inputs and constitutional conditions:
`ExecutionRequest₁ = ExecutionRequest₂ ACV₁ = ACV₂ Runtime conditions₁ = Runtime conditions₂ `
the relevant AMS-0801 execution behavior SHALL be equivalent.

In particular:

- ACV activation order SHALL be deterministic;

- validation results SHALL be deterministic;

- failure classification SHALL be deterministic;

- serialized constitutional inputs SHALL not depend on object insertion order or incidental runtime state;

- no random identifiers may be introduced;

- no wall-clock observation may influence behavior.

Jules SHALL add tests demonstrating deterministic behavior where the existing test suite does not already establish it.
