## Objective

Implement `EvidenceRecord` in `packages/domain` as a pure, immutable, JSON-safe Domain representation of the metadata and storage reference defined by CAW-008.

Evidence is immutable verification material—hashes and metadata—backing a claim. This task implements the **metadata record and reference only**. It does not implement evidence payloads, evidence retrieval, cryptographic verification, storage integration, or Runtime evidence bundles.

The implementation must remain a small, pure Domain model consistent with the completed Identity and Referent models.

## Constitutional Grounding

CAW-003 defines Evidence as:

> Immutable verification material (hashes, metadata) backing a claim.

CAW-008 defines the wedge’s `evidence` storage row as:

```text
id
identity_id
evidence_type
hash
storage_ref
retrieved_at
immutable: true
```

The Domain representation maps these storage names to the established TypeScript naming convention:

```text
id              → evidenceId
identity_id     → identityId
evidence_type   → evidenceType
hash            → hash
storage_ref     → storageRef
retrieved_at    → retrievedAt
```

CAW-008 establishes that Evidence is insert-only and never updated after insertion. The storage guarantee is enforced by database permissions. TypeScript `readonly` fields express the Domain-level immutability intent but do not replace the storage-level guarantee.

CAW-011 separates this task from the later Evidence implementation work:

- `IT-0701` — Evidence Bundle model
- `IT-0702` — Evidence reference resolver
- `IT-0703` — Hash verification
- `IT-0704` — R2 client integration
- `IT-0705` — Evidence retrieval tests

Do not pull any of those responsibilities into IT-0303.

## Required Domain Shape

Implement the following type:

```typescript
export type EvidenceRecord = {
  readonly evidenceId: string;
  readonly identityId: string;
  readonly evidenceType: string;
  readonly hash: string;
  readonly storageRef: string;

```

Do not add fields.

In particular, do **not** add:

- `updatedAt`
- payload data
- lifecycle status
- retention metadata
- expiration metadata
- archival metadata
- cryptographic algorithm fields
- verification results
- policy-decision data
- execution-receipt data

If a loaded governing source appears to require an additional field, report the exact source and conflict before implementing it. Do not silently expand the model.

## Field Contracts

### `evidenceId`

- Required.
- Must be a string.
- Must be non-empty after trimming.
- Preserve the supplied value exactly after validation.
- Do not silently trim, normalize, rewrite, or generate it.
- Do not impose UUID validation unless a governing source explicitly requires it.

### `identityId`

- Required.
- Must be a string.
- Must be non-empty after trimming.
- Preserve the supplied value exactly after validation.
- Do not query whether the referenced Identity exists.
- Referential existence is a Registry/Application concern, not a pure Domain validation concern.

### `evidenceType`

- Required.
- Must be a string.
- Must be non-empty after trimming.
- Preserve the supplied value exactly after validation.

For this wedge, `evidenceType` remains an open string rather than a closed union.

CAW-003 and CAW-008 define the field but do not define a finite canonical vocabulary. Do not invent literals such as `"verification_document"`, `"attestation"`, or `"execution_receipt"`.

Record the absence of a ratified evidence-type vocabulary as a bounded implementation note. A future closed union may be introduced only through an explicit constitutional or schema amendment.

### `hash`

- Required.
- Must be a string.
- Must be non-empty after trimming.
- Preserve the supplied value exactly after validation.
- Treat the value as opaque.

Do not:

- generate a hash
- calculate a hash
- verify a hash
- require SHA-256
- impose a fixed length
- require hexadecimal encoding
- require Base64 encoding
- parse algorithm-specific formats

Cryptographic generation and verification are outside this task and are scheduled separately.

### `storageRef`

- Required.
- Must be a string.
- Must be non-empty after trimming.
- Preserve the supplied value exactly after validation.
- Treat the value as an opaque storage reference/object key.

CAW-008 identifies `storage_ref` as an R2 object key and delegates storage concerns to CAW-009. This task must not construct, normalize, parse, resolve, or retrieve the key.

### `retrievedAt`

- Required.
- Must be a strict ISO-8601 UTC timestamp string.
- Must represent a valid calendar date and time.
- Preserve the supplied timestamp string exactly after validation.
- Do not normalize, reformat, or regenerate it.
- Do not use JavaScript `Date` objects as the Domain representation.
- Do not generate timestamps through `Date.now()`, `new Date()`, or any implicit clock.

Reuse the established AMS-0301 timestamp-validation logic if it is already exported and suitable for reuse. Do not duplicate the same calendar-validation algorithm under a different implementation merely because this is a new entity.

If the existing timestamp helper is not reusable without an unjustified refactor, report that constraint and follow the established behavior exactly. Do not weaken timestamp validation.

## Validation Contract

Implement an exception-free pure validation function:

```typescript
export function validateEvidenceRecord(
  candidate: unknown,
): ValidationResult<EvidenceRecord, EvidenceValidationError>;
```

Reuse the existing `ValidationResult<T, E>` convention established by AMS-0301. Do not create a second generic result abstraction.

Implement and export:

```typescript
export type EvidenceValidationErrorCode =
  | "INVALID_EVIDENCE_ID"
  | "INVALID_IDENTITY_ID"
  | "INVALID_EVIDENCE_TYPE"
  | "INVALID_HASH"
  | "INVALID_STORAGE_REF"
  | "INVALID_RETRIEVED_AT";

export type EvidenceValidationError = {
  readonly code: EvidenceValidationErrorCode;
  readonly field: keyof EvidenceRecord;
  readonly message: string;
};
```

The exact error-type formatting should follow the existing AMS-0301/AMS-0302 convention if the repository implementation has an established compatible pattern. Do not create a parallel error architecture.

Validation requirements:

- Ordinary malformed input must not throw.
- Exceptions must not be used as validation control flow.
- Valid input returns the validated `EvidenceRecord`.
- Invalid input returns a structured, machine-readable error.
- Validation must be deterministic and free of side effects.
- The validator must not perform I/O or cross-record lookups.

For a non-object or `null` root input, return:

```typescript
{
  ok: false,
  error: {
    code: "INVALID_EVIDENCE_ID",
    field: "evidenceId",
    message: /* stable explanatory message */
  }
}
```

This follows the established first-field error convention used by the earlier Domain validators.

## Canonical Serialization

Implement:

```typescript
export function serializeEvidenceRecord(record: EvidenceRecord): string;
```

The serialization must be:

- deterministic
- JSON-safe
- stable regardless of the object’s original property insertion order
- free of implicit normalization
- free of timestamps, randomness, or environmental input

Construct the serialized object explicitly in alphabetical key order:

```text
evidenceId
evidenceType
hash
identityId
retrievedAt
storageRef
```

Use the repository’s established deterministic serialization convention where compatible.

The serializer must preserve all valid field values exactly. It must not:

- trim strings
- normalize timestamps
- rewrite storage references
- canonicalize hashes
- alter evidence types

The tests must prove:

1. repeated serialization of the same valid record produces byte-identical output;
2. equivalent records with different JavaScript property insertion histories produce identical serialized output;
3. `serialize → JSON.parse → validate` returns the original valid value;
4. the serialized output uses the required alphabetical key order.

Do not claim cross-language or compiler-grade canonical interoperability beyond what the current repository implementation and RI-001 explicitly establish.

## Immutability

All `EvidenceRecord` fields must be declared `readonly`.

Do not implement:

- `updateEvidence`
- `patchEvidence`
- `deleteEvidence`
- mutation methods
- lifecycle transition methods

Changes to evidence are represented by new records or later storage/application behavior, not mutation of an existing Domain record.

Do not attempt to enforce runtime object freezing unless an existing repository-wide Domain convention already requires it. Type-level `readonly` is the appropriate scope for this task; CAW-008 provides the actual insert-only storage guarantee.

## Explicitly Out of Scope

Do not include binary data, documents, JSON payloads, or resolved storage content in `EvidenceRecord`.

### `EvidenceBundle`

Do not implement `EvidenceBundle`.

CAW-007 uses an `EvidenceBundle` as a Runtime input, but CAW-011 assigns its model to `IT-0701`. The bundle is downstream of this metadata record.

## Acceptance Criteria

- `EvidenceRecord` exists with exactly the six required fields.
- All fields are `readonly`.
- No speculative fields are added.
- `evidenceType` remains an open non-empty string because no ratified finite vocabulary exists.
- `hash` remains an opaque non-empty string with no algorithm-specific validation.
- `storageRef` remains an opaque non-empty storage reference/object key with no storage-key parsing or construction.
- `retrievedAt` uses the established strict ISO-8601 UTC validation behavior.
- Validation is pure, deterministic, structured, and exception-free.
- Existing `ValidationResult` conventions are reused.
- All ordinary malformed inputs return typed validation errors rather than throwing.
- Canonical serialization is deterministic and insertion-order independent.
- Serialization uses the exact alphabetical field order:

```text
evidenceId
evidenceType
hash
identityId
retrievedAt
storageRef
```

- Serialization round-trips successfully through `JSON.parse` and `validateEvidenceRecord`.
- No payload, `EvidenceBundle`, cryptographic verification, storage retrieval, lifecycle, retention, or Runtime behavior is added.
- No new external dependencies are introduced.
- No infrastructure dependency enters `packages/domain`.
- Existing Identity and Referent behavior remains unchanged.
- All required tests pass.
