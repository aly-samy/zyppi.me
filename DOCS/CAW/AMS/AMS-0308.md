1. # AMS-0308 — ExecutionRequest Domain Model

   **Milestone:** M03 — Domain Foundation
   **Task:** IT-0308 — ExecutionRequest
   **Size:** S
   **Depends On:** IT-0301 through IT-0307
   **Wave:** B — Composition Models
   **Status:** IMPLEMENTATION AUTHORIZED

   ***

   ## 1. Mandate

   Implement the `ExecutionRequest` Domain model as the normalized, carrier-independent, explicit input to the Zyppi Runtime.

   `ExecutionRequest` is a pure composition model. It assembles the Runtime input contract defined by CAW-007 without introducing Runtime behavior, policy evaluation, authorization logic, registry access, evidence retrieval, persistence behavior, or carrier-specific concerns.

   This task must preserve the exact six-field CAW-007 contract:

   ```ts
   ExecutionRequest {
     requestId: string
     identity: Identity
     activeConstitutionalView: ActiveConstitutionalView
     evidenceBundle: EvidenceBundle
     policyContext: PolicyContext
     executionContext: ExecutionContext
   }
   ```

   The implementation must use these exact top-level field names:
   1. `requestId`
   2. `identity`
   3. `activeConstitutionalView`
   4. `evidenceBundle`
   5. `policyContext`
   6. `executionContext`

   Do not rename, remove, merge, replace, or add top-level fields.

   ## 3. Architectural Determinations

   The following determinations are already made for this implementation. Do not reopen them as questions.

   ### 3.1 `Identity`

   The CAW-007 `Identity` contract is implemented by the existing Wave A `IdentityRecord`.

   Use the existing exported `IdentityRecord` type.

   Do not replace the `identity` field with `identityId`.

   The required field is:

   ```ts
   readonly identity: IdentityRecord;
   ```

   No new identity model, identity projection, compatibility wrapper, or duplicate identity type may be introduced.

   ***

   ### 3.2 `ActiveConstitutionalView`

   `ActiveConstitutionalView` is a Runtime-facing composition contract and is not a new Wave A primitive record.

   Implement only the minimum typed public boundary required by the current CAW-007 contract and the current repository corpus.

   The implementation must preserve the constitutional contents identified by CAW-007:
   - Identity
   - Relationships
   - Standing
   - Authorities
   - Capabilities
   - Evidence References
   - Applicable Policies

   Use the existing Wave A types and identifiers where the current corpus and repository provide an unambiguous mapping.

   Do not:
   - invent additional constitutional categories;
   - add speculative future fields;
   - create a generic JSON container;
   - use `any`;
   - use `unknown` as an architectural escape hatch;
   - redesign the Active Constitutional View as an identifier-only lookup envelope;
   - perform registry resolution inside the Domain model.

   The Active Constitutional View is explicit Runtime input. It is not a database query, lazy registry view, service, or resolver.

   ***

   ### 3.3 `EvidenceBundle`

   `EvidenceBundle` is assembled outside the Runtime boundary and supplied explicitly through `ExecutionRequest`.

   Do not implement evidence retrieval, R2 access, PostgreSQL access, blob loading, evidence storage, or evidence assembly orchestration.

   Reuse an existing authoritative `EvidenceBundle` contract if the current repository already provides one.

   If the current repository does not provide a complete public `EvidenceBundle` type, define only the narrow typed boundary required for `ExecutionRequest` composition. The boundary must be explicit, documented, structurally validated, and limited to the evidence contract supported by the current corpus.

   Do not use:

   ```ts
   any;
   unknown;
   {
   }
   Record<string, unknown>;
   ```

   as a substitute for an unresolved evidence architecture.

   Do not implement the deferred M07 evidence system in this task.

   ***

   ### 3.4 `PolicyContext`

   `PolicyContext` is a required Runtime input context and is distinct from policy evaluation.

   Implement only the explicit typed composition boundary required by CAW-007 and the current repository corpus.

   Do not assume that `PolicyContext` is identical to `PolicyRecord`.

   Do not:
   - parse policy definitions;
   - interpret policy definitions;
   - evaluate policies;
   - make authorization decisions;
   - create a policy engine;
   - replace `policyContext` with a policy identifier;
   - use an untyped JSON object.

   Where the existing corpus provides a direct relationship to Wave A policy types, reuse those types rather than duplicating them.

   ***

   ### 3.5 `ExecutionContext`

   `ExecutionContext` carries explicit execution inputs, including the CAW-007 concepts of:
   - budget;
   - entropy;
   - versions.

   Implement the minimum public structural contract required for `ExecutionRequest` to represent these inputs explicitly.

   Do not implement the broader IT-0309 or IT-0403 behavior inside this task.

   `ExecutionContext` must remain:
   - explicit;
   - deterministic;
   - data-only;
   - free of hidden clock access;
   - free of hidden randomness;
   - free of implicit version resolution.

   Do not generate entropy, read entropy from the environment, create timestamps, or resolve versions during validation.

   ***

   ### 3.6 Canonical Serialization

   `ExecutionRequest` must support deterministic canonical serialization in accordance with CAW-003 and the current Domain implementation pattern.

   Before implementing serialization:
   1. inspect the current repository for the authoritative canonical serialization mechanism;
   2. inspect package ownership and dependency rules;
   3. reuse the existing mechanism where package boundaries permit;
   4. do not create a second competing serializer if an authoritative compatible mechanism already exists.

   If the current Domain package cannot legally import an existing shared serializer, follow the current repository’s established Domain-compatible serialization pattern.

   Do not modify package architecture merely to complete this small task.

   The serializer must:
   - be deterministic;
   - include all six top-level fields;
   - preserve array order;
   - apply the repository’s established canonical treatment to nested objects;
   - avoid input mutation;
   - produce the same output for equivalent valid inputs;
   - comply with the current package-boundary rules.

   Do not introduce a new serialization architecture.

   ```ts
     readonly activeConstitutionalView: ActiveConstitutionalView;
     readonly evidenceBundle: EvidenceBundle;
     readonly policyContext: PolicyContext;
     readonly executionContext: ExecutionContext;
   }
   ```

   Export all required supporting public types through the established `packages/domain` public API.

   Follow the current Wave A conventions for:
   - `readonly` properties;
   - validation result types;
   - validation error representation;
   - validator naming;
   - serializer naming;
   - export organization;
   - test structure.

   Reuse the existing `ValidationResult<T, E>` abstraction if it remains the repository’s current Domain validation abstraction.

   Do not create a second validation-result system.

   ## 5. Validation Requirements

   Implement pure structural validation for `ExecutionRequest`.

   Validation must verify:
   - the root value has the required object structure;
   - all six top-level fields are present;
   - no required field is `null` or `undefined`;
   - `requestId` is a string;
   - `identity` satisfies the existing `IdentityRecord` contract;
   - `activeConstitutionalView` satisfies its implemented contract;
   - `evidenceBundle` satisfies its implemented contract;
   - `policyContext` satisfies its implemented contract;
   - `executionContext` satisfies its implemented contract;
   - nested validation failures are represented consistently with the current Domain validation pattern.

   Validation must be:
   - deterministic;
   - synchronous;
   - non-coercive;
   - non-mutating;
   - free of I/O;
   - free of hidden state;
   - free of implicit timestamps;
   - free of randomness.

   Do not invent a UUID format, maximum length, payload-size limit, or other `requestId` constraint unless the current governing corpus or an established binding Domain convention explicitly requires it.

   ***

   ## 6. Explicitly Prohibited Behavior

   The implementation must not:
   - query the registry;
   - check whether an identity exists;
   - retrieve or resolve evidence;
   - access PostgreSQL;
   - access R2;
   - perform HTTP requests;
   - access the filesystem;
   - read the system clock;
   - generate randomness;
   - generate entropy;
   - resolve versions from hidden state;
   - evaluate policy;
   - determine authority;
   - determine capability;
   - determine standing;
   - make an authorization decision;
   - execute Runtime behavior;
   - generate an execution outcome;
   - generate an execution receipt;
   - implement persistence;
   - implement carrier-specific behavior;
   - implement QR-specific behavior;
   - implement NFC-specific behavior;
   - modify existing Wave A entity behavior;
   - introduce speculative constitutional entities;
   - introduce `any`;
   - introduce unbounded `unknown`;
   - use generic JSON containers to conceal missing architecture.

   `ExecutionRequest` is a structural input model. Structural validation is not constitutional evaluation.

   ## 7. Required Tests

   Add focused unit tests covering the following.

   ### 7.1 Contract structure
   - a valid `ExecutionRequest` containing all six fields;
   - each required top-level field missing independently;
   - each required top-level field set to `null`;
   - invalid `requestId`;
   - invalid `identity`;
   - invalid `activeConstitutionalView`;
   - invalid `evidenceBundle`;
   - invalid `policyContext`;
   - invalid `executionContext`.

   ### 7.2 Validation behavior
   - validation does not coerce values;
   - validation does not mutate the input;
   - repeated validation produces the same result;
   - validation has no hidden timestamp behavior;
   - validation has no hidden state dependency;
   - validation does not perform policy or authorization behavior.

   ### 7.3 Composition behavior
   - the existing `IdentityRecord` contract is accepted directly;
   - existing Wave A types remain unchanged;
   - the Active Constitutional View uses only the authorized constitutional categories;
   - no registry lookup is required to validate the request;
   - no evidence retrieval is required to validate the request.

   ### 7.4 Canonical serialization
   - repeated serialization produces identical output;
   - equivalent requests produce identical canonical output;
   - serialization does not mutate the input;
   - all six fields participate in serialization;
   - nested objects follow the current authoritative canonicalization behavior;
   - array order is preserved;
   - serialization remains compatible with the current package-boundary rules.

   ### 7.5 Regression
   - all existing Wave A tests continue to pass;
   - no competing validation-result abstraction is introduced;
   - no package-boundary violation is introduced;
   - no unrelated Domain behavior changes.
