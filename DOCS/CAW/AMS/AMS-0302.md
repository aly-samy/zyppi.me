## 1. Constitutional Scope Decision

`IT-0302` is named **“GS1 identifier model”** in `CAW-011`.

`CAW-003` separately establishes **Referent (Product / Brand / Manufacturer)** as a canonical Domain entity:

> The real-world thing the Identity represents. Product identifies Brand and Manufacturer as related referents.

`CAW-008` defines the wedge-level `referents` registry structure.

The constitutional corpus therefore contains a terminology mismatch:

- the build-order task is named for the **GS1 identifier**;
- the Domain model requires the **Referent** entity;
- no separate numbered implementation task is assigned to Referent.

For this milestone, the Chair-approved interpretation is:

> **IT-0302 implements both the GS1 identifier value object and the minimal Referent domain record required by CAW-003 and CAW-008.**

This is an explicit scope decision for M03. It must not be presented as though CAW-011 independently named both models.

The implementation must preserve the distinction:

> **Identity represents. Referent exists. GS1 identifies.**

These concepts must not be collapsed into one type.

---

## 2. Objective

Implement the following pure, immutable, deterministic Domain models in `packages/domain`:

1. **`GS1Identifier`** — the validated Domain value object representing the wedge’s supported GS1 trade-item identifier.
2. **`ReferentRecord`** — the minimal Product, Brand, or Manufacturer entity defined by CAW-003 and CAW-008.

The implementation must:

- remain independent of Runtime, Application, Infrastructure, database, and framework concerns;
- reuse the non-throwing validation-result convention established by AMS-0301;
- preserve the Identity/Referent distinction;
- preserve the completed `IdentityRecord` public contract;
- provide deterministic serialization and comprehensive tests;
- introduce no speculative catalog, traceability, or Digital Link parsing behavior.

---

## 3. Required Domain Models

### 3.1 `ReferentType`

Implement the closed wedge-level union:

```typescript
export type ReferentType = "product" | "brand" | "manufacturer";
```

Do not add additional referent categories unless a governing source explicitly requires them.

---

### 3.2 `ReferentRecord`

Implement the minimal record aligned with the `referents` structure defined in CAW-008:

```typescript
export type ReferentRecord = {
  readonly referentId: string;
  readonly referentType: ReferentType;
  readonly name: string;
  readonly parentReferentId: string | null;
  readonly createdAt: string;
};
```

Field requirements:

- `referentId`
  - Required.
  - Must be a non-empty string after trimming for validation purposes.
  - Preserve the supplied value exactly; do not silently trim or rewrite it.
  - Do not impose UUID syntax or arbitrary length constraints unless directly required by a governing source.
- `referentType`
  - Required.
  - Must be exactly one of:
    - `"product"`
    - `"brand"`
    - `"manufacturer"`
- `name`
  - Required.
  - Must be a non-empty string after trimming for validation purposes.
  - Preserve the supplied value exactly.
- `parentReferentId`
  - Must be either `null` or a non-empty string after trimming for validation purposes.
  - Preserve a supplied non-null value exactly.
  - Do not query whether the parent exists. Referential existence is a Registry/Application concern, not a pure structural Domain validation concern.
- `createdAt`
  - Required.
  - Must be a syntactically valid ISO-8601 UTC timestamp representing a valid calendar date.
  - Preserve the supplied timestamp exactly.
  - Do not create, normalize, reformat, or regenerate it.

### 3.3 `updatedAt`

Do **not** add `updatedAt` to `ReferentRecord`.

The reported CAW-008 wedge schema does not include an `updated_at` field for `referents`. Do not add a field merely for symmetry with `IdentityRecord`.

If the exact loaded CAW-008 source contradicts this, stop and report the conflict before implementation.

---

### 3.4 `GS1Identifier`

Implement a minimal immutable value object representing the GS1 identifier scope directly assigned to IT-0302.

The initial model must contain only the identifier value required by the approved scope:

```typescript
export type GS1Identifier = {
  readonly gtin: string;
};
```

Do not add any of the following to `GS1Identifier` unless the loaded governing sources explicitly assign them to IT-0302:

- `serialNumber`
- `lotNumber`
- `expirationDate`
- Digital Link URI
- Application Identifier maps
- product description
- brand name
- manufacturer name
- price
- inventory information
- catalog metadata

These values represent broader GS1 Digital Link, traceability, or catalog concerns and must not be introduced merely because they may appear in later workflows.

The later Digital Link parser must remain free to compose or consume the validated identifier without this task preemptively defining its complete parsed output.

## 4. GS1 / GTIN Validation Boundary

### 4.1 Required Behavior

`GS1Identifier.gtin` must:

- be a required string;
- contain only ASCII decimal digits;
- support the GTIN representations explicitly required by the approved implementation scope;
- be validated using the standard GS1 check-digit algorithm for every supported length;
- preserve the supplied representation exactly after validation;
- never be silently padded, shortened, or normalized.

### 4.2 Supported Lengths

The implementation may support:

- GTIN-8;
- GTIN-12;
- GTIN-13;
- GTIN-14.

If all four are implemented, the validator must apply the correct GS1 check-digit calculation to each representation.

Do not convert GTIN-8, GTIN-12, or GTIN-13 values into GTIN-14 inside Domain. Representation normalization is not authorized by this mandate.

If the exact governing corpus limits the wedge to a narrower GTIN form, follow that direct requirement and report the deviation from this proposed range before implementation.

### 4.3 External Standard Boundary

The GS1 check-digit algorithm is an implementation of the named GS1 identifier standard, not a new Zyppi constitutional rule.

Therefore:

- implement the algorithm locally and transparently;
- add no external GS1 library;
- document the supported GTIN lengths and checksum behavior in implementation notes;
- do not claim that this task implements the complete GS1 General Specifications;
- do not add parsing for GS1 Digital Link URLs.

## 5. Relationship Among Identity, Referent, and GS1 Identifier

The following separation is mandatory:

| Concept                 | Meaning                                                            | Responsibility                |
| ----------------------- | ------------------------------------------------------------------ | ----------------------------- |
| `IdentityRecord`        | Persistent digital representation                                  | AMS-0301                      |
| `ReferentRecord`        | Real-world Product, Brand, or Manufacturer represented by Identity | AMS-0302                      |
| `GS1Identifier`         | Validated GS1 trade-item identifier value                          | AMS-0302                      |
| GS1 Digital Link parser | Parses and resolves Digital Link representations                   | Later task, including IT-0601 |

`IdentityRecord.referentId` remains the existing nullable string contract established by AMS-0301.

Do not modify AMS-0301 solely to introduce branded identifiers or stronger cross-entity typing.

Do not change:

```typescript
referentId: string | null;
```

unless a direct constitutional conflict is discovered and reported before any modification.

The implementation of `ReferentRecord` must use the same identifier field name:

```typescript
referentId: string;
```

This follows CAW-003’s cross-entity naming convention.

### Important boundary

This mandate does **not** require `ReferentRecord` to embed a `GS1Identifier`.

The constitutional sources establish both concepts but do not, based on the preparation findings, define a ratified direct field relationship between them.

Do not invent one.

The models may coexist as separate Domain types without implying that every Referent has exactly one GTIN or that every GTIN belongs directly to a stored Referent record.

## 6. Validation Convention

Reuse the generic result type established by AMS-0301:

```typescript
export type ValidationResult<T, E> =
  | {
      ok: true;
      value: T;
    }
  | {
      ok: false;
      error: E;
    };
```

Do not create a second generic result abstraction.

Implement structured, finite, machine-readable validation errors.

At minimum, define separate error-code unions appropriate to the two models.

Example:

```typescript
export type ReferentValidationErrorCode =
  | "INVALID_REFERENT_ID"
  | "INVALID_REFERENT_TYPE"
  | "INVALID_NAME"
  | "INVALID_PARENT_REFERENT_ID"
  | "INVALID_CREATED_AT";

export type GS1IdentifierValidationErrorCode =
  | "INVALID_GTIN_TYPE"
  | "INVALID_GTIN_FORMAT"
  | "INVALID_GTIN_LENGTH"
  | "INVALID_GTIN_CHECK_DIGIT";
```

The exact names may be refined for consistency with AMS-0301, but they must remain:

- finite;
- stable;
- machine-readable;
- specific enough to identify the failed validation category.

Implement:

```typescript
export function validateReferentRecord(
  input: unknown,
): ValidationResult<ReferentRecord, ReferentValidationError>;

export function validateGS1Identifier(
  input: unknown,
): ValidationResult<GS1Identifier, GS1IdentifierValidationError>;
```

Validation must not throw for ordinary malformed input.

Do not use exceptions as validation control flow.

## 7. Determinism and Domain Purity

The implementation must satisfy all of the following:

- No database access.
- No repository access.
- No HTTP or network access.
- No filesystem access.
- No environment-variable access.
- No framework decorators.
- No NestJS imports.
- No Azure imports.
- No Node.js native-module imports.
- No `Date.now()`.
- No `new Date()` for timestamp generation or normalization.
- No `Math.random()`.
- No implicit clock.
- No generated identifiers.
- No mutation of input objects.
- No mutation of validated output objects.
- No external validation or GS1 dependencies.

All timestamps and identifiers are explicit inputs.

The implementation must remain compatible with the repository ownership rules enforced by `pnpm graph:validate`.

The existing documented gap in mechanical purity enforcement for `packages/domain` must not be represented as closed unless this mandate explicitly implements and verifies the corresponding validator extension. This mandate does **not** authorize a broad validator redesign.

## 8. Deterministic Serialization

Provide deterministic serialization for both models.

Implement:

```typescript
export function serializeReferentRecord(record: ReferentRecord): string;

export function serializeGS1Identifier(identifier: GS1Identifier): string;
```

Requirements:

- equivalent valid values must produce byte-identical output;
- object insertion order must not affect serialized output;
- serialization must preserve field values exactly;
- serialization must not normalize GTIN representations;
- serialization must not generate or modify timestamps;
- serialize → deserialize → validate must reproduce the same value.

For `ReferentRecord`, use the stable alphabetical field order:

```text
createdAt
name
parentReferentId
referentId
referentType
```

For `GS1Identifier`, the serialized object contains:

```text
gtin
```

Do not claim that these functions establish a repository-wide or cross-language canonical JSON standard. They provide deterministic serialization for these Domain models under the established M03 convention.

## 10. Required Tests

### 10.1 Referent validation

Test valid:

- Product Referent.
- Brand Referent.
- Manufacturer Referent.
- Root Referent with `parentReferentId: null`.
- Child Referent with a valid non-empty `parentReferentId`.
- Valid leap-year timestamp where applicable.

Test invalid:

- missing `referentId`;
- non-string `referentId`;
- empty or whitespace-only `referentId`;
- missing `referentType`;
- invalid `referentType`;
- missing `name`;
- empty or whitespace-only `name`;
- invalid `parentReferentId`;
- invalid timestamp syntax;
- invalid calendar dates;
- non-UTC timestamp where the established AMS-0301 timestamp convention rejects it;
- missing `createdAt`;
- non-string `createdAt`.

Verify that validation preserves original non-empty string formatting rather than silently trimming or rewriting values.

### 10.2 GS1 identifier validation

Test valid examples for every supported GTIN length:

- GTIN-8;
- GTIN-12;
- GTIN-13;
- GTIN-14.

Use known valid examples with correct check digits.

Test invalid:

- missing `gtin`;
- non-string `gtin`;
- empty string;
- whitespace-only string;
- alphabetic characters;
- punctuation;
- embedded whitespace;
- unsupported length;
- correct-length value with an invalid check digit.

Verify that valid values preserve their original representation and are not normalized to GTIN-14.

### 10.3 Deterministic serialization

For both models, test:

- repeated serialization produces identical output;
- equivalent values with different object insertion histories produce identical output;
- serialized output has the required stable key order;
- serialize → deserialize → validate reproduces an identical value;
- serialization does not mutate the original object.

### 10.4 Regression

Run the complete existing Domain test suite to ensure AMS-0301 behavior remains unchanged.
