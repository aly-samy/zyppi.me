## 2. Objective

Create the first GitHub Actions CI workflow for the Zyppi monorepo.

The workflow must be a **thin, deterministic, least-privilege executor** of the repository’s existing validation commands. It must not become a second build system, a shadow configuration layer, or a source of application behavior.

The workflow must establish:

1. Explicit and repository-owned toolchain authority.
2. Frozen dependency installation.
3. Minimal workflow permissions.
4. A stable baseline execution environment.
5. Mechanical enforcement of formatting, linting, TypeScript project references, and tests.

---

## 3. Background

M01 has already established:

- pnpm monorepo structure;
- TypeScript project references;
- ESLint v9 Flat Config;
- Prettier;
- Vitest with isolated mocks and serial file execution.

This task makes the existing repository checks enforceable through GitHub Actions.

At the current repository stage, the authoritative TypeScript validation command is:

```bash
pnpm exec tsc -b
```

Do **not** use or repair `pnpm -r build` merely to make CI pass.

Workspace packages that currently have no independent build behavior must **not** receive dummy, empty, or placeholder `build` scripts.

# 4. Constitutional Execution Rules

## 4.1 Single Toolchain Authority

The root `package.json` is the authoritative repository-owned source of truth for the Node.js and pnpm versions used by CI.

The root `package.json` must explicitly contain:

```json
{
  "engines": {
    "node": "<exact-supported-node-version>"
  },
  "packageManager": "pnpm@<exact-pnpm-version>"
}
```

The executing agent must determine the exact compatible versions from the repository’s current dependency state and lockfile requirements.

Do not select versions arbitrarily.

Do not upgrade existing dependencies merely to adopt a newer Node.js or pnpm version.

Do not create competing version authorities such as:

- `.nvmrc`;
- `.node-version`;
- a second Node.js version declaration in another repository file;
- a pnpm version that conflicts with `packageManager`;
- a workflow-specific pnpm version that differs from `package.json`.

The GitHub Actions workflow may read the Node.js version from the root `package.json` or use an explicit workflow value derived from it, but the final implementation must preserve **one authoritative repository-owned declaration**.

The workflow must enable and use Corepack so that the exact pnpm version declared in:

```json
{
  "packageManager": "pnpm@<exact-version>"
}
```

is the version used in CI.

Do not install pnpm globally with an unpinned command.

Do not use floating runtime selectors such as:

```yaml
node-version: latest
node-version: node
node-version: lts/*
```

---

## 4.2 Least-Privilege Workflow Authority

The workflow must explicitly restrict its GitHub token permissions.

At the workflow top level, declare:

```yaml
permissions:
  contents: read
```

The CI workflow currently requires repository read access only.

Do not grant:

- `contents: write`;
- `pull-requests: write`;
- `issues: write`;
- `checks: write`;
- `actions: write`;
- `packages: write`;
- deployment permissions;
- release permissions;
- any other write capability.

Do not use `permissions: write-all`.

Do not omit the permissions declaration and rely on repository defaults.

---

## 4.3 Baseline Execution Environment

The workflow must explicitly define:

```yaml
env:
  TZ: UTC
  CI: true
```

These values establish a visible, stable baseline for time-sensitive and CI-sensitive behavior.

This task does **not** establish a global locale policy.

Do not add locale environment variables unless they are required by an existing repository dependency or validation command.

Future tests that depend on locale-specific behavior must define their required locale explicitly rather than relying on the GitHub runner’s default locale.

---

## 4.4 Command Fidelity

The workflow must execute the repository’s canonical validation commands directly.

The required commands are:

```bash
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm exec tsc -b
pnpm test
```

Do not reproduce formatting, linting, TypeScript, or test behavior inside workflow YAML.

Do not replace these commands with workflow-specific alternatives.

Do not add custom wrappers or shell scripts that duplicate repository behavior.

---

## 4.5 Fail-Closed Execution

Each validation gate must be a separate, visible GitHub Actions step.

The required validation order is:

```text
Install dependencies
→ Check formatting
→ Run ESLint
→ Run TypeScript project build
→ Run tests
```

If any command fails, the workflow must fail.

Do not use:

```yaml
continue-on-error: true
```

Do not suppress failures with:

```bash
command || true
```

Do not use shell logic that converts a failed validation command into a successful workflow step.

Tests must not run after a failed TypeScript build.

---

## 4.6 Thin CI Principle

GitHub Actions must orchestrate repository-owned behavior. It must not become an independent build architecture.

The workflow must not contain:

- custom build logic;
- inline application logic;
- custom dependency graph logic;
- duplicate lint configuration;
- duplicate TypeScript configuration;
- duplicate test configuration;
- hidden Bash orchestration;
- workflow-specific validation rules that are absent from the repository.

The repository remains the source of truth. CI executes and enforces it.

# 5. Scope

## In Scope

Create one baseline GitHub Actions workflow:

```text
.github/workflows/ci.yml
```

The workflow must:

1. Trigger on:
   - `push`;
   - `pull_request`.
2. Explicitly declare:

```yaml
permissions:
  contents: read
```

1. Explicitly declare:

```yaml
env:
  TZ: UTC
  CI: true
```

1. Use the Node.js version defined by the root repository authority.
2. Enable Corepack.
3. Use the exact pnpm version declared by the root `package.json`.
4. Use the standard pnpm cache integration supported by GitHub Actions tooling.
5. Install dependencies using:

```bash
pnpm install --frozen-lockfile
```

1. Run the repository validation gates in this order:

```bash
pnpm format:check
pnpm lint
pnpm exec tsc -b
pnpm test
```

1. Fail immediately when a validation gate fails.
2. Keep every validation gate visible as a separate workflow step.

# 6. Required Workflow Structure

The workflow must follow this logical sequence:

```text
Workflow trigger
→ Read-only permissions
→ UTC/CI environment baseline
→ Checkout
→ Set up Node.js
→ Enable Corepack
→ Restore standard pnpm cache
→ Install with frozen lockfile
→ Check formatting
→ Run lint
→ Run TypeScript project build
→ Run tests
```

The exact arrangement of Node.js, Corepack, pnpm, and cache setup may follow current GitHub Actions requirements, provided that:

- the toolchain remains explicitly controlled;
- `package.json` remains the authoritative source;
- the exact pnpm version declared in `packageManager` is used;
- no conflicting version source is introduced;
- the cache uses the standard supported mechanism.

# 7. Constraints

1. **Root `package.json` is authoritative**

   Node.js must be defined through:

```json
"engines": {
  "node": "<exact-supported-version>"
}
```

pnpm must be defined through:

```json
"packageManager": "pnpm@<exact-version>"
```

1. **Corepack is mandatory**

   CI must enable and use Corepack.

2. **No global floating pnpm installation**

   Do not use:

```bash
npm install -g pnpm
```

Do not use an unpinned pnpm installation command.

1. **Least privilege is mandatory**

   The workflow must explicitly use:

```yaml
permissions:
  contents: read
```

1. **Execution baseline is mandatory**

   The workflow must explicitly use:

```yaml
env:
  TZ: UTC
  CI: true
```

1. **Frozen installation is mandatory**

```bash
pnpm install --frozen-lockfile
```

must be used exactly.

1. **No lockfile mutation**

   CI must not modify `pnpm-lock.yaml`.

2. **No placeholder scripts**

   Do not add workspace `build`, `test`, or other scripts solely to satisfy CI.

3. **No hidden failure handling**

   Do not use `continue-on-error`, `|| true`, or equivalent failure suppression.

4. **No custom workflow orchestration**

Do not add Bash scripts or custom wrappers that duplicate repository validation behavior.

1. **No unrelated changes**

Do not modify application architecture, package boundaries, or production behavior.

# 8. Acceptance Criteria

The implementation is accepted only when all of the following are true:

## Workflow

- `.github/workflows/ci.yml` exists.
- The workflow triggers on both `push` and `pull_request`.
- The workflow explicitly declares:

```yaml
permissions:
  contents: read
```

- The workflow explicitly declares:

```yaml
env:
  TZ: UTC
  CI: true
```

- The workflow does not grant write authority.

## Toolchain

- The root `package.json` contains an explicit `engines.node` declaration.
- The root `package.json` contains an exact `packageManager` declaration for pnpm.
- No competing Node.js version authority is introduced.
- No conflicting pnpm version authority is introduced.
- CI enables Corepack.
- CI uses the exact pnpm version declared in `package.json`.
- No floating Node.js selector is used.
- No unpinned global pnpm installation is used.

## Dependency Installation

- CI runs:

```bash
pnpm install --frozen-lockfile
```

- CI does not modify the lockfile.
- The standard pnpm cache mechanism is enabled.

## Validation Gates

The following commands are present as separate visible workflow steps and execute in this order:

```bash
pnpm format:check
pnpm lint
pnpm exec tsc -b
pnpm test
```

- A failed formatting check fails the workflow.
- A failed lint check fails the workflow.
- A failed TypeScript build fails the workflow.
- A failed test run fails the workflow.
- Tests do not execute after a failed TypeScript build.
- No failure suppression is present.

## Architectural Scope

- No dummy or placeholder workspace scripts are added.
- No application code is introduced.
- No runtime, API, web, edge, domain, or registry behavior is introduced.
- No deployment or release behavior is introduced.
- No CI matrix is introduced.
- No unrelated dependency upgrade is introduced.
- Runtime purity enforcement is not added prematurely.

## Local Repository Validation

The following commands must all succeed after implementation:

```bash
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm exec tsc -b
pnpm test
```

The workflow YAML must be syntactically valid.
