## 1. Purpose

This record reconciles the identity-resolution reference produced by `M06 — GS1 Digital Link Resolution` with the canonical-reference contract persisted and queried by `M05 — Registry Layer`.

Its purpose is to establish one exact, attributable, enforceable cross-milestone registry-key representation without:

- altering the M05 Registry adapter;

- authorizing implementation;

- ratifying M05 production seed content;

- expanding the M06 wedge beyond its ratified support profile;

- introducing instance-level identity;

- selecting a database-enforcement mechanism; or

- authorizing `AMS-0601`.

The governing reconciliation question is:

**What exact normalized identity reference shall M06 produce and pass to the M05 Registry, and under what uniqueness and temporal-resolution invariant shall that reference operate?**

# Part I — Repository and Contract Findings

## 4. Current M05 Representation State

### 4.1 Direct repository findings

`DIRECT REPOSITORY EVIDENCE` established by `JRM-06-03`:

1. `identities.canonical_reference` is represented in the executable database schema as:

`TEXT NOT NULL `

1. The column has:

- no uniqueness constraint;

- no dedicated index;

- no format constraint;

- no length constraint; and

- no character-set constraint.

1.

The Domain representation `IdentityRecord.canonicalReference` is a primitive, non-nullable `string`.

2.

Domain validation requires only that the value:

- is a string; and

- is not empty after trimming.

1. The M05 seeder persists the supplied `canonicalReference` value without:

- normalization;

- padding;

- URI parsing;

- prefix removal;

- GTIN conversion; or

- other representation mapping.

1. `createValidatedCanonicalIdentifier` is a non-coercive validation boundary. It does not:

- trim;

- normalize;

- pad;

- parse;

- canonicalize; or

- transform the supplied value.

1. M05 lookup performs strict PostgreSQL text equality:

`WHERE canonical_reference = ${identifier} `

1.

Lookup operates under a `REPEATABLE READ READ ONLY` transaction.

2.

Leading zeroes, character casing, and all other stored characters remain representation-significant.

3.

Existing repository tests and seed-related test data contain mixed representations, including:

- raw GTIN-like strings;

- prefixed identifier strings; and

- full GS1 Digital Link URI strings.

1. No M06 implementation, GS1 Digital Link parser, identifier normalizer, qualifier model, or resolution pipeline exists in the active repository.

### 4.2 Constitutional characterization

The executable M05 repository does **not** currently embody a single canonical-reference representation contract.

It embodies:

**A permissive text storage field combined with strict, representation-sensitive equality lookup.**

Accordingly, the selection of a registry-key form in this record is **not** a clarification of an already-enforced repository behavior.

It is the establishment of a **new, explicit, enforceable cross-milestone representation contract**.

# Part II — Registry-Key Evaluation

## 7. Candidate Forms

The following candidates were evaluated against the governing architecture and the repository evidence.

### K1 — Normalized 14-Digit GTIN

**Definition**

A plain string consisting of exactly fourteen decimal digits representing a validated GTIN in normalized GTIN-14 form.

Example:
`09506000134352 `
**Repository position**

- physically storable in the existing `TEXT` column;

- not currently enforced;

- not currently generated by the existing GTIN validation behavior;

- requires an explicit normalization contract before M05 lookup;

- requires alignment of mixed test and seed representations when implementation is authorized.

**Architectural position**

- consistent with GTIN-level product-class resolution;

- separates the external carrier from the internal registry key;

- preserves M05 as a strict persistence and retrieval boundary;

- does not require M05 to parse GS1 syntax.

### K2 — Canonical GS1 Digital Link URI

**Definition**

A canonical GS1 Digital Link URI used directly as the M05 registry key.

Example:
`https://id.gs1.org/01/09506000134352 `
**Repository position**

- physically storable in the existing `TEXT` column;

- no URI canonicalizer exists;

- no URI normalization contract exists;

- existing mixed representations would require alignment.

**Architectural position**

- retains the external carrier representation as the internal registry key;

- would require a precise URI canonicalization contract;

- would couple registry-key equality to external carrier-form semantics.

### K3 — Native Zyppi Composite Reference

**Definition**

A Zyppi-defined internal reference encoding a GTIN and, potentially, qualifiers or other identity components.

Illustrative form only:
`urn:zyppi:ident:gs1:01:09506000134352 `
**Repository position**

- physically storable in the existing `TEXT` column;

- no grammar, constructor, parser, or mapping contract exists;

- no existing repository model establishes qualifier composition.

**Architectural position**

- would introduce a new native identity grammar;

- would require a new mapping layer;

- would expand the current wedge beyond the minimum GTIN-level registry-key requirement.

## 8. Council Evaluation

The repository is representation-neutral at the storage level.

Therefore:

- no candidate is selected because of an existing database constraint;

- no candidate is selected because the current repository already enforces it;

- no candidate is eliminated solely because it cannot be stored;

- the selection must be made according to the ratified wedge scope, constitutional boundaries, and cross-milestone responsibilities.

The Council determines that K1 is the appropriate representation for the current M05/M06 wedge because it:

1. establishes one exact representation for strict M05 equality lookup;

2. corresponds to the GTIN-level product-class resolution scope;

3. separates external GS1 carrier syntax from Zyppi's internal registry-key representation;

4. keeps GS1 interpretation and normalization outside the M05 Registry adapter;

5. avoids introducing a new proprietary composite identity grammar; and

6. establishes a narrow, deterministic contract without pre-authorizing instance-level identity.

# Part III — Ratified Registry-Key Contract

## 9. G06-03-K1 — Ratified Cross-Milestone Registry-Key Contract

The following provisions are ratified and binding.

### K1-01 — Exact registry-key representation

The M05/M06 registry-key representation shall be:

**A normalized, validated, fourteen-digit GTIN represented as a plain decimal string.**

The registry-key representation shall:

- contain exactly fourteen characters;

- contain only decimal digits;

- preserve all leading zeroes required to form the normalized GTIN-14 representation;

- be represented as a string; and

- satisfy the applicable GTIN check-digit requirement established by the preserved standards evidence baseline.

No URI, URI prefix, proprietary prefix, namespace label, or carrier-specific wrapper shall form part of the M05/M06 registry key.

### K1-02 — Normalization responsibility

M06 shall normalize an accepted GS1 identifier into the ratified fourteen-digit registry-key representation **before** invoking M05 lookup.

The normalization capability shall be:

- pure;

- deterministic;

- explicit;

- independently testable;

- located within the M06 interpretation boundary; and

- implemented without introducing GS1 parsing or normalization responsibilities into the M05 Registry adapter.

The M05 adapter and lookup path shall not:

- parse GS1 carrier syntax;

- pad GTIN values;

- calculate or repair check digits;

- strip prefixes;

- canonicalize URIs; or

- perform representation inference.

### K1-03 — Accepted GTIN forms and normalization

Where the ratified M06 support profile accepts GTIN-8, GTIN-12, GTIN-13, or GTIN-14 forms, the M06 normalization boundary shall:

1. validate the supplied GTIN according to the preserved standards evidence baseline;

2. convert the accepted value to exactly fourteen digits through the required leading-zero normalization;

3. preserve the resulting normalized value as a string; and

4. pass that exact string to M05.

This contract does not assert that the current repository already performs such normalization.

The capability does not exist in the current implementation and shall be introduced only through authorized M06 planning and implementation.

### K1-04 — M05 strict-equality boundary

M05 strict-equality lookup shall remain unchanged.

The M05 Registry shall receive the already-normalized registry key and resolve it through exact representation-sensitive equality.

No normalization behavior shall be added to:

- `PostgresRegistryRepository.lookup`;

- the M05 persistence adapter;

- the M05 database query; or

- `createValidatedCanonicalIdentifier`.

### K1-05 — Future seed representation

Any future ratified M05 production seed content governed by this contract shall store the applicable registry key in the exact normalized fourteen-digit GTIN representation defined by `K1-01`.

This provision:

- constrains future seed ratification;

- does not ratify any current production seed content;

- does not promote test data into production data; and

- does not authorize seed implementation.

### K1-06 — Existing test and fixture alignment

When implementation is authorized, existing mixed-format test and fixture representations relevant to the M05/M06 registry-key contract shall be reviewed and aligned with the ratified representation.

The alignment shall include, where applicable:

- raw GTIN representations;

- prefixed identifier representations;

- GS1 Digital Link URI representations used as canonical-reference values; and

- lookup expectations dependent on exact string equality.

Test alignment shall not be interpreted as authorization to alter unrelated domain behavior.

## 10. Qualifier Boundary

The following distinction is ratified:

1.

The M05/M06 registry key is GTIN-only for the current wedge.

2.

Serial, lot/batch, expiration, and other qualifiers shall not form part of the K1 registry key.

3.

The current M05 Registry does not store qualifiers in `canonical_reference` and contains no existing qualifier-preservation channel.

4.

Any M06 requirement to preserve qualifiers as interpretation context shall be explicitly designed and attributed in `M06-PLAN`.

5.

Qualifier preservation shall not be implied merely by excluding qualifiers from the registry key.

6.

This record does not authorize:

- instance-level identity;

- GTIN-plus-serial identity;

- composite registry keys;

- qualifier persistence in M05; or

- a future instance-resolution model.

Any future instance-level identity capability shall require a separate attributable architectural decision and shall not be inferred from this contract.

# Part IV — Uniqueness and Temporal Resolution

## 11. Registry-Key Uniqueness Invariant

The Council ratifies the following constitutional invariant:

**Within a defined registry resolution scope and at any given effective time, one normalized registry key shall resolve to no more than one authoritative identity.**

This is an invariant of authoritative resolution, not a mandate for a particular database constraint.

The invariant shall prevent ambiguity in the result of an authoritative registry lookup.

### 11.1 Scope of the invariant

The applicable registry resolution scope shall be explicitly defined by the governing architecture.

The scope may include, where constitutionally required:

- the registry authority;

- jurisdiction;

- issuer;

- namespace;

- tenant or constitutional domain; or

- another ratified resolution boundary.

No scope dimension shall be introduced implicitly.

For the current Commerce Atlas wedge, no additional scope dimension is established by this record. The current contract therefore applies to the registry resolution scope already defined by the governing M05/M06 architecture.

### 11.2 Temporal identity continuity

A registry key shall not be treated as permanently bound to one identity across all time merely because it is represented by the same normalized GTIN.

Historical change, decommissioning, reassignment, or other lifecycle events may require the preservation of multiple historical identity associations.

Where such temporal reuse is constitutionally permitted:

1. historical records may preserve prior identity associations;

2. historical preservation shall not create ambiguity in authoritative resolution;

3. the applicable effective-time or lifecycle rules shall determine which association, if any, is authoritative;

4. a prior association shall not silently remain authoritative after its governing validity has ended; and

5. any future temporal-reuse model shall be explicitly designed rather than inferred from the absence of a database uniqueness constraint.

### 11.3 Suspension and identity uniqueness

Suspension shall not automatically terminate identity continuity.

A suspended identity may remain the unique identity associated with a registry key even where its authority, availability, or executability is temporarily restricted.

Accordingly:

- identity uniqueness;

- trust status;

- execution authorization; and

- lifecycle availability

shall not be conflated.

The effect of suspension on resolution and execution shall be governed by the applicable Security, Policy, and Runtime authorities.

### 11.4 Enforcement mechanism

This record establishes the constitutional invariant but does **not** prescribe its technical enforcement mechanism.

The invariant may be enforced through one or more authorized mechanisms, including:

- a database constraint;

- a scoped or partial uniqueness constraint;

- a temporal exclusion rule;

- an application-level invariant;

- a transactionally verified repository rule; or

- another mechanism approved through the applicable schema and architecture authority.

No database migration is authorized by this record.

The selection of an enforcement mechanism shall occur only within an authorized implementation plan and shall demonstrate that it preserves:

- deterministic resolution;

- temporal correctness;

- lifecycle semantics;

- repository integrity; and

- the constitutional invariant established above.
