## 1. Executive Repository Snapshot
Milestone M08.5-PREP establishes a rigorous, comprehensive, and evidence-backed inventory of the existing repository substrate. This reconnaissance is designed exclusively to inform the Zyppi Constitutional Council for its upcoming drafting and ratification of the **Z-PROF** architecture.
This report documents the structural facts of the repository as of August 2026. The repository contains a complete, robust, and clean ESM monorepo substrate. The foundational packages (`@zyppi/domain`, `@zyppi/contracts`, `@zyppi/runtime`, `@zyppi/shared`, `@zyppi/testing`) compile flawlessly under ESM with TypeScript.
The primary findings confirm that:
1. **Purity-Preserved Execution Engine:** The runtime (`@zyppi/runtime`) operates with absolute AST-level purity (zero-I/O, fully synchronous, host-independent determinism verified via static AST analysis).
2. **Flexible In-Memory Composition:** The Application layer currently constructs the execution boundary dynamically in `apps/api/src/registry/pipelineOrchestrator.ts`, mapping state directly into an explicit `ExecutionRequest` contract without hardcoding intermediate runtime stages.
3. **Robust Cryptographic & Serialization Primitives:** The repository contains complete and compliant implementations of JCS (RFC 8785) canonicalization and SHA-256 hashing with stable domain separation, isolated under `@zyppi/domain` to maintain runtime purity.
4. **Pure Evidence Transport:** Dynamic loading from object storage with configuration-controlled retries and deep-freeze immutability is implemented under `@zyppi/contracts` and `@zyppi/api`.
5. **No Architectural Invention:** No hypothetical files or structures have been introduced; all present capabilities, gaps, and missing modules are registered verbatim from directly observed repository paths.

## 3. M03–M08 Implementation Status
This section evaluates the actual implementation status of Milestones M03 through M08.
### 3.1 Milestone M03 (Domain Models) — `IMPLEMENTED`

### 3.2 Milestone M04 (Runtime Pipeline Skeleton) — `PARTIALLY IMPLEMENTED`

- **Intermediate Stubs:** Stage 2 (Bundle Discovery), Stage 4 (Dependency Resolution), and Stage 5 (Compatibility Validation) natively return `_UNAVAILABLE` errors, blocking end-to-end successful executions natively.

### 3.3 Milestone M05 (Registry & Seeder) — `IMPLEMENTED`
- **Existing Elements:**
  - `RegistryRepository` & `ReceiptRepository` interfaces are defined in `packages/contracts/src/registry.ts`.
  - Concrete PostgreSQL adapters (`PostgresRegistryRepository`, `PostgresReceiptRepository`) are implemented in `apps/api/src/registry/` using `postgres.js` with `REPEATABLE READ READ ONLY` snapshot isolation.
  - Transactional `postgres-registry-seeder.ts` applying records in strict topological order under `SERIALIZABLE` isolation is verified inside `apps/api/src/registry/seed/`.



### 3.4 Milestone M06 (GS1 Carrier Processing) — `IMPLEMENTED`
- **Existing Elements:** Pure semantic validation and resolution of GS1 Digital Link carriers.
  - Parser: `parseGs1DigitalLink` in `packages/domain/src/gs1Parser.ts` maps URI components to distinct sources (path vs query).
  - Validator: `validateGs1DigitalLink` in `packages/domain/src/gs1Validator.ts` uses the closed 9-error taxonomy.
  - Normalizer: `normalizeGs1DigitalLink` in `packages/domain/src/gs1Normalizer.ts` outputs a deeply frozen `NormalizedGs1DigitalLink` with resolution key `k1`.
  - Resolver: `resolveGs1DigitalLink` in `packages/contracts/src/gs1Resolver.ts` maps normalized inputs to existing Registry Referents.



### 3.5 Milestone M07 (Evidence Engine) — `IMPLEMENTED`
- **Existing Elements:**
  - `RegistryEvidenceResolver` (in `apps/api/src/registry/evidenceResolver.ts`) batches and validates evidence metadata using the repository and domain validation bounds.
  - `ObjectStorageEvidencePayloadProvider` (in `apps/api/src/evidence/objectStorageEvidencePayloadProvider.ts`) retrieves JSON payloads from an `ObjectStorageClient` using a deterministic 3-attempt transient retry policy, returning recursively deep-frozen maps.
  - `verifyEvidenceBundle` (in `packages/domain/src/evidenceVerification.ts`) validates cryptographic hashes and enforces the canonical 10MB payload size limit.



### 3.6 Milestone M08 (Runtime Verification Integration) — `IMPLEMENTED`
- **Existing Elements:** Stage 6 (ACV Activation) boundary checking, Stage 7 (Resolution Graph Materialization), Stage 8 (Active Execution with topological policy sorting and conjoined ternary evaluation), and Stage 9 (Deterministic Receipt Materialization conforming to the ten-field contract ratified in G-0804).
- **Replay suite:** `packages/testing/src/replay/pipelineReplay.test.ts` executes 9 vectors under zero-StageOverrides (verifying 5 natively, 4 blocked due to unimplemented intermediate stages).

## 6. M05 Registry Findings
Detailed factual observation of the M05 Registry capabilities:
### 6.1 Registration Boundaries
- **What can be registered:** `ReferentRecord`, `IdentityRecord`, `EvidenceRecord`, `PolicyRecord`, `AuthorityRecord`, `CapabilityRecord`, and `StandingRecord`.
- **Supported arbitrary types:** **UNKNOWN**. The registry schema is strict and has explicitly typed tables (defined in `infra/migrations/001_initial_registry_schema.sql`). It enforces foreign keys and RESTRICT delete rules. It does not support arbitrary non-relational blobs except inside the JSONB `definition` field of the `policies` table.
- **Dependencies & Versions:** Versions are stored strictly as text columns (`version` in `policies`, `runtimeVersion` / `policyVersion` in `execution_receipts`). Structural dependencies are modeled via `ResolvedPolicyGraph` edges (`dependeeId` and `dependentId`).

### 6.2 Discovery & Retrieval
- **FACT:** Retrieval from `PostgresRegistryRepository.lookup` fetches a complete, unified `RetrievedRegistryState` matching strictly by `identity_id === subject_id`.
- **FACT:** There is no generic dynamic SQL query interface. Callers lookup specifically by canonical identity identifier (`lookup`) or by list of IDs (`lookupEvidenceByIds`).
- **Identity Verification:** The retrieved structures are mapped to domain records and validated immediately upon mapping via domain-native validation helpers in `apps/api/src/registry/mappers.ts`, returning `DataCorruption` if invalid.

## 12. Dependency / Resolution Mechanisms
Factual evaluation of graph-handling components:
- **FACT — Present:**
  - `materializeResolutionGraph` (in `packages/runtime/src/evaluator.ts`) computes a deterministic topological sorting of applicable policy rules based on the `ResolvedPolicyGraph`.
  - It utilizes **Kahn's algorithm** with **lexicographical tie-breaking** on the ready set to ensure 100% deterministic ordering of execution paths.
  - Cycle detection is fully implemented: detects and fails with `CYCLIC_POLICY_GRAPH` on self-dependencies or graph cycles.
  - Referential integrity is verified: fails with `REFERENTIAL_INTEGRITY_VIOLATION` if an edge references a policy ID not present in the applicable policies set.


- **FACT — No matching implementation found within inspected scope:**
  - There is **no graph-based package dependency resolver** or generic version compatibility engine. Version constraints (e.g. semantic version ranges) are not dynamically parsed or resolved; they are either exact matches or handled out-of-band.
