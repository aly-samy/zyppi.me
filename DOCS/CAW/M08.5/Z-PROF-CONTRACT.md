# CONTRACT-R1 — Z-PROF Contract Closure
 
**Document ID:** `CONTRACT-R1` **Title:** Z-PROF Closed Contract Set **Program:** `CAW-011 — Commerce Atlas Wedge` **Milestone:** `M08.5 — Z-PROF Profile Architecture` **Version:** `v1.0` **Status:** `RATIFIED — CLOSED` **Authority:** Zyppi Constitutional Council **Implementation Authority:** `NONE` **Predecessors:** `Z-PROF-D1`, `Z-PROF-D2`, `Z-PROF-D3`, `Z-PROF-D4`, `Z-PROF-D5`, `M08.5-PREP`, `M08.5-PLAN`, `Z-PROF-001`
  
# 1. Purpose
 
`CONTRACT-R1` formally closes the contract boundary established by the Z-PROF investigation and constitutional architecture.
 
Its purpose is to establish the **minimum authoritative contract set** required for Z-PROF to exist as a governed domain-composition architecture without creating a competing:
 
 
- Reality model;
 
- ontology;
 
- Asset Profile system;
 
- Projection engine;
 
- Reasoning engine;
 
- Policy engine;
 
- Security model;
 
- Evidence engine;
 
- Registry;
 
- Runtime;
 
- execution authority.
 

 
The contracts defined here are **semantic and structural contracts**.
 
They are not implementation technology specifications.
 
They do not grant implementation authority.
  
# 2. Constitutional Position
 
Z-PROF is connective architecture between existing constitutional capabilities.
 
The governing principle is:
 
 
**Z-PROF composes existing constitutional capabilities; it does not become a new constitutional authority.**
 
 
The canonical direction remains:
 `                    REALITY                        │                        ▼               Asset / Domain Context                        │                        ▼                Z-PROF Composition                        │         ┌──────────────┼──────────────┐         ▼              ▼              ▼        PRJ            RSN          POL / SEC         │              │              │         └──────────────┼──────────────┘                        ▼                       RI ` 
Z-PROF may declare, bind, validate and preserve relationships among these capabilities.
 
The underlying capabilities remain independently authoritative.
  
# 3. Golden Question Invariant
 
The complete Z-PROF contract set SHALL remain subordinate to Zyppi's Golden Question:
 
 
**"Who did what, to whom, where, when, and how do we know?"**
 
 
The constitutional mapping is:

Did what?

To whom?

Time remains a constitutional dimension of Reality and is not introduced as a sixth primitive.
 
Governance and authority remain separate protective/evaluative concerns.
 
They do not become additional Reality primitives.
  
# 4. Naked Reality Constraint
 
Every Z-PROF contract SHALL preserve the following invariant:
 
 
**No Z-PROF composition, interpretation, representation or downstream presentation SHALL make a claim stronger than the Reality and Evidence supporting it.**
 
 
Therefore:
 `UNKNOWN      ≠ FALSE UNAVAILABLE  ≠ FALSE CONFLICTING  ≠ FALSE UNVERIFIED   ≠ VERIFIED INTERPRETED  ≠ OCCURRED AUTHORIZED   ≠ OCCURRED ` 
Governance cannot rewrite Reality.
 
Interpretation cannot become Reality.
 
Absence of Evidence cannot be silently converted into evidence of absence.
  
# 5. Closed Contract Set
 
The Council hereby recognizes the following contracts as the closed Z-PROF contract boundary.
 
## CONTRACT-01 — Domain Template Card
 
### Purpose
 
Defines the canonical domain-authoring and registration template.
 
The Domain Template Card answers:
 
 
**What does this domain require in order to participate in Zyppi?**
 
 
It SHALL describe domain requirements without implementing them.
 
### Authority
 
Z-PROF.
 
### Nature
 
Declarative, authoring/governance artifact.
 
### It MAY declare
 
 
- domain identity;
 
- domain scope;
 
- applicable Asset Classes;
 
- applicable ARM Profiles;
 
- domain vocabulary;
 
- Epistemic Requirements;
 
- required PRJ specifications;
 
- required RSN Blueprints;
 
- required Context dimensions;
 
- applicable POL requirements;
 
- applicable SEC requirements;
 
- required RI capabilities;
 
- external jurisdiction;
 
- supported compositions;
 
- version constraints;
 
- provenance requirements;
 
- domain-specific compatibility requirements.
 

 
### It SHALL NOT
 
 
- create Reality;
 
- redefine Reality;
 
- create an ARM Profile;
 
- redefine an ARM Profile;
 
- define projection mathematics;
 
- define reasoning methodology;
 
- authorize an operation;
 
- create security authority;
 
- execute an operation;
 
- perform infrastructure retrieval.
 

 
The Domain Template Card is **not a Runtime artifact**.
  
# 6. CONTRACT-02 — Epistemic Requirement Contract
 
### Purpose
 
Defines what must be known to satisfy a domain requirement.
 
It answers:
 
 
**What must be established before this domain interpretation or operation can legitimately proceed?**
 
 
### Nature
 
Declarative semantic contract.
 
### It MAY reference
 
 
- Subject requirements;
 
- Event requirements;
 
- Object requirements;
 
- Place requirements;
 
- Valid Time requirements;
 
- Evidence requirements;
 
- relationships;
 
- context;
 
- required projections;
 
- required reasoning inputs.
 

 
### It SHALL NOT prescribe
 
 
- SQL;
 
- GraphQL;
 
- database queries;
 
- storage mechanisms;
 
- network retrieval;
 
- cache mechanisms;
 
- transport mechanisms;
 
- infrastructure topology.
 

 
The Application layer determines how declared requirements are resolved.
  
# 7. CONTRACT-03 — Interrogation Contract
 
### Purpose
 
Defines the declarative expression of a domain's epistemic requirements.
 
Interrogation means:
 
 
**What information must be established from the authorized constitutional substrate?**
 
 
It does **not** mean:
 
 
"How should the database be queried?"
 
 
### Authority
 
Z-PROF semantic composition boundary.
 
### Requirements
 
An Interrogation SHALL be:
 
 
- declarative;
 
- technology-independent;
 
- deterministic in interpretation;
 
- bounded;
 
- provenance-preserving;
 
- explicit about required and optional information;
 
- capable of representing unavailable or conflicting information.
 

 
### Prohibition
 
The Interrogation Contract SHALL NOT become an infrastructure retrieval API.
  
# 8. CONTRACT-04 — Authorized Reality Surface
 
### Purpose
 
Defines the Reality that a composition is permitted to consume.
 
It establishes the boundary between:
 `Z-PROF requirement         ↓ authorized constitutional substrate         ↓ resolved Reality inputs ` 
### Authority
 
Existing constitutional authorities remain authoritative.
 
Z-PROF does not become owner of:
 
 
- Reality;
 
- Evidence;
 
- Identity;
 
- Registry;
 
- authorization;
 
- security.
 

 
Z-PROF merely declares the required surface.
  
# 9. CONTRACT-05 — Composition Contract
 
### Purpose
 
Defines the structural relationship among the capabilities required by a domain.
 
Composition SHALL remain:
 
 
- declarative;
 
- structural;
 
- reference-based;
 
- deterministic;
 
- version-bound;
 
- dependency-explicit.
 

 
Composition SHALL NOT contain arbitrary executable domain logic.
  
# 10. CONTRACT-06 — CompositionManifest
 
### Purpose
 
The `CompositionManifest` is the concrete, validated representation of a particular domain composition.
 
It answers:
 
 
**Which governed constitutional artifacts satisfy the requirements of this domain composition, and how are they bound?**
 
 
### It MAY contain references to
 
 
- Domain Template Card;
 
- ARM Profile;
 
- Epistemic Requirement Contracts;
 
- PRJ specifications;
 
- RSN Blueprints;
 
- Context requirements;
 
- POL requirements;
 
- SEC requirements;
 
- RI capabilities;
 
- version constraints;
 
- compatibility declarations;
 
- provenance references.
 

 
### It SHALL NOT
 
 
- contain canonical Reality;
 
- become a second Registry;
 
- contain unrestricted executable logic;
 
- replace POL;
 
- replace SEC;
 
- replace RI;
 
- replace PRJ;
 
- replace RSN;
 
- create a DomainJudgment as Reality.
 

  
# 11. CONTRACT-07 — Bound Constitutional Payload
 
A validated CompositionManifest MAY produce a downstream **Bound Constitutional Payload**.
 
This is the resolved set of constitutional inputs required by the downstream governed subsystem.
 
The Bound Constitutional Payload is:
 
 
- derived;
 
- validated;
 
- non-authoritative over its source artifacts;
 
- version-bound;
 
- provenance-preserving.
 

 
It does not become a new source of Reality.
  
# 12. CONTRACT-08 — Projection Binding
 
Z-PROF MAY declare that a composition requires a particular PRJ capability.
 
For example:
 `Composition     │     └── requires PRJ-X ` 
Z-PROF SHALL NOT define:
 
 
- projection mathematics;
 
- projection semantics;
 
- projection generation;
 
- projection canonicality.
 

 
PRJ remains authoritative for Projection.
  
# 13. CONTRACT-09 — Reasoning Binding
 
Z-PROF MAY declare that a composition requires a particular RSN Blueprint or reasoning capability.
 
For example:
 `Composition     │     └── requires RSN Blueprint-X ` 
Z-PROF SHALL NOT define:
 
 
- reasoning methodology;
 
- reasoning execution;
 
- planner internals;
 
- intelligence semantics.
 

 
RSN remains authoritative for Reasoning and Intelligence.
  
# 14. CONTRACT-10 — Context Binding
 
Z-PROF MAY declare required Context.
 
It SHALL distinguish:
 `Context Requirement         ≠ Context Interpretation ` 
Z-PROF may route or require Context.
 
It does not acquire authority to interpret Context merely by referencing it.
  
# 15. CONTRACT-11 — Composition Validation
 
Every CompositionManifest SHALL be validated before downstream admission.
 
Validation SHALL establish, at minimum:
 
 
1. referenced artifacts exist;
 
2. references are authorized;
 
3. versions are compatible;
 
4. dependencies are satisfiable;
 
5. ownership is unambiguous;
 
6. prohibited capabilities are absent;
 
7. Profile isolation is preserved;
 
8. no new constitutional primitive is introduced;
 
9. provenance requirements are satisfied;
 
10. the composition remains within its declared domain scope.
 

 
Failure SHALL be explicit.
 
A composition SHALL NOT be silently repaired by inventing missing semantics.
  
# 16. CONTRACT-12 — Conflict Result
 
Composition validation SHALL distinguish at minimum between:
 
 
- unsupported;
 
- unavailable;
 
- missing;
 
- incompatible;
 
- conflicting;
 
- unauthorized;
 
- unverified;
 
- invalid.
 

 
Z-PROF SHALL prefer existing constitutional error taxonomies where semantically applicable.
 
Z-PROF SHALL NOT create a parallel error constitution merely for convenience.
  
# 17. CONTRACT-13 — Provenance
 
Every resolved composition SHALL preserve sufficient provenance to establish:
 
 
- which Domain Template Card governed it;
 
- which CompositionManifest was used;
 
- which constitutional artifacts were referenced;
 
- which versions were bound;
 
- which evidence requirements were declared;
 
- which downstream capabilities were invoked or required.
 

 
Provenance SHALL not convert Z-PROF into an Evidence Engine.
 
The underlying Evidence and execution systems remain authoritative for their respective records.
  
# 18. CONTRACT-14 — Version Binding
 
Composition references SHALL be explicitly version-bound.
 
A CompositionManifest SHALL NOT silently float across incompatible versions of:
 
 
- ARM Profiles;
 
- PRJ specifications;
 
- RSN Blueprints;
 
- Epistemic Requirement Contracts;
 
- Context definitions;
 
- POL requirements;
 
- SEC requirements;
 
- RI capabilities.
 

 
A version change SHALL produce a new composition identity or otherwise follow the lifecycle rules established by the governing constitutional authority.
  
# 19. CONTRACT-15 — Replay Determinism
 
A composition SHALL be reproducible when provided with equivalent:
 
 
- CompositionManifest version;
 
- referenced constitutional versions;
 
- Context;
 
- Evidence;
 
- authorized inputs.
 

 
The governing invariant is:
 `Same composition + same versions + same context + same evidence + same authorized inputs         ↓ same result ` 
Execution Time SHALL remain distinct from the Valid Time of Reality.
  
# 20. CONTRACT-16 — Domain Judgment Boundary
 
`DomainJudgment` is **not** a Z-PROF constitutional primitive.
 
Z-PROF may establish the composition required to support a domain interpretation.
 
The resulting interpretation remains downstream under the appropriate RSN/Intelligence authority.
 
Therefore:
 `Reality    ↓ Evidence / Projection / Context    ↓ RSN    ↓ Domain Interpretation ` 
not:
 `Reality    ↓ Z-PROF DomainJudgment ` 
Z-PROF SHALL NOT make a domain interpretation canonical Reality.
  
# 21. CONTRACT-17 — Policy Boundary
 
Z-PROF may declare policy requirements.
 
It SHALL NOT:
 
 
- authorize;
 
- deny;
 
- override;
 
- weaken;
 
- reinterpret
 

 
a POL decision.
 
Authority remains with POL.
 
Governance protects Reality; it does not define whether the underlying event occurred.
  
# 22. CONTRACT-18 — Security Boundary
 
Z-PROF SHALL consume SEC-governed trust and security mechanisms.
 
It SHALL NOT create:
 
 
- alternative identity authority;
 
- alternative trust authority;
 
- alternative attestation authority;
 
- alternative cryptographic authority.
 

 
Security remains under SEC.
  
# 23. CONTRACT-19 — Runtime Boundary
 
Z-PROF SHALL NOT become a Runtime.
 
The established boundary remains:
 `Application      │      │ resolved constitutional inputs      ▼ RI Runtime      │      ▼ ExecutionOutput + ExecutionReceipt ` 
Z-PROF may provide validated structural requirements.
 
RI determines governed execution.
 
Z-PROF SHALL NOT place ambient I/O, infrastructure access or domain retrieval inside the constitutional Runtime.
  
# 24. CONTRACT-20 — Application Resolution Boundary
 
Infrastructure resolution belongs outside Z-PROF.
 
The Application layer MAY resolve Z-PROF declarations against:
 
 
- Registry;
 
- Evidence;
 
- authorized external sources;
 
- infrastructure;
 
- caches;
 
- transport systems.
 

 
Conceptually:
 `Z-PROF   │   │ "I require X, Y, Z"   ▼ Application Assembly   │   ├── Registry   ├── Evidence   └── authorized sources   │   ▼ Resolved Constitutional Inputs   │   ▼ RI / PRJ / RSN `  
# 25. CONTRACT-21 — Domain Isolation
 
Each domain composition SHALL remain isolated from other domain compositions.
 
A single Asset Reality MAY participate in:
 `Product Reality      │      ├── GS1      ├── DPP      ├── Customs      ├── Logistics      ├── Healthcare      └── E-commerce ` 
without requiring:
 `GS1 Product Profile DPP Product Profile Customs Product Profile Logistics Product Profile ... ` 
The architecture SHALL therefore support domain multiplication without Profile multiplication.
  
# 26. CONTRACT-22 — Disappearance Test
 
The following remains a mandatory architectural test:
 
 
**If Z-PROF disappears tomorrow, do the underlying constitutional artifacts remain valid, governed and independently usable?**
 
 
The test SHALL apply to:
 
 
- Domain Template Cards;
 
- CompositionManifests;
 
- Interrogation Contracts;
 
- domain bindings;
 
- projection references;
 
- reasoning references.
 

 
If deletion of Z-PROF would invalidate the underlying constitutional capability itself, the boundary has been violated.

# 28. Contract Completeness Test
 
The Z-PROF contract set SHALL be considered complete when a domain can be expressed through:
 `Domain   ↓ Domain Template Card   ↓ Epistemic Requirements   ↓ Interrogation   ↓ CompositionManifest   ↓ Composition Validation   ↓ Bound Constitutional Payload   ↓ Existing Zyppi Capabilities ` 
without requiring Z-PROF to acquire authority over:
 `Reality Ontology Evidence Projection Reasoning Policy Security Runtime Infrastructure UI `  
# 29. Golden Question Contract Test
 
A compliant Z-PROF composition SHALL ultimately support the truthful answering of the applicable Golden Question:
 `WHO?   Subject  DID WHAT?   Event  TO WHOM?   Object  WHERE?   Place  WHEN?   Valid Time  HOW DO WE KNOW?   Evidence ` 
The composition may determine **what constitutional capabilities are required** to establish these dimensions.
 
It SHALL NOT manufacture a missing answer.
 
If the substrate cannot establish a dimension, the resulting experience SHALL preserve that epistemic state rather than fabricate completeness.
  
# 30. Final Contract Closure Criteria
 
`CONTRACT-R1` passes closure when all of the following are true:
 
 
- Z-PROF has a single contract boundary.
 
- Every Z-PROF-owned contract has explicit ownership.
 
- Existing constitutional capabilities remain authoritative.
 
- No contract creates a competing ontology.
 
- No contract creates a competing Reality model.
 
- No contract creates a competing Evidence system.
 
- No contract creates a competing Policy or Security system.
 
- No contract creates a competing Runtime.
 
- Composition remains declarative.
 
- Interrogation remains epistemic rather than infrastructural.
 
- Domain Template Card remains an authoring/registration artifact.
 
- CompositionManifest remains a validated structural artifact.
 
- Domain Judgment remains outside Z-PROF.
 
- Projection remains PRJ-owned.
 
- Reasoning remains RSN-owned.
 
- Authorization remains POL-owned.
 
- Security remains SEC-owned.
 
- Execution remains RI-owned.
 
- Application remains responsible for infrastructure resolution.
 
- Provenance remains preserved.
 
- Version binding remains explicit.
 
- Replay remains deterministic.
 
- Domain isolation remains preserved.
 
- The Disappearance Test passes.
 
- The Golden Question remains the vertical semantic invariant.
 
- The Naked Reality constraint remains preserved.
 

  
# 31. Implementation Boundary
 
Contract closure does **not** constitute implementation authorization.
 
The following remain prohibited without an explicit AMS:
 
 
- creating a Z-PROF package;
 
- implementing the contracts;
 
- modifying the Runtime;
 
- modifying Registry semantics;
 
- creating production Domain Template Cards;
 
- creating production CompositionManifests;
 
- introducing a new Interrogation engine;
 
- modifying ARM/ZRM/PRJ/RSN/POL/SEC constitutional contracts;
 
- selecting infrastructure merely because it satisfies a contract.
 

 
The governing sequence remains:
 `Council defines meaning         ↓ Contract Closure         ↓ Architecture Closure         ↓ AMS Authorization         ↓ Implementation         ↓ Verification ` 
Jules executes only within an issued AMS.
